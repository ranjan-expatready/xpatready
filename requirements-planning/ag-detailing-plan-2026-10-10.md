## 2. What "done like SA-01 or SA-02" means

Read against SA-02 v2.19 (the most complete example) and SA-01 v2.2, a module is "done" when it carries these nine marks. This is the checklist the AG work must reach.

1. **Header.** Status reads "Reviewed — product decisions applied"; "Reviewed by: Tanu and Sanjay (product owners)"; "Code state verified <date> against GitHub `dev`: backend @ <commit>, frontend @ <commit>" (rule DOCS-6).
2. **§0 Decision log.** Module-prefixed decision IDs (SA2-D1 to SA2-D14), each with the exact requirement IDs and sections where it was applied.
3. **§0.1 Deferred.** Each deferred item with "why" and "reopen when", so it can be carried to the developers' deferral register.
4. **§0.2 Knock-ons.** Decisions other modules must apply (SA2-X1 to SA2-X11), each with an owner module and a status (Pending or "Applied in <file> <version>").
5. **§0.3 Release 1 priorities.** One line per slice: Must now, Should now, with the note.
6. **Body sections 1 to 11 updated in place.** Changed requirements marked "(changed vX.Y — decision ID)"; withdrawn requirements kept as one line; numbers never reused (rule 3); no "Phase 1" or "demo" wording (release vocabulary, AG17-D60).
7. **§12 Reference note rebuilt against `dev`** of both repositories on the review day, with both commit ids (and a dated note when `dev` has moved since), split into "on `dev` today and in conflict — stop or reverse", "built and usable", and "gaps against this version".
8. **§13 Open questions closed.** Either "None — all closed by the product owners on <date>" with a closure table, or only items routed to a named outside owner (Immigration SME, counsel) with what is being asked.
9. **Bookkeeping.** New file name with version and date, previous file in `_archive/`, change-log row with decision IDs; `00-Overview` scope row and `99-Phasing-and-Glossary` row aligned; file sent to the development team (they update Confluence and Jira, DOCS-4) and the older sources it supersedes named (rule 8, so Spec Kit features are re-based); QA writes the test scenarios and cases (SA-02 scenarios 22–24 Sep, approved by Sanjay and the developers; Action Item Tracker).

What happened after SA-02 reached this state is also part of "done": the developers re-based `specs/002-sa2-module-contracts/spec.md` on the shared file (its header now names `SA-02-tenant-firm-management_v2.8` as the only requirements source), and the firm screens were walked through with Sanjay on 26 Sep (tracker).

## 6. SA-1B: before or after the AG modules?

**Answer: now, in parallel with Wave 1, as its own track. Not after AG, and not instead of AG.** The remaining SA-1B *requirements* work is one revision pass plus one content-scope session; the reasons it cannot wait are these.

3. **It is on the build's critical path for reasons that have nothing to do with AG.** A country cannot be activated until it has a published production pack (SA-1-4), and a firm whose country has no published pack sits in "waiting on platform" and cannot become ready or open cases (AG-01 §3.4 and §13 Q2); the Charter notes state the same dependency in the words "packs must be published before any firm can be created". ### 7.4 How to do it: one repeatable "module review pass" (Recommendation)

One module = one pass; a pass is five steps and about two working days of calendar, with one founder-facing session in the middle. Three passes a week holds the Appendix D dates.

| Step | Who | Input | Output |
|---|---|---|---|
| **A. Prepare** (half day, no decisions taken) | Claude Code | Fresh read-only copies of both repositories at today's `dev` and the newest Drive snapshot; the module file; its row in `00-Overview` and `99-Phasing`; its section of `SCOPE-TRIAGE`; every §0.2 row in every other file that names this module (pending knock-ons); its rows in the developers' `DEFERRALS-REGISTER.md`; the frontend QA sheet, mock store and backend spec or branch if any | A **review brief** of five parts: (1) the triage proposals and the requirement IDs they touch; (2) every open question in §13 with a recommended answer and the evidence for it; (3) conflicts with other modules, the Charter or the Founder Decisions Log; (4) a draft §12 against today's two commit ids; (5) items to route outside (Immigration SME, counsel) and the knock-ons this module will emit |
| **B. Decide** (60–120 minutes) | Sanjay and Tanu; Ranjan only for triage items and founder decisions | The brief | Numbered module decisions (AGn-Dx), deferrals, knock-ons; founder decisions recorded in the Founder Decisions Log when they change Release 1 scope |
| **C. Apply** (half day) | Claude Code | The decisions | New file version with the nine marks of §2: header, §0 to §0.3, body edits "(changed vX.Y — ID)", §12, §13 closed; `00-Overview` row, `99-Phasing` row and glossary aligned; previous file to `_archive/`; change-log row |
| **D. Check** (2 hours, separate session) | An independent Claude Code session acting as adversarial checker | The new file, the previous version, every file it references | A findings list against a fixed checklist: IDs permanent and unique; every decision's "where applied" exists; every emitted knock-on is recorded as Pending in the receiving module or applied; no "Phase/demo" leftovers; nothing restated from another module; quotes match; §12 commit ids equal today's `dev` heads; glossary terms used consistently. Nothing goes to Sanjay before the findings are fixed |
| **E. Share** (same day) | Sanjay | The file and its change-log row | Sent to the team with the list of older sources it supersedes (rule 8); the team re-bases Spec Kit or the `build-from-spec` plan, updates Confluence and Jira (DOCS-4); QA writes scenarios and cases in the agreed format; the module appears in Appendix D as "Delivered" with the date |

Two operating rules make this scale: **one knock-on day a week** (apply all pending cross-module items in one batch, one version bump per file, instead of a ripple per decision), and **the master stays on Drive** (Claude Code writes to local copies only; Sanjay uploads the new version file to the master folder and moves the old one to `_archive/`, exactly as DOCS-2 describes). The whole of step A, C and D can be packaged as one project skill (for example `/fr-review AG-NN`) with the brief template, the nine-mark checklist and the checker list inside it, the same way the frontend team packaged `build-from-spec`.

## 9. Plain-words glossary

| Term | In plain words |
|---|---|
| Techno-functional document (Doc 1 to Doc 4) | The high-level requirement books written in June and July, one per plane; the per-module files below them give the exact behaviour |
| Module file (SA-nn, AG-nn, CP-nn) | One Markdown file per module on Drive, the only requirements source for the team (DOCS-7) |
| Decision log, knock-on | §0 of a module file records the product owners' decisions by ID; a knock-on is a decision another module must apply, listed as Pending until that module's review applies it |
| §12 Reference note | The section that says honestly what exists in the code today, what is new and what changed, checked against a named GitHub `dev` commit |
| `dev`, commit, branch | `dev` is the shared development line of the code on GitHub; a commit is one saved change with an id; a branch is work not yet merged into `dev` |
| Mock UI | Screens that look real but run on sample data in the browser and save nothing; the team's way to review screens before the server side exists |
| Spec Kit, `build-from-spec`, `/akplans` | The team's Claude Code tools: Spec Kit turns a module file into a backend specification and task list; `build-from-spec` turns an AG file into mock screens; `/akplans` is the backend planning routine |
| Country Pack, configurator, resolver | Canada's immigration rules held as data (SA-1 holds and publishes it; SA-1B holds the content); the configurator is where a row per programme is assembled; the resolver turns a row into a client's questionnaire, checklist and form list |
| Practice Pack | The firm's own rules: regulator, trust money, fees, retention, privacy (FD-22); a different thing from the Country Pack |
| PQR, SQR | The short prospect questionnaire and the full smart questionnaire |
| Filing | One application to one authority inside a case (a family's separate permits sit side by side; a two-step route runs in sequence) |
| Conductor, Doers, Needs you | The automation engine ("when X, do Y"), its named workers (Minder for dates, Reader for documents, and so on), and the inbox of items waiting for a person's approval |
| Four-eyes, Filler, deficiency library | A second person approving a government form; the engine that would fill government forms; the list of standard reasons a case is not ready |
| Golden journey, G1 to G6 | The nine end-to-end business scenarios that must pass before launch; the six founder gates of the Charter |
| SME, RCIC, CICC | The Immigration Subject Matter Expert (Ishaan); Regulated Canadian Immigration Consultant; the College that regulates them |
| Must now / Should now | The Release 1 priority labels used in §0.3 of a reviewed module |
