1Scope and principles

  1. AI drafts and reads; code checks and fills; people decide. Nothing the engine produces is live until two people have handled it.
  2. Reuse first. A fact, document type or section that exists is reused; a new one is created only when nothing fits.
  3. Every item cites its source. File, page, box or passage, with the date it was read.
  4. Scored before trusted. Each AI step runs against a hand-verified test set and must meet its agreed score.
  5. Versioned. Every item has a version; a case keeps the version it started on until a person adopts a new one.

Terms. Combination: Pathway › Program › Category › Sub-category. PQR: pre-qualification questionnaire, one per country, in blocks. SQR: the full questionnaire for a combination. Master field: one shared definition of a fact. Box address: whose fact a form box shows, which field, which row, which format. Agent: firm staff.

2Architecture

  1. A separate engine service runs the read, build and check stages. It can start outside the product and feed the platform's existing draft import; later the configurator's "run" button calls it.
  2. The platform keeps ownership of the master library, versions, release and every case screen. The engine never writes to a released version.
  3. AI is called only from the builders and change watch, through the provider's SDK, with typed tool calls into the draft. No agent framework is needed.
  4. The barcode-form filler is its own small service if its best library is Java or .NET; everything else stays in the product's language.

3Read: sources into structured inputs

  1. Forms. Every box: internal name, printed label, type, maximum length, allowed options, required flag, page, position and reading order. The count must equal the form's own box count.
  2. Barcode forms. The same, read from the form's template, plus each show/hide script, which becomes a candidate rule ("show spouse section when marital status is married").
  3. Checklist. Each line becomes an item: document name, who provides it, and any "if applicable" note.
  4. Guide. Passages that state who must complete what and when ("fill out this form only if…") are kept with their heading or page.
  5. Portal. The extension captures each screen's field list and labels in the representative's session.
  6. Failure rule. A file or part that cannot be read stops the run and is named; nothing is skipped silently.

4Build fields: reuse first

  1. Known label, same context: matched by rule. "Context" means the form section and whose fact, so "Family name" under the spouse heading never matches the applicant's family name.
  2. Unknown label: the AI proposes the closest existing field with a confidence and a one-line reason. Below the review threshold, a person checks it.
  3. No fit: the AI proposes a new master field with type, validation taken from the form's own limits, whose fact (person or organisation) and tier: lead, prospect, case or staff-only.
  4. Learning. Every approved label is saved on its field, so the next form matches it by rule. Reuse grows with every combination.
  5. Guard. A proposed field too similar to an existing one blocks submission until a person merges or confirms it.

5Build sections: one library, each form's own layout kept

  1. One shared section library organises questionnaires and the agent working view, so a name is always in "Personal details" on every combination.
  2. Each form keeps its own layout: its section names, field order and grouping, used only by the form check view. "Personal history" on IMM 5669 and "Employment" on IMM 1295 both point to the library's "Work history".
  3. Placement once. The AI places each new field in a library section; a new library section is proposed only when none fits; a person approves once and every combination reuses it.
  4. Different fields under the same name. Allowed: the form layout lists exactly the boxes that form prints; the library section holds the union.

6Build documents and rules

  1. Documents. Each checklist item becomes a document line linked to a reused or new document type, with who provides it (client, employer, government) and whether it is base or conditional.
  2. Base versus conditional is per person. A form that is base for the principal can be conditional for others: a family member's own copy depends on role, age and whether they apply.
  3. Three rule sources. Show/hide scripts inside barcode forms; guide passages ("fill out only if"); checklist notes ("if applicable"). Each drafted rule keeps its source.
  4. One rule language. Rules are written in the product's condition language (equals, in, exists, and, or, not) over master fields, so the server evaluates them the same way for the client portal and the agent screen.
  5. People confirm, never write. The specialist accepts, edits or rejects each drafted rule and value.
  6. Judgement is not a rule. "If the officer requests" becomes an agent request on the case.

7Build questionnaires

  1. The PQR comes before the combination is known. One per country, in blocks that unfold from intent and status; the engine reports each combination's PQR as the blocks it reads, and flags rule fields no block asks.
  2. The SQR asks the fewest questions. A question dropped because a document supplies the fact returns automatically if that document is missing, unreadable or in conflict.
  3. Each tier pre-fills the next; nothing is asked twice across lead form, PQR and SQR.
  4. Staff-only facts (representative details, application numbers, boxes only the firm completes) are a fourth tier. A unique client identifier is asked and also read from an old permit.

8Build form and portal maps

  1. Every box gets a box address: the copy owner, whose fact relative to the owner (self, spouse, child 2, mother), the master field, the row for lists, the format, and the overflow rule.
  2. Copies per person. The rules decide which people complete which form; each gets their own copy, rendered from their facts and the facts of the people their boxes describe.
  3. Value lists. Each answer value maps to the form's own option ("Korea, South" against "South Korea"); a miss refuses rather than guesses.
  4. Portal maps are built the same way from captured screens and versioned like form editions; a changed screen stops filling.
  5. Gap in today's platform: a map entry holds only field and box. The box address is a required extension.

9Check: proven before a person looks

  1. Completeness. Every box mapped or explicitly marked; every checklist item linked; every rule's fields exist.
  2. Consistency. No near-duplicate fields; no condition that can never be true; no hidden field that a form reads.
  3. Test families. One made-up family per branch (single, married, common-law, with children, inside or outside Canada) is generated and previewed per person.
  4. Scoring. On the hand-verified test set, each step reports precision (how many proposals were right) and recall (how much it found). A step below its agreed level stays switched off.
  5. Result. A check report that blocks submission until resolved, and becomes part of the package.

10Review and release

  1. Only what needs a person. New fields, uncertain matches, new document types, rules, section placements and check findings. Rule matches are hidden by default but open on demand.
  2. Evidence beside each item. The source box or passage, the confidence and the reason.
  3. Three actions. Accept, edit or reject; every decision is logged and teaches the next run.
  4. Two people. The author submits; a second publisher releases or rejects with a reason and never edits.
  5. Roles. Content publisher reviews structure; the immigration specialist reviews rules and values.

11Publish and change

  1. One package per combination holds every item the engine built, its sources, the check report and the difference from the last version.
  2. Import. The package loads through the platform's existing draft import; release follows the platform's existing two-person path.
  3. Versions. Each item carries its own version inside the pathway version; a case keeps its version.
  4. Change watch. Official form pages and guides are re-read on a schedule. A new edition re-enters the pipeline for changed boxes only; affected combinations and open cases are listed.
  5. Open cases. Each sees "what changes for this file" and a person adopts it; after a government cut-off, adoption is required.

12Data model

  1. Everything joins at the master field. Boxes, rules, sections and facts all point at it.
  2. Exists today: master fields, sections, document types, form editions with box inventories, map entries (field and box only), facts per person with supersede and history, combination rows and versions.
  3. To add: box address on map entries; staff tier; approved labels and plain meaning on fields; each form's own layout; conflict state on facts; source and score on every engine-built item; portal maps.
  4. Facts: one current value per person per field; a newer verified value supersedes; a contradicting declared value raises a conflict; a case-only difference is an override on that case.

13How the package runs at case time

  1. Duplicate check on email, phone or organisation name asks "same person?" everywhere a person is created; nothing is merged at capture. A returning client starts with confirmed facts; only "still true?" items are re-asked.
  2. Opening a case pins the combination's version and gives each person a role; the rules decide each person's forms and documents.
  3. Ask once. PQR answers, SQR answers, read documents and agent entries all land in the fact store; no screen keeps its own copy.
  4. Fill everywhere. Each box resolves through its box address to one confirmed value. One fix re-renders every affected form and withdraws earlier approvals.
  5. Outputs. Standard PDFs filled by rules; barcode forms get their data written and a person clicks Validate; the portal extension types, reads back and stops on change. The licensed representative approves and submits.

14Individual, family and corporate

  1. Same engine, same package shape. The difference is the subjects and the "for whom" on each rule and line.
  2. Family. The highest value: the same facts appear on several people's forms and on boxes about each other. The box address is what makes it correct.
  3. Corporate. The employer is a subject in its own right; its facts are reused across its cases; each worker stays an individual with a linked case.
  4. Edge cases the rules must cover: spouse not applying, child turning 18 during a case, a worker already a client, a household address shared by spouses.
{{SCREENS}}

15Screens

  1. Two setup screens (configurator grid, review workbench) and one release screen are all the content team uses.
  2. Two client screens (PQR, portal SQR) take answers and uploads; nothing is configured per firm.
  3. Two agent screens: the working view is the only place a fact is typed; the form check view shows each form as it will be filed and is read-only.
  4. Every layout comes from the package, so a new combination needs no screen work.

Acceptance

  • Each engine step meets its agreed precision and recall on the test set.
  • Zero wrong values on filed forms in the pilot, confirmed by a second licensed check.
  • Configuration hours per combination and review minutes per file measured against today's baseline.

For an implementation partner's quote

  • The platform's existing data model, import and release paths are reused, not rebuilt.
  • Immigration values and rule meanings are supplied and signed by the client's specialist.
  • The AI provider contract and data terms are the client's.
  • Portal filling is switched on per portal after its terms are checked; legal review is the client's.
  • Firm-specific questions are excluded.
