Part A · Executive slides
Executive summary1

An AI configuration engine reads the government's own forms, checklists and guides, and builds each combination's setup for people to approve

The problem

Every immigration combination is configured by hand: the document list, the fields, the sections, the form mappings, and the rules that add fields, documents and forms when a client's answer requires them.

It is slow, it repeats with every new combination and every new form edition, and each mistake reaches a client's form.

The solution

An engine reads the same sources a person reads and produces the whole configuration as one package: documents, fields, sections, rules, questionnaires and form maps.

Plain code does the reading and checking. AI does the judgement. A person approves only what is new or uncertain; a second person releases.

The result

A combination is configured in a review session, not built from scratch. Form changes touch only changed boxes.

Clients are asked each fact once, and every form and portal screen fills from the same confirmed facts.

The problem2

Nine setup artefacts are built by hand for every combination, and an error in any of them reaches a client's form

1Master list of documentswrong: client never asked for a document
2Master fields (one name per fact)wrong: the same fact stored twice
3Sections and field placementwrong: questions scattered, asked twice
4Same section, different name and fields per formwrong: agent cannot match screen to form
5Box-to-field map, including spouse and child boxeswrong: right value in the wrong box
6Rules that add fieldswrong: spouse details never asked
7Rules that add documents and formswrong: IMM 5409 missing for common-law
8PQR and SQR question setswrong: too many or missing questions
9Rework at every form editionwrong: open cases filed on stale forms

Why people cannot simply write it

  • Each combination draws on several forms, a checklist and a guide; every box must be read.
  • Rules hide in guide prose ("fill out only if…") and inside barcode forms' own scripts.
  • Business staff know the outcomes, not a rule language; asking them to write rules adds errors.
  • The work repeats for every new combination and every form edition, forever.
Example combination: individual · work · work permit · employer-specific. Base forms IMM 1295 and IMM 5707; IMM 5409 only if common-law; IMM 5476 only if a representative acts; the official checklist; the instruction guide.
The solution3

The engine works like a careful analyst: it reads, builds and checks, then a person approves

Code where possible. Reading boxes, matching known labels and checking are exact and repeatable.
AI where judgement is needed. New labels, guide prose, document meaning, section placement.
Every item cites its source. A reviewer sees the page or box it came from.
Proven before trusted. Each AI step is scored against combinations the specialist verified by hand.
What it produces4

One approved package drives every questionnaire, every screen and every form

Ask once. A fact from the PQR, the SQR, a document or the agent is stored once and never asked again.
Fill everywhere. Each form box knows whose fact it shows; one fix re-fills every form.
No AI at fill time. Filling is rules over approved maps, so the same facts always give the same form.

What we will measure

  • Hours to configure one combination, by hand and with the engine
  • Items a person reviews per combination
  • Boxes typed by hand per family file
  • Wrong values on filed forms (target: zero)
  • Hours to absorb one form edition

Today's figures are not yet measured; the first combination produces the baseline.

Next steps7

Four steps take the engine from one proven combination to every pathway

1

Build the test set

Configure two to three combinations by hand; the specialist verifies every document, field, rule and map.

Owner: content team and specialist

Done when: the answer key exists

2

Prove the engine on one combination

Run read, build and check on the work-permit combination outside the product; score each step.

Owner: build team

Done when: each step meets its score

3

Connect review and import

Review workbench, second-person release, package import, versions, and the platform additions below.

Owner: build team

Done when: a released package runs a test case end to end

4

Scale and embed

All combinations; change watch on form editions; the engine runs from the configurator's "run" button.

Owner: build team and content team

Done when: new combinations need review only

Platform additions the engine needs: box address on form maps · staff-only fields · each form's own section layout · conflict state on facts · barcode-form filler · portal extension · review workbench
