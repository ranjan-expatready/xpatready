## Recommendation and reason

Use a compact program table as the main entry, with expandable combination rows and direct access from cells to the corresponding editor. Keep the existing combination workspace for detailed configuration, preview and release. This preserves the founder's row-and-cell idea while keeping complex rules and long lists readable.

The user needs to find, compare and maintain about 100 programs, each with several combinations. A program card gallery makes comparisons depend on repeated scanning and navigation. A giant spreadsheet containing every condition, document and question would instead create too many columns and ambiguous edits. The recommendation is a task-based design inference, not a measured claim of being the most usable interface available. Validate it with realistic tasks before calling it proven.

## Screen behavior

1. **Overview:** one parent row per program, pathway as a filter/breadcrumb; expand to show the actual full configuration/combination rows. Parent rows summarize and navigate; child rows own configuration. No fixed “combination 1/2/3” columns: programs can have different numbers of combinations.
2. **Compact columns:** Program/combination, Forms, Questions/sections, Documents, Rules/checks, Review/release. Updated date and extra metadata can be optional. Program counts must say whether they count distinct items or combination usages; never add shared definitions together and call them unique. Keep the name/context visible; avoid horizontal scrolling for the default desktop overview.
3. **Find and see:** search across program/combination names and stable keys, with linked form identifiers where supported; pathway and review/attention filters; useful sorting, clear active filters and empty/error/loading states. A match in a child must reveal its parent and the matching child. Released version and pending draft changes must be visible together; do not hide a draft issue behind a green released badge.
4. **Select and edit:** click the Forms/Documents/Questions/Rules cell on a combination to open that precise area. Short edits may use an inline control or small focused panel with Save to draft and Cancel. Full lists, condition builders, sources, field maps and previews use the existing full-width workspace. Show the program, full combination, item, person scope and draft/released mode throughout. Return restores search, expansion, selected row and scroll position.
5. **Shared versus local:** clearly distinguish a placement/requirement on this combination from a shared canonical definition. A shared edit shows where used and affected combinations before submission; changing the view must not bypass existing permissions, stale-approval handling or separate release. No silent fan-out, publish toggle, direct JSON/SQL authoring or AI invocation from merely opening a row.
6. **Operational tools:** add a combination and attach forms through normal services; show AI job state and proposed/reused/new/ambiguous results in context. Preserve the current review/release journey. Keep SA-1B-61 row-copy and selected-row add/remove requirements tracked; implement only the bounded slice needed by the current outcome, not a new general spreadsheet engine or bulk approval route.
7. **Practical scale:** exercise at least 100 clearly labelled synthetic programs with several combinations in an isolated demo/review copy, separate from the five meaningful demo programs. Allow all 100 to be browsed; keep combinations collapsed until requested. Avoid one expensive request per row. Measure first display, filtering, expansion, errors and responsiveness. Add paging/virtualisation or a grid dependency only for a demonstrated gap under D278; fixture rendering alone is not backend scalability proof.

## Inline and full configuration: D283 clarification

This is a refinement of the **pathway configurator**, not a redesign of the generated applicant SQR. Pick it up at NEXT's existing D279 layout step, after the current recorded gates; no new task, immediate restart or approval round.

Use two depths of interaction over the same saved configuration:

- **Overview:** compact program rows and their combinations support scanning, state comparison and small permitted edits with clear Save/Cancel or equivalent reliable save feedback. Program name edits belong to the program; a configuration item belongs to its exact combination or explicitly shared definition.
- **Full combination page:** the combination name and **Open full configuration** link open a real application route, normally in the same tab. Native link behavior can support opening another tab when the user chooses. Show program/full path, combination, applicable people, draft/released version and next action prominently. Reuse the existing combination workspace and the D280 contextual AI controls.
- **One editing model:** inline and full-page changes use the same record ids, current revision, validated service operations, permission checks and review/release path. Do not fork a second configuration or require users to copy data between modes. Preserve visible saved/unsaved/error state, handle concurrent changes, and restore the overview's search/filter/selection/expansion/scroll on return.

The full page needs comfortable body/label sizes, clear headings and room for long names, document lists, conditions and source evidence. Start from the team's readable typography scale and verify normal use and zoom; do not use tiny text to fit every detail into a row. Choose a small number of task-based tabs or anchored sections. Suggested content groups are Sources and forms; Questions and sections; Documents and checklist; Rules and checks; Preview; Review and release. Overview/people/version information can live in the page header or a concise overview. These are content responsibilities, not a requirement for another nested navigation hierarchy or every section open simultaneously.

In particular distinguish:

1. **Official setup sources:** attach official forms, checklist PDFs and guides through the existing normal source-upload path, with edition/status and relevant AI read/draft/reuse actions. A convenient upload entry in the Documents/checklist area should use that same handler and source record.
2. **Configured document requirements:** base and conditional requirements, who each applies to, the plain-language reason, evidence and rule/condition. These determine the generated case checklist; they are not uploaded client evidence.
3. **Case/client evidence:** later collection and extraction on an actual case remain in their existing journey. This screen clarification neither moves that work into global configuration nor expands the approved processing route.

The maker should choose the simplest grouping based on complete operator tasks, preserve useful existing controls and report justified deviations. The current code already has a combination route with Overview, Sources/forms, Configuration, Preview and Review/release; its presence is inspected evidence, not proof this usability refinement is implemented or accepted.

**Add to the existing layout proof:** find a combination from a large catalogue, make a quick permitted edit, open its full page at the right section, upload an allowed official checklist through the normal path, edit a conditional requirement, preview its effect for the right person, save/reload and return with list context restored. Confirm both modes show the same saved change and preserve release controls. Exercise a long label/list, unsaved departure, stale concurrent edit, keyboard navigation and zoom. Record observed task success, not an unsupported best-in-class rating. No new paid run or infrastructure is required by this planning note.

### Structure recommendation — challenged, not a universal optimum

Retain the bounded business hierarchy in SA-01B v1.5 §4–5: country/pack context → Pathway (Individual/Corporate) → Program → Category → optional Sub-category. It separates client type, immigration area, opened application and a meaningful content variant. A flat program list obscures those distinct configuration scopes; an arbitrary-depth taxonomy adds an editor and validation burden without a demonstrated need. This is the recommended fit for the recorded requirements, not proof that it is universally best or usable without testing. Sub-categories are absent where the category itself is terminal. Family composition, inside/outside location, source edition and filing stage do not automatically become more hierarchy levels. Applicability conditions and the pinned released version remain separate from identity.

**Challenge to the founder's assumption:** category names are not necessarily one universal interchangeable list. The same label in different program/country contexts may describe different content. Reuse an existing *identity in its allowed context*; never merge nodes by label alone. The maker must reconcile the saved code's STREAM/CATEGORY enum vocabulary with the requirement's Category/Sub-category labels; do not silently change persisted meanings.

### Selection and master maintenance

1. **Default workflow:** searchable, labelled selections over existing master IDs. Filter Program by Pathway, Category by Program, Sub-category by Category and everything by country/pack. Clear incompatible descendants when a parent changes and state what changed. Hide or disable Sub-category with a clear “No sub-category” value when the category is terminal.
2. **Keep ordinary configuration out of free-text taxonomy creation.** “New configuration” selects a complete existing path, checks for an existing configuration and offers Open existing rather than creating another one. Maintain program/category definitions through the existing authorised master-authoring path. A convenient “Add missing master” entry may open that same governed editor; it does not create a second service, bypass review or give firms taxonomy authoring.
3. **One master home:** assess the existing ProgramDef hierarchy/catalogue first; four pickers do not imply four new tables or duplicate lookup systems. Parent/context constraints belong on the server as well as the picker. Use immutable stable IDs/keys; labels can change without breaking references.
4. **Duplicate prevention:** enforce the actual key/context uniqueness in persisted services, including concurrent creates. Detect trivial duplicate labels within the same allowed parent/kind/country after boundary normalisation; point to the existing record. Aliases/near matches can assist human review but must not silently merge genuinely different concepts. Do not normalise the displayed input on every keystroke.
5. **Change impact:** show where a shared master is used before a consequential edit. Disable/retire rather than deleting referenced history; preserve existing released configuration and case pins. Master edits follow applicable existing permissions and draft/review/release, not a new approval process.

## Options researched

| Layout | Fit and trade-off |
|---|---|
| Current program cards | Useful entry for a small catalogue; retain useful content, but not the recommended default for comparing 100 programs |
| Program table with combination rows | Recommended default: compact program scan, clear hierarchy and direct configuration access; aggregates and edit scope need explicit labels |
| Flat table, one full combination per row | Useful within a selected program or when comparing combinations; repeat the program/path so rows remain understandable. Maker may use this as the simpler implementation if tasks succeed; no mandatory second mode |
| Tree navigation plus full editor | Strong for sustained editing, weaker for cross-program comparison; the existing detailed workspace can supply it without rebuilding the engine |
| All configuration in spreadsheet cells | Reject as the default: long conditional lists, shared definitions and release duties do not fit simple cells; no need for an Excel clone |

**Primary sources opened 21 October 2026:** [Carbon data-table guidance](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines), Overview and Placement, supports sorting/search/expansion and cautions against treating a data table as a spreadsheet or cramping nested tables. [PatternFly table guidance](https://www.patternfly.org/components/table/design-guidelines/), tree tables/expansion, supports related nested rows and revealing detail that exceeds a row. [PatternFly primary-detail](https://www.patternfly.org/patterns/primary-detail/design-guidelines/) supports editing a selected item's details while retaining list context. [WAI-ARIA grid pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/) describes keyboard/focus responsibilities for an interactive grid. These inform the recommendation; they do not establish a universal UX winner or require importing those libraries. Prefer semantic table controls; if implementing a true grid/treegrid, implement and check the complete applicable keyboard behavior.
