# AI that moves the work forward

Founders' research brief | Expat Ready | 13 October 2026

**Proposal, not a ratified design.** *Incorporated 13 Oct 2026 as the research appendix of `../concept.md` (AIW-D124, D126); moved from `parked/founder-research/`, links re-based, text unchanged.* This appendix-ready research supports the Lead's design comparison of 13 Oct (decided as AIW-D124; its summary is in `../concept.md`). The recommendation aligns with its option C: a simpler experience over retained delegation and run records. Page 1 explains the idea; the appendix holds alternatives, functional detail and evidence.

## One assistant in the work, with rules underneath

For a solo or small consultancy, organise assistance around the application file, from enquiry to decision. It reads permitted evidence, identifies missing or conflicting facts, prepares work and shows what needs attention. Keep assistance in lead, billing and firm administration screens too.

**Stages organise work. Roles assign responsibility. Rules control effects. AI handles language and ambiguous evidence.** These choices complement each other; they need not create separate AI personalities.

<!-- visual: layers -->

| The experience | The foundation |
|---|---|
| Intake / File build / Filing and after | Position derived from existing product states, with cross-stage corrections |
| One firm review inbox | Sources, proposed changes and item-specific approvals; internal platform work stays separate |
| Assistance in the current screen | Shared skills, delegated permissions, existing product rules and recorded results |

## The first valuable experience

A document upload becomes a review bundle: proposed facts with sources, conflicts, missing information and a draft follow-up. The consultant corrects or accepts facts; the product records authorised changes and refreshes affected forms and drafts. AI-written messages wait for the required approval before sending.

**Value hypothesis:** less repeated entry and a clearer route to a review-ready file. This is not a measured saving. A calm interface should show useful results and decisions, with chat available when it helps.

**Why recommend it?** It fits the buyer's file journey while preserving firm-wide work and existing controls. It avoids requiring the person to understand an AI organisation chart. Its hardest work is selecting sufficient context, handling changes and keeping approvals understandable.

**Next decision:** resolve the Lead's self-approval question first, then choose the product shape. No feature is removed by this recommendation.

# Appendix A | Four credible approaches

These compare how assistance is organised, not four model brands. Each can use rules and AI. The judgments are hypotheses, not measured rankings.

## 1. Automation first

**Experience:** existing screens, templates, checklists and reminders, with bounded AI extraction or drafting.

**Strength:** predictable steps, calculations and checks remain inspectable. This foundation belongs in every option.

**Limitation:** isolated task assistance may leave cross-document context, correction propagation and next-action coordination to the person. Its AI can handle language; the weakness is the connected experience. Choose this alone where bounded tasks meet the need.

## 2. Roles first

**Experience:** four firm teammates for intake, case work, billing and ownership; two separate internal Expat Ready teammates. It is not six assistants sold to the firm.

**Strength:** clear ownership of work across files, especially billing and operations; useful views for larger teams.

**Limitation:** one person may do all four jobs. Separate identities and handoffs can add navigation and explanation overhead. Runtime overhead is not inevitable: roles may share skills and orchestration. Keep ownership and work views without requiring separate personalities.

## 3. Stages first

**Experience:** one file assistant guides intake, file build, then filing and after, with a shared review inbox.

**Strength:** the person recognises the journey, next result and home for evidence.

**Limitation:** rigid stages mishandle reopened facts. Strict case-only coverage misses unconverted leads, receivables, imports and privacy work. A run that automatically follows a new owner needs an explicit design; stage labels alone do not provide it.

## 4. Assistance that understands the current work

**Recommended hybrid:** stage-led file view, assistance in other existing work screens, one permission-filtered firm inbox. Retain the current specified delegation/run contracts; roles govern ownership, skills prepare work and product rules govern effects.

**Strength:** combines journey clarity, practice-wide coverage and predictable execution. Use bounded model reasoning where language or evidence genuinely varies.

**Limitation:** context selection, change propagation and review need careful integration. One interface must not imply unlimited data access or an automatically transferable delegation. Prefer another view if testing shows less review effort at equal correctness.

**Why not chat as the main product?** Chat can request work, but people should not need to discover features by prompting or reconstruct a file before receiving help. Show evidence, proposed effects and available actions in the work screen.

**Research basis:** official orchestration guidance favours starting simply and adding specialists for concrete benefits; it does not establish which Expat Ready interface users will prefer. Sources are in Appendix C.

# Appendix B | Functional experience and controls

The following is a proposed fictional scenario. Existing permissions, mandatory checkpoints and action-specific controls still apply.

| Step | Observable result |
|---|---|
| 1. Evidence arrives | Usable, permitted upload links to the right lead/file; unusable evidence is flagged |
| 2. Prepare | Values link to document/page; conflicting sources remain visible |
| 3. Review | Show current/proposed values, missing facts and consequences |
| 4. Apply | Record authorised changes; refresh affected forms/drafts; void approval of changed previews |
| 5. Continue | Approve AI-written follow-up; recheck send conditions; record outcome |

**Failure example:** conflicting birth dates must show both sources and require resolution, rather than guessing or overwriting an accepted value. Provider failure preserves accepted work and leaves a manual route. Retry must not duplicate effects or charge another unit for correcting a system error.

Each review card shows source, change, effect and action; history opens on demand. Bundles retain item-specific approvals. Rules calculate; authorised people approve consequential effects; the product executes and records them. Signatures remain with the signer. Those need decisions/integration, not a cosmetic rename. The Lead's wider decision map covers naming, overview, switches and positioning changes.

# Appendix D | Choosing the product-book reading style

Founder-requested independent analysis | 13 October 2026 | checked at 15:02 IST

**Status: research and recommendation, not founder approval.** This addendum assesses the chapter/house-style choices in the founder's Scrum 2 interview. It does not reopen the settled assistant shape, alter the product specification, or authorise another product writer. Claude Code remains the delivery Lead. ## D1. The recommendation and its limits

**Keep the current layered approach, with a small, explicit refinement pass before freezing the template.** The business reader gets purpose, people, a realistic journey, decisions, failures and results. The builder gets authoritative requirements, acceptance criteria and exact source/version context through links and the existing detailed section. Use the existing Markdown sources and generated HTML reader.

This is the strongest balance among the alternatives examined for this project's combined purposes. It is not established as the best design on every dimension: an investor-only summary can be faster to skim; a reference-only specification can be faster for a developer looking up a clause. Research supports principles, not a universal winning layout. No comparative human study of these Expat Ready editions has run.

The four refinements are: (1) make the source controls understandable and every supported reference resolvable, including abbreviated IDs and business-rule references; (2) preserve keyboard focus when a source drawer closes; (3) bring the business opening forward and make the tables comfortable in the actual pane; (4) treat the chapter skeleton as a preservation checklist whose presentation can suit the subject, rather than forcing irrelevant sections into every chapter. These are recommendations for the Lead's existing work, not new deliverables, process stages or product controls.

## D2. What the chosen format must accomplish

The founder's existing instructions define the job more precisely than visual taste alone. A reader without technical training must understand what happens, who decides, what can fail and where supporting detail lives. Full feature scope, conditions, exceptions and acceptance criteria must survive. Editable Markdown and one derived HTML reading package are already agreed (AIW-D122 Q4; AIW-D123 Q5; AIW-D125).

The audiences need different depths, reached from the same authoritative package:

- The founder and investor need the buyer's problem, useful result, responsibility, limits and evidence.
- A consultant needs the normal and failure journeys, what to review and how to recover.
- A technical implementer and tester need exact conditions, integration requirements, current sources and observable checks.
- A returning reviewer needs search, stable destinations, versions, conflicts and evidence status.

A book can connect these needs. It cannot replace a sales deck, operational how-to guide, or complete reference specification with one uniform page shape. Audience adaptation is consistent with [Google's audience guidance](https://developers.google.com/tech-writing/one/audience) and [Diataxis's distinction between explanation, tutorials, how-to guides and reference](https://diataxis.fr/start-here/). Application to this project is our inference, not evidence of measured reader benefit.

## D4. Local findings: strengths and gaps of the actual edition

**Inputs inspected:** [house style](../handbook/00-house-style.md) and [chapter 1](../handbook/01-one-file-evidence-to-result.md), both version 0.2; [concept](../concept.md); AW-01 header 0.12 with change-log 0.13, section 8.1; the prototype trace; AIW-D124 to D130; generated reader/template/data and saved validation outputs. The Lead's 09:19:30 UTC log records one independent review, PASS WITH FIXES, five Material and twenty Minor, all addressed. That is saved review evidence, not a fresh full review by this research session.

**What is working.** The chapter gives people, trigger, a source-linked facts table, a conflict, human correction, exact previews, permission refusal, solo form approval recorded Self-approved, a provider failure/manual route, changed-fact handling and billing limits. It labels proposals and separates document status from behaviour evidence. The detailed build section is folded, and the glossary explains terms. The generated house style and chapter match their current source hashes. The previous rendered inspection successfully opened the AIW-D128 source drawer.

**What the complete analysis found:**

1. **Source access is incomplete.** House style section 4 rule 3 says, exactly, “The reading edition turns every ID into a link that opens the exact words, file and version.” Chapter 1 section 8 uses shortened test references such as “TC-AW1-103, -104, -105”. The browser has no link to TC-AW1-104 on this chapter, though that test exists in the embedded reference index. The business-rule reference “AG-07 BR-24” is also not a reference link and is absent as that exact key in the index. The template's matching pattern covers full AW/test IDs, not these two forms. This is a concrete mismatch between the promise and the edition, independent of visual preference.
2. **Keyboard return needs repair.** In the browser, navigate to Step 6, open AIW-D128, then press Escape on the focused Close button. The drawer closes and the reading position returns to Step 6, but the active element is BODY, rather than the invoking link. Scroll position was preserved in this case; keyboard focus was not. This is a specific interaction finding, not a claim of complete accessibility testing.
3. **The business opening is delayed.** The generated chapter duplicates its title as two top-level headings and presents a substantial status/source paragraph plus an expanded 23-heading contents list before “In one minute”. These can be arranged more economically while keeping evidence status visible. GOV.UK guidance calls for one page-level heading. This is a focused reader repair, not grounds to redesign the whole book.
4. **The mandatory shape is too rigid for all subjects.** House style section 3 says, exactly, “Every chapter has these sections, in this order, with these headings”; a non-applicable section must remain with a one-line explanation. A money chapter, introduction, skill catalogue and file journey have different reading tasks. Preserve all relevant information, but allow the Lead to vary headings/order and omit genuinely inapplicable presentation blocks. Record the mapping in the existing review rather than adding a new catalogue.
5. **Length and speed remain unproven.** A whitespace count found 5,937 words in the full chapter and 4,169 in business sections 1–9, including tables, codes and captions. These are content-volume observations, not reading-time estimates or quality scores. An “In one minute” opening is a summary label; an hour-long complete-book read has not been demonstrated. Brevity should come from reducing repetition and moving build-only codes, not deleting approvals or exceptions.
6. **Source correctness still matters.** The earlier UC-1 row 6a/acceptance/finding contradiction remains in the source specification, while the chapter correctly applies AIW-D128. Source drawers should expose version/conflict status; they cannot settle the contradiction. Its correction remains with the delivery Lead. The existing validators' 411/411 and 125/125 saved passes concern preservation and generation logic, not reader comprehension, full reference coverage or product execution.

The normal/failure story is a good business foundation. Its safeguards, field-review obligations and unresolved team conflict must survive every presentation refinement. Legal points remain **Unconfirmed: no counsel (AIW-D94)**.

## G2. Brutal answers

1. **"Should we be doing tested mapping per form version?" Yes, and it is not our idea: it is the industry standard.** VisaFlo and Visto both maintain field maps per form and portal and both have shipped it (VisaFlo since 2024, with a beta portal autofill; Visto with a form-change monitor). AW-1-147 (a) "tested field mappings for that portal and form version" is the same approach with two additions nobody on the market states: **read-back of every entered value** (d) and **stop on any unexpected page** (e). Those two additions are good engineering, not a moat.
2. **"Is it our moat?" No.** A field map is a maintenance chore every vendor does. The things upstream of the map are where we differ: the fill runs from **verified values** with evidence and conflict handling (AW-1-25 to 33, AG11-D10), while VisaFlo fills from what the client typed into intake and Visto from client tasks. Nobody on the market says "the value entered on the portal was verified against the passport by a person and the conflict between the passport and the job letter was settled first". That is the sentence worth selling.
3. **"Can we simplify it?" Yes, in two places, and one of them needs you.** (a) Mapping must be **data, not code**: a mapping version is released like a skill version (AW-1-148 to 152), so a new form edition is a new mapping row, not an AI change (Appendix E principle). (b) AW-1-147 (c) asks a person to approve a "planned entry" under the form key, **after** the same person already approved the government form with the same values (AG-07 BR-24). If the planned entry is built from the approved form's values through a released mapping version, the second approval is duplication; one approval of the values should carry to every target (PDF and portal) until a value changes (AW-1-130). That is a Proposal to simplify a Lead ruling (M5 after review R10), inside AIW-D113, and it should go to you as one question (G5).
4. **"How are we doing against them?" Honestly: behind on shipping, ahead on paper.** VisaFlo and Visto have working autofill today; nothing of ours has run (Specified only), and the team's backend has no case or form ACTION rows yet (Appendix E3). It wins on coverage speed only.

## G3. The next level: AI-proposed, rule-tested, deterministically run mappings

The way to get pattern B's coverage speed with pattern A's determinism, without changing the AI layer's code (Appendix E):

1. **Form-change watch (rules):** a monitor detects a new IMM form edition or a changed portal page (Visto already markets one). It opens a task for the Platform engineer role; nothing fills until a mapping version exists for the new edition.
2. **Mapping proposed by AI (skill, prepare class):** a model reads the new form or page structure and the product's field catalogue and **proposes** a mapping (field → verified-value key, with confidence). It is a proposal item, never used directly.
3. **Mapping tested by rules (rules only):** the product fills a synthetic test case through the proposed mapping, reads every value back (AW-1-147 (d)) and compares; every field must round-trip; unmapped required fields fail the set. This is the mapping's acceptance set (AW-1-155 applied to mappings).
4. **Released by a second person (AW-1-150 (a)):** the mapping version goes LIVE; the proposal becomes data on the product's registry (a mapping row with its form edition, portal, version and test result).
5. **Run deterministically:** at fill time no model is in the loop; verified values go through the released mapping inside the representative's own session; read-back and stop rules as AW-1-147 (d), (e); Submit, Pay, Sign stay human (f).
6. **Drift handled by the pin check (Appendix E, 16e):** a changed form edition marks the mapping stale; the skill that uses it drops to shadow for that form until a new mapping version is released.

What this buys: new-form coverage in hours instead of weeks (the AI drafts the map, the rules prove it), no model risk at fill time, a mapping you can show a regulator, and no change to the assistant when a form changes. What it costs: one new rules-only skill (mapping test harness), one AI skill (mapping proposer), the form-change monitor (if the team does not already plan one), and the mapping registry on the product side (a change note). Everything else reuses the release contract already written.

### Smallest complete integration contract — Proposal

A **contract** is the product’s maintained description of an operation, its allowed data and its conditions. Reuse five existing responsibilities:

1. Product resolves the person, firm/platform scope, current permissions, delegation, enabled capabilities and the **concrete operation**. A screen action may group several operations; discovery is useful, the server’s final check is authoritative.
2. Product owns request/response validation, rules and contextual approval policy. AI keeps references and its own accepted output/instruction versions, not copied product SQL/schemas/rules. Preserve AI-text, licensed-review and automatic-template exceptions.
3. Product owns the preview, bound facts/versions, required approver, effect, duplicate protection and audit. A lost response is resolved through the product’s recorded outcome before repeating an effect.
4. Existing SkillVersion/release checks record relevant dependencies and distinguish compatible changes, breaking shape/meaning/approval changes and quality failures. Structurally invalid waiting work cannot remain executable merely because a person checks it.
5. Already specified AI records use normal product tenancy, contracts and audit rails. AI-specific record types are needed; a parallel permission/workflow/audit system is not.

Only demonstrated additions: operation-policy binding where the current screen map is too coarse; lendability on the existing permission catalogue; affected-skill/pending-work compatibility checks attached to current release/parity services. Owner: team, specified by Lead; checks are below. No new framework, approval engine or documentation repository is justified.
