It does not amend the authoritative decision register, authorise implementation or claim the founder has submitted an answer in the maker's session. ## Selected direction for the one-pager

Select **Saved maps; test runtime AI**. AI generates reusable mappings for each supported form edition or portal version; people review new or uncertain items, and the existing release controls apply. Case-time filling uses the approved mappings and confirmed facts. No person authors a mapping spreadsheet for every combination or client. Retain the existing first-use exception only after resolving its authority against the later central-operation decision; do not silently give firms engine access.

The same form edition reuses its mapping across combinations. Combination rules select the applicable forms, documents and questions. Genuine differences in meaning, applicability or repeated-person context need explicit reviewed rules or variations, not untracked copies. A mapping must resolve the source person/organisation, relationship, canonical field, relevant time or purpose, target field, format, conditions and repeated-row handling where applicable. Reusing a canonical definition does not merge different people's values.

Compare runtime AI with the reusable route in the planned real-read experiment, using the same independently checked answers. This is a bounded alternative test, not a commitment to two production engines. Include family/relationship ambiguity, omissions, conditions and repeated rows; a successful test on one simple form cannot establish all-format support. Compare complete-form correctness, human review/correction time, remaining errors, maintenance work, cost and latency. Recommend changing the selected route only if the evidence supports it and the founder agrees.

Saved mappings reduce repeated interpretation; they do not prove the original interpretation correct. Keep source-grounded semantic review, independent expected-answer tests, applicable form validation, actual-output readback and human approval. Assess the product AI checker's added value separately from ordinary value-equality checks; do not automatically delete it or claim it guarantees correctness.

## Explanatory examples inside activity details

This is a requirement for the first usable one-pager's documentation, not permission to start a separate product prototype or screenshot project.

- Every activity's contextual inspector must include a concise concrete example or an explicit reason that another example would add no understanding. Reuse one fictional family/case across the journey so the reader can follow the same records and outputs.
- Put an **Example** control inside the current activity's detail card. It expands the example in that same inspector. Do not navigate to another page, open another inspector/modal or make the reader find a distant appendix. Keep the activity and map position identifiable. Opening the inspector must already provide readable detail; examples must not be hover-only.
- Lead with a short **Input → Action → Output → Next owner** explanation. Include **What the reviewer does** where a human action exists. If there is no human action, say so. Use concrete values or states rather than generic claims such as 'AI processes the data'.
- Prefer a small table, comparison, matrix, highlighted field example or short flow when it teaches the concept better than prose. Do not force every concept into the same layout. Use clear labels, accessible controls and restrained styling; decoration must not replace the explanation.
- Show the normal case first, then one meaningful exception where relevant. Preserve required rules and acceptance conditions; an illustrative example is not the full specification.
- Label illustrative labels, values, identifiers and outcomes as examples. Actual government field identifiers must come from the real inventory. Do not invent measured accuracy or duration; show a time estimate only with a clear evidence/estimate label if it is useful.

## Minimum example coverage

| Concept | Example to show in the relevant inspector |
|---|---|
| Canonical fields and values | One date-of-birth definition; separate confirmed values for applicant, spouse and child. |
| Master sections and combinations | Existing section/field reused; a missing definition proposed for review; a small combination-by-section/field applicability matrix. |
| PQR, SQR and staff views | The same fact displayed in applicable views, with collection/visibility differences explained and no duplicate value store. |
| Form field mappings | Destination label and section → source person/relationship → canonical field → format/condition; show applicant versus spouse ambiguity. |
| Mapping review | Source evidence and highlighted target; proposed match; Approve / Correct / Flag actions; distinguish a wrong mapping from a wrong fact. These are proposed interactions, not claims of existing screens. |
| Reuse across combinations | Several combinations referencing the same form-edition mapping; show what actually requires a new mapping or variation. |
| Conditional rules and documents | A small if/then table showing the triggering answer, applicable person, added question/form/document and resulting state. Immigration values remain specialist-confirmed. |
| OCR and confirmation | Document evidence → proposed fact → confirmed fact; show a conflicting or unreadable value and its correction route. |
| Validation and review | Example check result with reason/source, separate review priority and human approval; show why green does not itself mean approved. |
| Handoffs and exceptions | Completed record, receiving owner and readiness condition; show a missing prerequisite and the return/recovery path. |
| Form edition or guide change | What changes, what remains reusable, what is rechecked and which affected approval/output becomes stale. |

## Coverage check for the maker and checker

Track activity/concept → example location → what it demonstrates → relevant exception, or a concise reason for omitting a redundant example. Keep this audit outside the main reading path. Test example access and return behaviour with keyboard, desktop and phone layouts. Confirm that example values and relationships remain consistent across cards. Explanatory examples do not replace real-form proof or the independent review.
