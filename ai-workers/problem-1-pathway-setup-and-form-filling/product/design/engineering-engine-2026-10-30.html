The engineering engine, redesigned

How the AI team builds, checks and merges today, where the time really goes, and the setup I recommend: faster, with every independent check kept and machine-enforced guardrails between parallel teams.

Your question: does the cloud use extra tokens?

No. A cloud session does the same work with the same tokens as a session on your Mac, and the cloud machine itself is free (Anthropic's page: "there's no separate charge for the cloud VM"). Your plan allowance is the fuel tank: running five builders at once burns it five times as fast, wherever they run. Using the allowance up is fine when it buys finished work. What wastes it is rework, reruns and handovers, and the numbers below show that is where most of it goes today. Cutting rework is the cheapest speed you can buy.

Parallel work without stepping on each other

runs in parallel

  • Builders on separate files (each lane owns a list of paths)
  • Designing the next item while the current one is built
  • Reviews, breakers and qa explores
  • GitHub test runs for different pull requests

never in parallel

  • Two writers on the same files
  • Merges (one at a time, each on the latest main)
  • Two Leads
  • Any paid live AI run (your approval, one at a time)

machine-enforced

  • Merging only from the Mac, never from a cloud session
  • File overlap and migration order checked on every pull request
  • No AI key in any cloud machine; a check fails if a live switch is on
  • Changes to shared contracts name the pull requests that depend on them and merge together

Rework: why it happens and how we'll find out

From the records so far, rework comes from four places: the design changes after building starts (Screen 01 was first seen cluttered only after it was coded); review finds gaps the builder could have caught (first scores 5.5–7.5); a shared change in one lane breaks another (PR #98 broke #94 and #96); and timing tests fail on an overloaded Mac. We do not yet know the split, so from now on every fix commit carries one cause tag: design-change, missed-requirement, bug, review-standard, cross-lane, flaky-test or environment. The first weekly report then names the biggest cause and which lane or step produces it. Some rework is healthy: a reviewer raising the bar is the system working. Rework that a check before building could have caught is waste.

Bookkeeping: what it is and what changes

Bookkeeping is the Lead and lanes writing about the work instead of doing it: the state table, the log, lane notes, the progress page, decision rows copied into several files, and trimming files that hit their size limits by moving lines word for word into history. Some of it is essential, because it is how a fresh session and you know where we are. The waste is in copying the same fact into many places and the size-limit trims. The fix: one small file per decision and per log line, the state table generated by a script, notes as pull-request comments, and one records update a day. The facts stay; the copying goes.

Records: lighter, nothing lost

One small file per decision and per log line instead of long files that hit size limits and need word-for-word moves (30 such trims this week). The state table is generated by a script. One records pull request a day, which only runs the fast checks. Lead notes go to lanes as a pull-request comment plus a direct message, so a lane never waits for a merge to read its instructions.

Your three decisions

1. Tests on GitHub's machines, capped at US$50 a month. Recommended: it is the only independent test result that cannot be faked, and it removes the Mac queue. Expected cost US$10–30.
2. The new way of working: one-day slices, acceptance checks first, pre-review, reviewer started by the Lead, platform lane, lighter records. Recommended: it targets the 120–160 hours of rework.
3. Builders move to the cloud at their next handover, once the cloud trial passes; the Lead stays on the Mac and you reach it from your phone. Recommended.

Rollout

  1. Today: the lanes keep building and the current queue keeps merging on the Mac as is; nothing stops for this redesign. Read the cloud trial result.
  2. Platform lane: GitHub-machine tests and guard checks, merge only from the Mac, cloud setup fixes, flake list.
  3. Builders move to the cloud one by one at their next handover, not all at once: each lane finishes and pushes its current step, then its next session starts in the cloud with the new rules. No lane loses work; acceptance checks and pre-review start with each lane's next item.
  4. Records simplified with the tools that check them.
  5. After a week of real numbers: package it as a reusable kit for your other products.
