## 1. Stripe's Node library (`BillingPort` and `ClientPaymentsPort`)
* **Problem (contracts §0.3, §1.1, §2.5):** firms subscribe to us through Stripe Billing (Checkout, customer portal, subscription status by webhook) and clients pay firms through Stripe Connect into the firm's own account. Each needs signed webhooks checked before anything is stored (§0.4), Checkout and portal URLs, and Connect onboarding links. The `fake` adapter covers CI; the real adapter runs in test mode on the Mac only.
* **Options:** (a) `stripe`, Stripe's own library; (b) the REST API by Node's `fetch` with our own form encoding, webhook signature check (HMAC-SHA256 over `timestamp.body`, with a tolerance) and retries; (c) a third-party wrapper (none worth the trust for money).
* **Pick: (a) `stripe` 23.1.0.** Money code: the webhook signature check (`webhooks.constructEvent`), idempotency keys, safe automatic retries (`maxNetworkRetries`) and typed objects come from the vendor and are kept in step with its API. Zero runtime dependencies. One library serves both ports (Billing on our platform account; Connect with the firm's `stripeAccount` per request). (b) means re-writing and owning the signature check and every type: more code in the money path for no gain.
* **Integration cost:** one adapter per port in `api/src/platform/billing/` and `api/src/front-office/payments/`, about 150–250 lines each, behind the port; tests use the `fake` adapter and Stripe's documented test events. **One prerequisite outside the fences:** the signature check needs the request's raw bytes, and `main.ts` parses JSON globally (`app.useBodyParser("json", …)`, line 233) without keeping them. The usual one-line fix is `rawBody: true` in `NestFactory.create`'s options (line 232); it is not in contracts §5's list of hooks, so it needs Lead 37's OK (Question 1). Construct the client with `telemetry: false` (below).
* **Upkeep:** 104 releases in the last 365 days (weekly; most add API fields). Each major version moves the pinned API version (23.0.0, 1 Oct 2026; 22.0.0, 3 Apr 2026: about two majors a year). We pin the exact version and the API version (`2026-10-28.endive`, read from the package's `ApiVersion`), and upgrade in one row about twice a year, reading the changelog.
* **Licence (read at source):** `https://raw.githubusercontent.com/stripe/stripe-node/HEAD/LICENSE`, read 13 Nov 2026: MIT (copyright: the original author and Stripe, Inc.). npm `license` field for 23.1.0: MIT. Stripe's own service terms are a separate agreement the founder accepts when opening the account (P-558 (5)). Unconfirmed: no counsel.
* **Data: where and which country:** Stripe holds the firm's billing contact, billing address and card (cards are typed on Stripe's hosted pages and never reach us); for client payments, the client's card and payment details, in the firm's own Stripe account. Our database keeps only Stripe ids, statuses and amounts (in Canada, with the app). **Country:** Stripe's privacy policy, as quoted in search results, says personal data of Canadian (including Quebec) residents is transferred to data centres in the United States; `stripe.com/en-ca/privacy` was not reachable from this lane, **to confirm on the Mac** with the quote and date. The library also sends request telemetry (latency, feature usage) to Stripe by default (its README, "Telemetry"; option `telemetry`, default `true`): switch it off. Cross-border transfer for client payment data is a privacy-notice point: Unconfirmed: no counsel.
* **Version:** 23.1.0, published 29 Oct 2026 (16 days old on 14 Nov). Requires Node 20 or later.
* **Reconsider when:** Stripe offers Canadian data residency, or counsel requires client payment data to stay in Canada; a major version changes webhook verification; or we drop Stripe for a Canadian processor.

## 2. Cognito token checker (`IdentityPort`): `aws-jwt-verify` vs `jose`
* **Problem (contracts §1.2, row PF-4):** the guard verifies a Cognito **access** token against the pool's public keys and refuses a wrong issuer, a wrong client, an expired token, and an ID token used in place of an access token (PF-4's tests). The local stand-in token (`PLATFORM_IDENTITY=local`) is signed and checked by us.
* **Options:** (a) `aws-jwt-verify`, AWS's verifier for Cognito; (b) `jose`, a general JWT library (6.2.14, 29 Oct 2026, MIT, zero dependencies); (c) Node's own `crypto` with our own JWKS fetching and caching.
* **Pick: (a) `aws-jwt-verify` 5.2.1.** It checks the Cognito-specific claims for us: `tokenUse: "access"` refuses an ID token, and `clientId` matches `client_id` on access tokens (Cognito access tokens carry no `aud`, so a general library's audience check does not apply and we would hand-write that check; its README, "`clientId` (mandatory): verify that the JWT's `aud` (id token) or `client_id` (access token) claim matches"). It caches the pool's keys, can be warmed at start (`hydrate()`), and accepts a test key set (`cacheJwks(jwks)`), which PF-4's tests need. Zero runtime dependencies. Security code we do not write is code we cannot get wrong. `jose` is the fallback if we ever leave Cognito for a general OpenID provider.
* **The local stand-in and the tests need no second library:** the stand-in's token is an HMAC-SHA256 token signed and checked with `node:crypto` (about 30 lines, refused unless `PLATFORM_IDENTITY=local`); the tests sign RS256 tokens with `node:crypto` keys and load the public key with `cacheJwks`.
* **Integration cost:** one verifier object in `api/src/platform/identity/`, about 40 lines with the guard's checks; no change elsewhere.
* **Upkeep:** 2 releases in the last 365 days; maintained in the `awslabs` organisation. Low.
* **Licence (read at source):** `https://raw.githubusercontent.com/awslabs/aws-jwt-verify/HEAD/LICENSE`, read 13 Nov 2026: Apache License, Version 2.0. (`jose`: `https://raw.githubusercontent.com/panva/jose/HEAD/LICENSE.md`, MIT, read the same day.) Unconfirmed: no counsel.
* **Data:** no personal data leaves: the token is verified in-process; the only outbound call fetches the pool's public keys from Cognito's address for the pool's region (ca-central-1 per contracts §0.3; the pool and its users live in Cognito in that region, which the founder opens, P-558 (5)).
* **Version:** 5.2.1, published 5 Jun 2026 (162 days). Node 18 or later.
* **Reconsider when:** we move off Cognito, add another identity provider (then `jose` for that path), or the library goes a year without a release while Cognito changes its tokens.

## 6. Time-zone library
* **Problem (contracts §2.2, row FO-3):** staff hours are local wall-clock times in the staff member's zone (`fo_availability.time zone`); bookings are stored in UTC with the booker's zone; slots must be right in the week of a daylight-saving change (America/Toronto, 1 Nov 2026: no lost or doubled slot). Turning "Monday 09:00 in America/Toronto" into a UTC instant, and back for display in the lead's zone, is the core operation.
* **Options:** (a) `@date-fns/tz` 1.5.0 (`TZDate`, zone-aware dates) with `date-fns` 4.4.0; (b) Luxon 3.7.2 (5 Sep 2025; MIT; zone-aware `DateTime`, no dependencies); (c) Day.js 1.11.23 with its `utc` and `timezone` plugins; (d) the Temporal API through `temporal-polyfill` 1.0.6 (13 Oct 2026, MIT) until Node ships it by default; (e) only `Intl.DateTimeFormat` and our own conversion code.
* **Pick: (a) `@date-fns/tz` + `date-fns`.** It is already required by the date picker (entry 5), so the API and the web share one family and one set of rules; both have zero dependencies; `date-fns` functions work on `TZDate` directly (`addDays`, `startOfDay`, `eachDayOfInterval` in the zone). Luxon (b) is equally good on its own but would be a second date family next to the picker's. Day.js (c) depends on plugins and adds a third style. Temporal (d) is the future standard; the polyfill is younger and would be removed later: reconsider when Node runs it without a flag. Our own code (e) re-implements the hard part (the gap and the doubled hour at a change).
* **Where the zone rules come from:** both (a) and (b) read the IANA zone database through `Intl`, i.e. from Node's ICU on the API (the official Node build carries full ICU) and from the browser on the web. A government changing its zone rules reaches us through a Node update; this is a reason to keep Node current (entry 9).
* **Integration cost:** one `slots.ts` helper in `api/src/front-office/booking/`; FO-3's tests cover the 1 Nov 2026 change.
* **Upkeep:** `date-fns` 5 releases and `@date-fns/tz` 1 release in the last 365 days. Low.
* **Licence (read at source), 13 Nov 2026:** `@date-fns/tz`: `https://raw.githubusercontent.com/date-fns/tz/HEAD/LICENSE.md`, MIT (copyright: its author); `date-fns`: `LICENSE.md` inside the published package `https://registry.npmjs.org/date-fns/-/date-fns-4.4.0.tgz` (the repository's root path did not answer), MIT (copyright: its authors). (Luxon: `https://raw.githubusercontent.com/moment/luxon/HEAD/LICENSE.md`, MIT-style text, read the same day.) Unconfirmed: no counsel.
* **Data:** none.
* **Version:** `@date-fns/tz` 1.5.0, published 21 May 2026 (177 days); `date-fns` 4.4.0, published 29 May 2026 (169 days).
* **Reconsider when:** Node's default build enables Temporal (then move to the built-in and drop both), or a zone bug appears that `TZDate` cannot express.

* **Upkeep:** ours; changes only if mail clients change how they read invites.

## 8. Infrastructure as code for the Canadian cloud (row PF-8)

## 10. Background jobs on our PostgreSQL: `pg-boss` (`JobPort`, row PF-14)

* **Options:** (a) `pg-boss` 12.38.0, a job queue in PostgreSQL (`SKIP LOCKED`), in its own schema; (b) BullMQ 6.5.3 (31 Oct 2026; MIT), "Queue for messages and jobs based on Redis" (its npm description): a second data store to run, back up and secure in Canada; (c) `graphile-worker` 0.18.0 (8 Sep 2026; MIT), also on PostgreSQL, but still a 0.x version, needs Node 22.18+, and brings `yargs`, `cosmiconfig`, `json5` and a beta `graphile-config`; (d) our own table and polling loop (we would write locking, retries, schedules and cron ourselves).
