# Best in class after the build: C6.9 case check, row A4 (eligibility rules on the combination), 7 Nov 2026

Read-only study under the founder's 7 Nov bar (market research, competitors, open-source projects, published practice), method of `screen-concept` step 4b. The screen studied is A4 as approved on PR #1172 (`concept.md`, `build-notes.md`, `challenge.md`, `review.md` and four walk screenshots, read from git ref `pr1172`), plus the case page it feeds (`screens/C6.9/concept.md`, `engine/runtime/eligibility.ts`, `web/src/runtime/eligibility.tsx`). Web sources were read on 7 Nov 2026 from their own pages. Where a page refused a direct read, the claim rests on a search-engine extract and is marked so. No app run, no AI call, US$0.

## Summary
1. A4 already matches or beats every product checked on three things: draft, sign-off and release of rules, with each case pinned to its release; a true "can't tell yet" state that never turns a missing answer into a refusal; and rules shown in plain words ("Met when: Passport number is answered …").
2. No immigration product checked (Docketwise, INSZoom, eImmigration, LawLogix, Clio with Gavel, Visto, Migrawise) publishes a way for staff to write eligibility rules. Their public pages show checklists, questionnaire show/hide logic or fixed calculators. Our lead here rests partly on what their pages leave out.
3. The best rule tools outside immigration (DMN test scenarios, OpenFisca tests, Blawx, Stripe Radar, Alloy) all let the author **try a rule on example people before it goes live**. A4 lists this as Not built. It is the largest gap, and the engine A4 feeds is pure and free (US$0), so it can be closed.
4. A4 checks every gate against every travelling person, but has no "who must meet it" setting, although documents and checks in the same app already have one. OpenFisca's roles and household screeners treat people by role. Without it, a principal-only rule would wrongly fail a spouse or a child.
5. Best 3 improvements: (1) try the rules on sample families in the dialog, and save a try as a test; (2) "who must meet this gate" by role and age, with a "Does not apply" state; (3) an official source (link, IRCC's words, date) on each gate, as forms already carry.

## How A4 compares, pattern by pattern

| Pattern | What A4 does today | Where the best do better |
|---|---|---|
| Rules over many people on one case | Each gate is checked for each travelling person ("Checked for each person"); the case page runs per person | OpenFisca models roles inside a household [6]; Visto scopes rules by age and family member [30]. A4 gates have no "applies to", though documents (`appliesToRoles`) and checks (`appliesTo`) in the same app do (`engine/import.ts:86,123`) |
| "Can't tell yet" when facts are missing | Met / Not met / Not answered per gate; a missing answer never gives Not eligible; a failed gate still wins over a missing one (P-229 (3)); "the representative reviews it" option. **At or above the best:** json-rules-engine throws on a missing fact by default [19]; Direct File needed a written decision record to handle it [2] | Direct File separates "placeholder" from "complete" [2]; Migrawise flags verified versus unverified values [29]. A4 counts an unconfirmed answer as answered and marks it "not confirmed yet" on the case page only |
| Showing which fact decides | Case page: each gate lists its facts and values, "(not confirmed yet)", and the missing facts with a link to answer them | Camunda highlights the matched rule on the table [11]; OpenFisca and PolicyEngine trace dependencies [9][38]. The author never sees this until a real case runs |
| Test cases before release | Answer-key tests can expect gate results, and the remove-confirm warns that they fail; "trying a gate on a sample person" and "N tests expect this gate" are Not built (concept §7) | KIE test scenarios run before deploy [13]; OpenFisca YAML tests with several people [5]; Blawx scenario explorer [21]; Stripe tests a rule on past payments before adding it [25] |
| Versioning against a released configuration | Released / New / Changed / Removed in draft per gate; content reviewer signs, approver releases; each case keeps the release it opened on. **At or above the best:** Camunda versions decisions but does not require a second signer [12]; no immigration product describes it (V4) | Alloy and Stripe show the impact of the new version on past cases before go-live [25][26] |
| Plain-language rule display | "Met when: Passport number is answered and Passport expiry date is answered · If not met: Not eligible"; key only under Details; Officer's judgement lines; disclaimer. **At par with** react-querybuilder's `natural_language` export [16] | Leaks remain on A4's edges: Review's Eligibility line shows a field key ("person.intended_job_title is answered", build notes "Seen, not this row"); the builder shows `yes_no` at 200 % zoom; "Edit as JSON" sits on the main path. The combining rule (how gates make one outcome) is not shown, while DMN puts the hit policy on the table [10] |

## Improvements (best first, at most 8)

| # | Pattern | Improvement | What the best do (source) | Size | When |
|---|---|---|---|---|---|
| 1 | Test cases before release | **Try the rules on sample families inside the dialog, before Save.** A "Try on" panel picks a saved Sample family (for example "Couple, one child") and shows, for each person, each gate as Met / Not met / Not answered with the facts it read, and the outcome, from the unsaved rules. Runs the existing pure `assess` (US$0). A "Keep as a test" button saves the try as an answer-key expectation; the content reviewer sees the results when signing | KIE test scenarios before deploy, and quick tests kept only when saved as a scenario [13][14]; OpenFisca multi-person YAML tests [5]; Blawx scenario explorer [21]; Stripe tests before adding a rule [25] | Medium | Fits M3 |
| 2 | Many people on one case | **"Who must meet this gate":** every travelling person (today's default), the principal applicant only, a spouse or partner, dependent children, or an age band. People outside it read **Does not apply**, never Not met. Same role list as documents and checks; stored on the gate only when set, so older releases keep their fingerprints. Example to confirm with the immigration expert: a rule that only the principal applicant must meet (Unconfirmed: no counsel). Whether a role fact can already be used in a gate's condition as a workaround is Unverified; even if it can, it would show Met or Not met, not "Does not apply" | OpenFisca roles inside group entities [6]; Visto rules by age and family member [30]; ACCESS NYC household screening [22] | Medium | After M3 (fits M3 only if the founder pulls it forward) |
| 3 | Plain language, trust | **An official source on each gate:** link, IRCC's words and the date read, shown under the gate on the section and on the case page; "(Sample)" stays until a source is given; the release check warns on a gate with no source. Same pattern forms already use ("IRCC's words"), and AGENTS rule 4 / P-170. Any gate wording remains Unconfirmed: no counsel | OpenFisca `reference` on each variable [7]; Catala code beside the law text [20] | Medium | Fits M3 |
| 4 | "Can't tell yet" and which fact decides | **Say how the outcome is worked out and what each gate waits for.** One line on the section and in the dialog: "A gate not met gives Doesn't qualify; a fact not answered gives Can't tell; a gate the representative reviews gives Can't tell, never Doesn't qualify." Under each gate: "Can't tell until: Passport number, Passport expiry date" | DMN shows the hit policy on each table [10]; GOV.UK: explain why and what to do instead [37]; Direct File links the result to the question that caused it [3] | Small | Fits M3 |
| 5 | Test cases before release | **Show "N tests expect this gate" and their last result** on each gate and in the remove-confirm; run the answer-key tests on the draft at Save, not only at submit and release, and show a failure under the gate it concerns | OpenFisca `openfisca test` [5]; KIE coverage reports [13]; Alloy batch re-run of a new version [27] | Small | Fits M3 |
| 6 | Plain-language display | **Plain words wherever the rule appears:** the content reviewer's Review line uses question labels, not field keys; the builder stops showing type codes (`yes_no`) at 200 %; "Edit as JSON" moves under Details | react-querybuilder `natural_language` export with labels [16]; lock released rules [17] | Small | Fits M3 |
| 7 | "Can't tell yet" | **Make confirmed versus unconfirmed visible in the outcome.** The capability is named "case check from confirmed facts", yet C6.9 BR-9 counts an unconfirmed answer as answered. Show "Qualifies, on facts not yet confirmed" (and the same for Doesn't qualify) until every deciding fact is confirmed. Whether a gate may require confirmed facts only is a founder decision | Direct File: placeholder versus complete facts [2]; Migrawise: verified, unverified and needs-review flags [29] | Small (wording); Medium (per-gate setting) | Fits M3 (wording); after M3 (setting) |
| 8 | Versioning, test before release | **Impact preview at sign-off:** run the draft gates and the released gates side by side over the Sample families and, read-only for staff, over the facts of open cases; show "3 people would move from Qualifies to Can't tell" with the list. Cases keep their release, so this is a forecast for new cases, said as such | Stripe Radar past-payment summary [25]; Alloy control versus test, What If, shadow testing [26][27]; Unit21 shadow mode [28] | Large | After M3 |

Not proposed: reordering gates, drag and drop and nested groups (A4 recorded them as not needed for the proof; no source showed users need them for eligibility), and a shared gate library across combinations (no source in this pass showed it).
