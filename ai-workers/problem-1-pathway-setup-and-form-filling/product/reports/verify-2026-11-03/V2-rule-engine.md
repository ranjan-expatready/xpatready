Independent read-only verification (P-290, P-291 (1)), 3 Nov 2026. Main at `3b0d4d64`. Live AI off, US$0; no `STUDIO_*_LIVE` set. The verifier built and scored none of this. **Status: final.**

## Summary in plain words

* **458 rules** are in the table: every BR-n in the 30 concept folders that define rules (the agreed concept, or the draft where no agreed concept exists), the BR-n rule sets that tests name by capability (C2.4, C3.15, C5.3, C6.11, C6.12, C7.6, C9.1, C11.5, C11.9, C11.10), and every founder decision P-01 … P-293 that sets a product rule (what the app must allow, refuse, derive, show or require; process decisions left out). Some rules appear twice where a decision and a concept state the same rule, so the decision rows can be read on their own.
* **Built and proved by a passing and a failing test: 282** of 458. Proved only one way: 24 (passing case only) and 8 (refusal only). The test is weaker than the rule: 58. No test: 18. Not built: 65 (most of these by decision: the browser extension and portal capture are parked by P-102, and M3's Ready to file, filing record and review are not built yet).
* **Result on main:** 379 rules pass (6 of them only by their own labels while another check in the same cited suite or pack is red: listed under “Rules failing on main”), 0 fail, 65 not built, 13 have no test, 1 could not be matched to a run (mostly browser-only checks or labels the readers could not quote exactly; see the Result column). An earlier run on 877acf66 (stopped at the 2-hour limit after 256 suites, no summary table) agreed: every finished suite passed except the same `check_forms_c34_ai.ts` and one browser check cut off by the stop. A rule counts as **pass** only when the named test's own labels were found as PASS lines in the run log, or (marked) when its whole suite passed but the label was not quoted exactly.
* **Contradictions: 16 live** (two rules in force that the code cannot both satisfy: the most serious are 4-step vs 5-step setup progress, P-227's Live-or-Saved against the Rules-only mode still offered, and answer keys per edition against one key per item), **6 held** (the founder changed the rule on 2 Nov, P-235 … P-248, but those changes wait for the SA-01B product owner under P-251, so the code correctly keeps the old rule while DECISIONS.md reads as if the new one is in force: Ready to file blocks, Declared answers, eligibility words, release without a form line, guarded Add), and **19 stale records** (a concept or decision text that a later decision overtook; four of them still have tests proving the old rule).
* **Rule engine core holds together.** The release refusals (no source entry, no passing signed answer key) both hold on the demo's Visitor visa release; eligibility gates, filing modes, filings and fees, the lifecycle (delete, retire, restore) and the guarded change tiers each have a passing and a failing test and are green. The weak spots are at the edges: wording and step counts that drifted between screens, API doors the screen no longer uses, and M3's Ready to file, which follows a rule the founder has since changed (held).
* **Testing gaps that matter:** six runtime suites (case team, employer link, filings, generate, words) are never run by `run-suites.sh` or CI; the verifier ran them here and all six pass (164 checks). `tests/qa/*` is not run either. `check_screen01_api.ts`, the only home of the intake identity tests, is quarantined from PR checks. One full run of the suites rewrote **668 committed files** (screenshots under `product/screens/*/`, saved stub runs under `prototype/p2/runs/stub-pass/`, the canary digest, an evidence file) and added two untracked run files, so every local run leaves a dirty copy that a careless commit would push. One suite fails on main: `check_forms_c34_ai.ts` (C3.4, scored Partial) loses its server connection at the Saved masters replay, on two fresh copies and when run alone; no rule in the table rests on it.

## Method

1. **Rules listed** by nine read-only readers (Sonnet, as this task's brief asked; P-303's “Opus for any judging subagent” came after they ran, so their proof grades are Sonnet's reading), each on a slice (A–H2 below), from the concept files under `product/screens/*/` and from `product/DECISIONS.md` with `product/decisions/*`. For each rule the reader named the enforcing line, the test file and the exact label of the passing and failing case, and graded the proof. The verifier spot-checked the most serious findings in the code (marked "Checked" under Contradictions) and refuted one.
2. **Suites run** on a fresh clone of `origin/main` at `3b0d4d64` (main when the tech lead asked for the M2 re-test, after SH3 #659 and the first fixes), set up with `product/tools/cloud-setup.sh`: `bash product/tools/run-suites.sh` (every suite, engine, API and browser; no `--demo`), exit 1. The runner has no port option, so its own copies use the ports in each suite's usage line; the verifier's extra runs used 4470–4478.
3. **Extra runs** the runner skips: the six `tests/runtime/check_*` suites it never calls (on 877acf66; none of their files changed by 3b0d4d64 except through shared code), every M2 acceptance pack on 3b0d4d64 (36 packs, port 4470; see `retest-M2.md`), and the M3 packs of pack 4 on 877acf66 (`acceptance/lib/run_pack4.sh 4478`). Acceptance packs are red on purpose until built (`acceptance/README.md`), so a red pack means "not yet built" or "defect", read case by case.
4. **Result per rule**: the named labels looked up as PASS/FAIL lines in that run's log (`gen_report.py` in the verifier's scratch copy; method, not product code).
