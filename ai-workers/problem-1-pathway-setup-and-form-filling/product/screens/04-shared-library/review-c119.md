## Majors (fix before Approve)
1. **A retired field still takes a new use through Screen 02's field map (BR-10; round-1 fix order: "Refuse retired items on every write route").** `api/src/sources.ts:701-707` (decision CHANGED) accepts any key that exists, including a retired one. `apply` (`sources.ts:806`) then writes the form-field maps. The Library field key input on the job page (`web/src/pages/job.tsx:164`) is free text. *Failing scenario:* retire `person.probe_ret` (approved, RETIRED). Run a replay draft of IMM 5257 for the Visitor visa, `POST /jobs/:id/items/:item {decision:"CHANGED", key:"person.probe_ret"}` → 201, then apply → 201. Result: 2 form fields on IMM 5257 (09-2023) map to the retired field, and `GET …/person.probe_ret/uses` lists "Visitors › Visitor visa: blocks". *Fix:* call `refuseRetired(db, ws, "field", [key])` in the CHANGED branch, and again for every `decidedKey` inside `apply`'s transaction. Add a fail test.
2. **A merged field can be retired, and a later restore publishes its merged row (challenge M4: "Merged fields are never 'Retired'").** `stateOf` (`api/src/library-items.ts:31`) treats an item as retired only when no version is PUBLISHED or DRAFT. A merge of a published field leaves v1 PUBLISHED and adds v2 RETIRED with `merged_into_key` (`forms.ts:330`). Retire then picks v1 and restore picks v2 (`library-items.ts:146-147`). *Failing scenario:* merge `person.mg_gone` into `person.mg_keep` (approved). `…/uses` answers `retired:false, can.retire:null`, and the default list shows the row with Retire. Retire and approve, then restore and approve: v1 RETIRED, **v2 PUBLISHED with merged_into_key = person.mg_keep**. *Fix:* read the newest version, as `current()` does. Refuse all three actions on a merged field with a sentence that names the field it was merged into, and leave merged fields out of the Retired list.

## Minors (should fix; none blocks on its own)
1. A failed Undo still says nothing a person can read. `components/lifecycle/index.tsx:128` calls `clear()` in `finally` after `undo()` resolves, which wipes the "Not undone: …" toast that `library-item-actions.tsx:48` showed. Observed: the toast showed for one render, then nothing. Show the message after `run` finishes, or skip `clear()` when the undo replaced the toast.
2. The Restore confirm contradicts itself: "It comes back to pickers and AI suggestions **with the next release**" next to "Takes effect: **When it is approved**" (`contracts/lifecycle.ts:78`, used by `library-item-actions.tsx:87`). Pass the item wording, as the tip does.
3. On the field page, a retired field reads "v1 **Removed in draft**" (`configuration.tsx:28` through `library.tsx:99`). It still offers Rename, Save as draft and Save placement as draft, and each one answers 409 (`library.tsx:86-91`). Show Retired and make those controls read-only, with the reason.
4. On Document types, a new type whose ADD is waiting offers **Delete**, and a click is always refused with "A change to it is waiting". `openItemChanges` adds ADD for fields only (`library-items.ts:161`). Show the waiting state with no action, or route the action to To review.
5. The "Add an alternative" picker offers retired document types (`configuration.tsx:99` has no `!t.retired` filter, unlike the type picker on line 89). BR-10 says pickers hide them. The server refuses with 409 at Save.
6. A condition that reads a retired field is refused as "reads person.c119_released, which is not in the library" (`engine/validate.ts:38`). That shows a system key and says the wrong thing (EXPERIENCE §3). Say it is retired, and use its name.
7. A use that comes from `fact_source` or an alternative reads "Its document checklist lists it: remove the line there first" and links to `/c/:id/documents` (`library-items.ts:66`). For a fact source the line is not there: it lives on the Sources tab. No test covers the `fact_source` use (STANDARDS §6 [M]).
8. A check-then-write window is still open. `refuseRetired` (`studio.ts:630`, `:495`) reads before it inserts, with no lock. `applyItem`'s re-check (`library-items.ts:136`) runs under READ COMMITTED without locking the item, so a line committed at the same moment is not seen. I did not reproduce it in 15 parallel rounds of approve plus add-a-line, but nothing in the code serialises the two (`break-report-c119.md` reports it 2 times in 12). Lock the item row (`SELECT … FOR UPDATE` in `applyItem`, `FOR SHARE` before the insert), or recheck after the insert.
9. Its test does not prove the M2 guard. With `status: "APPROVED"` removed from `applyItem`'s guarded write (`library-items.ts:133`), `check_c119_library_items.ts:150-155` still passed: the withdraw always lands before the approval's claim, so the approval fails in `decideChange`. STANDARDS §6 [M] ("a rule's test fails when the rule is removed") is not met for M2. Force the order, for example withdraw while the change is APPROVED via a test-only hold, or call `applyItem` on a withdrawn change directly.
