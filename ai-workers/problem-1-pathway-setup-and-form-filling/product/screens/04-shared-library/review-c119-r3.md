## Majors (fix before Approve)
1. **A retired section can still end up chosen by a current combination (BR-10; the same race as break round-2 Ma2, now for sections).** `api/src/studio.ts:542` checks `refuseRetired` on `this.db` with no lock, and the selection is written at `:552`, also outside a transaction. `applyItem` takes the section's lock (`library-items.ts:169`), but nothing on the selection side takes it. *Failing scenario:* I planted a published section, proposed Retire as user-A, then sent `POST /library/changes/:id/approve` (user-B) and `POST /combinations/:id/sections/:key` (user-A) at once, with the select 0–60 ms later. **10 of 40 rounds** ended RELEASED with the section RETIRED and still selected. `GET /library/sections/rev4_race_525622/uses` → `retired:true` and lists "Family sponsorship › … Applicant outside Canada: blocks". `placeField`'s section check (`studio.ts:501`) has the same gap: it locks only the field. *Fix:* in one transaction, `lockItem(tx, ws, "section", [key])`, then `refuseRetired(tx, …)`, then the upsert, for both routes. Add a staggered race test that fails when the lock is removed.
2. **Undo of an own-draft delete puts its draft question back into a retired or deleted section (BR-10, data integrity).** `undoOwnItem` re-creates the stored questions with no check (`api/src/library-items.ts:256`). *Failing scenario A:* own draft field `person.rev4_b` placed in published section `rev4_pub`. Delete it at once (its question goes with it), then retire `rev4_pub` and approve. Undo → `section_question` rev4_pub DRAFT for the field. The placement route refuses the same write with 409 "The section … is retired". *Failing scenario B:* own draft field placed in own draft section `rev4_sec`. Delete the field at once, which frees the section, then delete the section at once. Undo the field → its question points at `rev4_sec`, which no longer exists, and `GET /library/fields` still shows placement `rev4_sec`. *Fix:* under the section's lock, refuse the Undo in words, or bring the field back without its question and say so, when a stored question's section is retired or gone. Add a fail test.
3. **The filing order of forms has no screen (P-33; P-116 "reorder where order matters").** `POST /combinations/:id/forms/reorder` (`api/src/library-items-routes.ts:34`) and `combination.form_order` work, but nothing in `web/src` calls the route or shows the order. `qa/built/C11.9.md` says "On a combination, the author sets the filing order of its forms". *Failing scenario:* as the author, open a combination's Forms tab (`/c/:id/forms`). There is no Move, Reorder or filing-order control, and no order shown. The only way to set it is a script. *Fix:* put the order on the combination's Forms tab (Move up/down with the shared pattern, as Questionnaire sections do), or take the claim out of the built record and capability row and record it as a question to the tech lead. The pack proved only the API.
4. **"Delete" of a never-released document type or section cannot be reached in the product, so the own-draft delete with Undo works only on rows planted by SQL (BR-9, P-116 amended, P-33).** Every product path that creates one opens an ADD change (`api/src/studio.ts:640-641`, `api/src/proposals.ts:169-170,186-188`). `itemUses` treats any open change as `pending`, which sets `immediate:false` and refuses every action (`library-items.ts:112-114,127`). `withdrawChange` withdraws a field's ADD only (`api/src/library-changes.ts:163`). *Failing scenario:* user-A names "Rev4 New Type" on a checklist line, removes the line, and user-B returns the ADD. Then user-A gets: `…/delete` → 409 "A change to it is waiting for a second person." (it is not waiting: it was returned to user-A), and `…/changes/:id/withdraw` → 409 "Only a new shared field … is withdrawn." It is a dead end. The pack's delete steps pass only because `check_c119_acceptance.ts:30,106` and the browser suite insert the drafts with SQL. *Fix:* count the author's own WAITING or RETURNED ADD as part of their own draft: Delete at once withdraws that ADD in the same transaction, and Undo reopens it. Or extend Withdraw to document-type and section ADDs as for fields. Test it from a draft made through the product.

## Code checks asked for
* **`lockItem`:** a transaction-scoped advisory lock with keys sorted within one kind, and no transaction takes two kinds, so I found no deadlock path: each transaction takes the advisory lock before it locks rows, in the same order. Screen 02's apply takes one lock per mapped key inside the default 5 s transaction. That is fine on the sample data, but a large form edition (hundreds of keys) is worth one timed run.
* **`deleteOwnItem`/`undoOwnItem`:** the rows come back faithfully. A field with aliases `["Alt one","Alt two"]`, a note, label and group, and its draft question (help text and question text), diff identical after Undo, the same ids included; only `updated_at` loses its microseconds. Dropping nulls in `again` is safe, because no nullable column has a default. Someone else's draft goes to WAITING, and user-B's approval removes it. A second Undo → 409. user-B's Undo → 403. Gaps: Majors 2 and 4, Minor 4.
* **Sections:** a selection by a combination stops Retire; placed questions stop Delete, not Retire; releases are listed and kept; restore works. Gap: Major 1.
* **Migration and hash:** `ADD COLUMN form_order JSONB` (nullable) keeps all data and applied cleanly on 4 fresh copies. When it is null, `byFilingOrder` gives `Infinity − Infinity = NaN`, falls to `localeCompare`, and so keeps the old order. No new key enters the snapshot, so existing hashes are unchanged. `comp` is loaded with every scalar (`engine/snapshot.ts:72`).
