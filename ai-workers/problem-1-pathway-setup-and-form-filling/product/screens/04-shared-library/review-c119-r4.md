## Majors (fix before Approve)
1. **The author's own new document type or section still cannot be deleted on its screen (round-3 Ma4 not closed; P-33, BR-9, P-116 amended).** The API now allows it, but the row actions were not changed:
   * *Document types:* `web/src/pages/library-item-actions.tsx:62` greys every row whose change is an ADD with "Its addition waits on To review: decide it there first.", whoever proposed it. *Failing scenario:* as user-A, add a checklist line with new type "Rev5 New Type", remove the line, and have user-B return the ADD. On Shared library › Document types the row says "New: waiting for a second person" and **Delete is disabled** (`aria-disabled=true`), while `GET …/uses` answers `immediate:true, can.delete:null`.
   * *Sections:* `api/src/library-items.ts:212` gives a section with an open ADD the row action WITHDRAW (only document types are excepted). `withdrawChange` refuses any ADD that is not a field's (`api/src/library-changes.ts:163`). *Failing scenario:* own draft section with its own WAITING ADD (as `landSection` makes on To review, `api/src/proposals.ts:169-170`). On Sections, click Withdraw, give a reason, then Withdraw → the panel shows "Only a new shared field that is waiting or returned is withdrawn." It is the same dead end as round 3, and the Delete that the API allows is not offered.
   * *Fix:* when `change.action === "ADD"` and `change.by_id` is the person acting, and the item was never released, give the row DELETE with the own-draft panel (deleted at once, with Undo) for both kinds. Leave it greyed for someone else's ADD. Add browser steps that make the item through the product (the checklist line, To review) and delete it from its row.
2. **Undo of that delete erases the second person's decision on the ADD (data integrity; P-188 "records keep their facts").** `undoOwnItem` resets the stored ADD with `decidedBy: null, decidedAt: null, decisionNote: null` (`api/src/library-items.ts:256`), and `deleteOwnItem` stores only `{id, status}` (`:237`). *Failing scenario:* user-B returns "Rev5 New Type" with "Use the existing type." (row: `RETURNED|user-B|Use the existing type.`). user-A deletes it at once, then Undo → `RETURNED|||`. The change is "returned" with no one who returned it and no reason. The audit line keeps the note, but To review and the change record lose it. *Fix:* store `decidedBy`, `decidedAt` and `decisionNote` with the ADD in `matches.add` and put them back on Undo. Extend the Major-4 test to compare the whole change row before and after.
