## Verdict: **Build after these changes**
The product shape holds: five levels with Pathway type as a stored attribute, one Structure page that adds names through one checked entry point, and a New combination page where names are only picked. Two things must change before BUILD. First, the data option is not yet a working data design: the database and seven places in the code still assume one Pathway per type. Second, renaming and the migration interact with release snapshots in a way the concept does not describe. The rest are fixes to make while building.

## Objections

### Blocker

* What breaks: (a) The existing unique index `program_def_parent_name_key` is on (`workspace_id`, `COALESCE(parent_node_key,'')`, `name_key`), and Pathways have no parent. So "Temporary residence" under Retail and "Temporary residence" under Corporate collide, and Load sample fails on Sample row 6. The concept adds a new index but never changes this one. (b) `studio.ts:60-64` refuses a second PATHWAY with the same `clientType` (409 "pathway already exists"). The following all take *the one* PATHWAY of a type: `programs.ts:379` `pathOptions`, `:403` `createPath`, `:204` and `:183` `catalogue`, and `screen02.ts:134` (the rules path proposal), all via `.find(...)`. (c) `programs.ts:67-73` `ensurePathways` recreates the nodes "Individual" and "Corporate and employers" whenever no PATHWAY of that type exists. Reset deletes every `programDef` (`demo.ts:164`), so after every Reset (P-108) two Pathways named "Individual" and "Corporate and employers" would appear in the Structure. (d) Labels and counts drop the PATHWAY level: `programs.ts:46,117,121`, `review-queue.ts:60` and `engine/snapshot.ts:140` skip it, and `demo.ts:54` / `studio.ts:43` count "programs" as `nodeKind != PATHWAY`. (e) W1-08's BR-15 says Reset keeps "structure below the two Pathway types", which means it still assumes two stored rows (its own "Missing" line asks about this).
* Fix: Make §3 say all of the following. Replace the old index with one keyed on (`workspace_id`, `COALESCE(parent_node_key,'')`, `COALESCE(client_type,'')`, `name_key`), as one migration with its rollback. Delete `PATHWAY_NODES`/`ensurePathways`: Pathway type is the enum `PATHWAYS`, never a row. Remove the 409 in `studio.ts:63`. Make `pathOptions`, `createPath`, `catalogue` and `proposePath` walk *every* PATHWAY of the type. Count "structure exists" as any node. Put PATHWAY labels into the trail. Record in W1-08/W1-11 that after Reset the Structure is empty under both tabs. Add tests: same Pathway name in both tabs is accepted; a second Pathway in one tab is accepted; after Reset there are 0 nodes and a read creates none.

## Builder's addendum (screens lane, 26 Oct, P-20)
Against `main` 4cbb326 and the agreed `concept.md` (with §10b), read in code. It does not repeat B1 and M1–M6 above, which the concept already takes in. Also read: the forms lane's W1-02 branch `claude/forms-park-ext-0266c0` (d575150, at CHECK, not merged), `decisions/P-52-library-lifecycle.md`, `prisma/schema.prisma`, `engine/channels.ts`, `engine/programs.ts`, `api/src/runtime.ts`. Verdict: **Build after these changes.** None of them changes the screens. Points 1–3 change the data and API of slice 1. Point 4 changes one card word. Point 5 changes when slice 1 starts.

**A1 (Major · Needed). Remove, retire, restore and reorder on the Structure and on combinations have nothing to approve them and nothing to publish them.** Confidence high.
* Fact: `ProgramDef` and `Combination` have no status, no `version` and no `retiredAt` (`schema.prisma:101-171`). A node change applies the moment it is saved. Library items are different: they carry DRAFT/PUBLISHED/RETIRED, and their approval goes through `LibraryChange` (`schema.prisma:307`, kinds field · section · document_type · check), which records `proposedBy`, `decidedBy`, `appliedBy` and `releasedIn`. `api/src` has no shared guard service for delete, retire or restore yet. P-52 asks for exactly one ("one guard service for delete, retire and restore, used by every screen"), and WAVE-1 says W1-06, W1-08 and W1-09 reuse it.
* What breaks: §10b says "each is a draft change a different person approves (L4)". With today's data, a structure delete or retire would either apply at once, which breaks L4, or need a new versioned table for the structure.
* Fix (no new table): (a) add `retired_at`, `retired_by` and `version` to `program_def`, and `retired_at` to `combination`, in one migration with its rollback; (b) a structure or combination delete, retire or restore is a `LibraryChange` with kind `structure_node` or `combination`. The node shows "Removal waiting for approval". The author can withdraw the change, which is the Undo. A different person approves it in To review, and only then is it applied. The next pack release lists it in its summary; (c) put the guard in its own file (`api/src/lifecycle.ts`, `usesOf(kind, key)` + `assertRemovable` / `assertRetirable`) so the forms lane imports it for W1-06 rather than editing it.
* **Reorder needs a decision from the Lead.** Display order is not part of the release snapshot (`engine/snapshot.ts:138-141` has no order; `programs.ts:90` sorts by `displayOrder`). A firm never sees a structure reorder through a release, so asking a second person to approve it adds clicks for no protection. Recommended: reorder of structure nodes applies at once (author only) with one audit line. Filing order of forms inside a combination is different: it is release content and keeps the approval and release path. §10b and P-116 now say every action needs a different approver, so this is the Lead's call.

**A2 (Major · Needed). "Same for a combination" in §10b cannot work as written: a Live combination could never be retired, and a retired one would still open cases.** Confidence high.
* Fact: L3 refuses a retire "while the latest release uses it". A Live combination always is its own latest release: a pack keeps the earlier row snapshot of unchanged combinations (`schema.prisma:857`). So every retire of a Live combination would be refused. And if it were allowed, nothing would stop new cases: `runtime.ts:73-74` opens a case on the newest `ConfigRelease` and checks nothing else.
* Fix, by level. **Combination:** its own release does not count as a use. Retire is allowed and carried by the next pack release. The combination then stops being startable (status "Retired", left out of "All", shown under a "Retired" Status option). Open cases keep their pinned release (P-52 L2). It is blocked only while a draft change is waiting on it. **Structure node:** in use when any combination below it is not retired, or any combination below it has open cases (L6: leaf first, then upwards). **Case opening:** add one guard in `runtime.ts` that refuses a case on a retired combination. That file belongs to the runtime lane, which is paused, so the Lead decides whether this lane makes that one-line change, with a test.
* Test: retire a Live combination, then release: it can no longer be opened, and an open case on it still reads its pin. Retire a Program with one non-retired leaf: 409 that lists the leaf.

**A3 (Major · Needed). The four setup-progress steps (Forms · AI draft · Review · Release) cannot be computed from today's data, and "AI draft" never completes when AI is off.** Confidence high.
* Fact: today a row has a status (In setup · Not ready · Live, `engine/programs.ts:81-87`), a `drafted` flag per form that is true when the form's boxes are mapped by any means (AI, reused from the library, or by hand; `programs.ts:150`), and a `ReviewSubmission` with a status. Nothing defines "step 2 done" or "step 3 done". By P-51 a form already in the library comes mapped, and with the paid-run switch off (BR-10, US$0) AI never runs. So step 2 would be "done" with no AI at all, or would never be done, depending on how it is coded.
* Fix: define each step from data that already exists, all calculated with no new columns. **Forms**: at least one form line. **Draft** (relabel "AI draft" to "Draft"; tooltip "Every form's boxes are mapped: by AI, from the library or by hand"): every data form is `drafted`. **Review**: a submission for the current draft is approved and no AI proposals are waiting. **Release**: the combination is in a pack release and nothing has changed since (= Live). The chip shows the release state, and the stepper shows the draft. So a Live combination with a new change shows "Live" plus "1 change waiting", and the stepper sits at Review. Tests: one pass and one fail per step; a demo at US$0 can reach step 4.

**A4 (Major · Needed). "Filed: PDF + answer sheet" (BR-14) has no data behind it, and the answer sheet does not exist.** Confidence high.
* Fact: `engine/channels.ts:43-48` `filingKind` returns "PDF only", "Online only", "Mixed: online and PDF" or "No forms yet". No code or contract anywhere mentions an answer sheet. The W1-02 branch keeps "Online" as a choice per line, with a later-wave warning. The Lead's log already notes that the P-113 answer sheet has no owner.
* What breaks: a card that says "+ answer sheet" promises a document the app cannot produce, which breaks EXPERIENCE's "no claims the app cannot keep".
* Fix (words only, no new data): derive "Filed:" from the line channels. Every line on PDF gives "PDF". Any line on Online gives "PDF + answer sheet (later wave)", with the tooltip saying the answer sheet comes when its own item is built. This changes only `filingKind`'s words, which `programs.ts:167` already sends. Test: a permanent residence Sample with one Online line shows it; a PDF-only combination shows "PDF".

**A5 (Major · Needed, order of work). Slice 1 changes the same files as the forms lane's unmerged W1-02.** Confidence high.
* Fact: W1-02 (d575150, at CHECK) changes `programs.ts`, `demo.ts`, `review-queue.ts`, `screen02.ts`, `engine/snapshot.ts`, `engine/validate.ts` and `contracts/programs.ts`.
