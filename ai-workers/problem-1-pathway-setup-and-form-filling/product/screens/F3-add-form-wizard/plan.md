## 2. What the builder measured in the code
* **To review** (`api/src/review-queue.ts`, screens lane, 194 lines): one service builds every item kind inline from 11 queries (jobs, submissions, captures, online versions, merges, held files, library changes, batches, form-field decisions). No item carries a form; the release item runs `releaseGates` and `unapprovedAdds` per submission. The Programs row and the combination header compute their own "next step" in `engine/programs.ts` `setupActionOf`/`missingItems`, a third copy of the same choice (`studio.ts`, `programs.ts`).
* **Validator** (`engine/validate.ts`, `engine/channels.ts`): `Problem = {level, where, item, message}`; `item` is a form code for form-level problems, a data path or a field key for others: there is no reliable form. **The runtime lane's Screen 03 branch (9dfe9b8, not merged) changes `validate.ts`** (coverage gaps, one problem naming several forms: `g.forms`), so a form tag must be a list and F3a-1 must land after that merge.
* **Second draft**: `ai.ts plan()` skips a source only when its own job is queued or running, or when the same checksum was planned in this same plan (`draftedHere`). A waiting draft of the same file in **another** combination is invisible: the AI plan would draft it again (concept M2, P-38 "analysed once").
* **Screen map** (`form_field_map` rows on the ONLINE edition; `dataPath` = the page's element id, `screenKey` set): decisions `mapped`, `not_a_fact`, `person_answers_on_screen`, `unresolved`; readers that iterate an online version's rows: `engine/snapshot.ts:74` (into the release), `engine/extension/fill.ts:71` (filters by screen key), `engine/channels.ts` (open inputs), `forms.ts` screen-map review and `resolveInput`, `review-queue.ts:135` (PDF only), `studio.ts:502` (draft changes for sign-off). `draftScreenMap` (`engine/twin.ts:83`) returns `pdf_not_on_portal: {caption, fact}` with no heading and is never stored.
* **Captures**: `POST /api/captures` accepts `way: "extension"` and `combinationId` (`contracts/forms.ts:48`), but nothing stops two OPEN extension captures of the same form by the same person; the panel (`extension/src/panel.tsx`) lists the person's OPEN/RETURNED captures without saying where they were started. No coverage endpoint; re-capture tasks are listed only on the Studio route `GET /api/extension/recapture-tasks` (x-actor, review duty).
* **Workspace** (runtime branch `api/src/workspace.ts`, `GET /api/combinations/:id/workspace?tab=`): the Forms tab builds `WorkspaceFormLine` rows; it is the runtime lane's file.
* **Team model** (newest capture, `code/ERv2-sanitized@fb76410`, read-only): `FormFieldMap` is one versioned row per edition with `entries Json`; `PackCompletenessProfile(+Version)` is the team's approved definition of "complete"; no task or work-queue model; the UI has a `Sheet` (`components/ui/sheet.tsx`) and no stepper (§8).

## 3. Decisions in this plan (builder, after the challenge; the Lead agrees or changes them)
* **D1 · "Asked differently online" is a screen-map decision on the online version, no new table** (concept BR-12 [M]; challenge B1, B2, m3, m4, m10).
  * **Grain (B2):** one decision per **PDF section group** = the XFA subform name without its page (`Page2.MaritalStatus.Spouse…` → `MaritalStatus`; IMM 5257 gives about 20 groups, buttons and barcodes excluded because they hold no mapped field). Each group shows a plain **Sample** label from a small per-form table (`contracts/pdf-sections.json`, e.g. `MaritalStatus` → "Marital status and spouse"), confirmed by the immigration expert; never the path on the main path (BR-16). A group with no label shows "Other questions of IMM 5257" and is listed in the build notes for the expert.
  * **Coverage key (B2):** a PDF entry is seen when a captured screen input maps to the same **(shared field, person)**; from the accepted screen map's rows when one exists, from `draftScreenMap`'s proposals during capture. The spouse's family name is not seen because the applicant's is.
  * **Row:** `form_field_map` on the ONLINE edition: `dataPath = "@asked-differently:" + <group key>` (never a page id: an id cannot start with "@"), `outcome = "asked_differently"`, `heading` = the group key, `caption` = its label, `reason` required, `screenKey` and `canonicalFieldKey` null, `origin HUMAN`; versioned and released with the screen map (P-100).
  * **When:** only on a version whose screen map is accepted (409 "Accept the screen map first" otherwise). A re-captured version carries a decision forward **inside `acceptScreenMap`'s transaction**, in the same `createMany`, for a group still not seen; the accept result lists it as carried.
  * **Every reader goes through `isScreenInput(row)`** (`engine/twin.ts`), with one test each: `channels.ts` open inputs and "no screen map yet" (the decision never counts as an input or as a screen map); `forms.ts` `draftScreenMapFor` and `acceptScreenMap` row-count guards (count screen inputs only); `leftoverJob`; `review-queue.ts` "Draft the screen map" (`maps take 1` → screen inputs only); `snapshot.ts` (carried, so a release shows it); `fill.ts`, `render.ts`, `draftOptionMaps` (skip it); `validate.ts diff` gives it its own change line ("PDF section marked asked differently online: Marital status and spouse"); `demo.ts` counts (not a form field); `studio.ts:502` (the decider becomes an author, so author ≠ approver holds). Plus the end-to-end test: a combination with a decision still submits and releases.
  * **Un-deciding (m3):** a DRAFT-only decision is deleted; a PUBLISHED one gets a retired version (`revise` with `status: RETIRED`), which `effective()` drops in both modes; the next change list shows "no longer marked asked differently". Tested.
  * **Duty (m4):** the SME duty, as "You answer this on screen" (a judgement about what the portal asks); `diff` sets `needs_sme: true` so the expert ticks it in Review and release. The Lead may choose the review duty instead (§11).
  * **Retrofit (m10):** in the team's model a typed non-field entry of the online edition's `FormFieldMap.entries` (or edition metadata), never a box a `FormInstance` would read (Unverified). The "JSON list on the edition" alternative would need a new column, so it is a migration and is not proposed.
* **D2 · Forms on queue items and problems are lists** (`forms: string[]`, Lead note on PR #33; m1, m8). Per kind: ai_proposals → job → attachment → edition → form; release → every form line of the combination; capture → `formKey`; screen_map → edition → form (the query adds `form.formKey`); form_fields → edition → form; held_file and new_edition → `code` (null → `[]`); merge and field library_change → every form whose field map reads either key; section and document-type library changes → `[]` (so step 4 counts fields only, K3, and its words say so); running → batch → jobs → attachments → forms. **Golden test (m1):** items with `forms` removed, their order, `counts` and `kinds` identical before and after the extraction on the loaded demo and the F2 setup; under `?form=` the counts and `kinds` count the filtered set and the page says so (BR-5).
* **D3 · Same next step, stated honestly (M1).** **Rail next = To review next** for the same item and the same person: one function (`queueItemsOf`), compared on id, href and label. **The header** (`setupActionOf`, per combination, actor-blind, screens' file) keeps its data source and words (concept M1 option c); the contract test compares it on **kind and target** (job or batch id) with the rail's first open step across the combination's forms, for a person who holds the duty, on a two-job combination with a maker and a reviewer. Its missing "Add the decisions to the draft" step (a decided, unapplied job falls through) goes to the screens lane as a finding, not a silent change.
* **D4 · Second-draft guard by checksum, across combinations (M2).** "Waiting" = the **newest** `field_map` job per attachment, mode not STUB, status QUEUED, RUNNING or COMPLETED with proposals pending or not yet added to its draft (the To review rule, `review-queue.ts:69-72`); an older superseded draft never blocks. The check **ignores `draftAgain`** (the per-form Draft setup button, `launchSource`, sends it) and applies to `draft` and `reuse_saved_output` alike ("analysed once" is about competing proposals, not only cost). **Race:** inside the launch transaction, per target, `pg_advisory_xact_lock(hashtext('draft:' + workspace + sha256))` and a re-check; the loser gets 409 "Being mapped in Visitor visa…" (the pattern of `sources.ts:620`). Words: "Being mapped in Visitor visa: 12 proposals left · a content publisher", a link to that job; applied → "Add from the library · no AI · US$0".
* **D5 · Progress is computed, never stored** (concept §2; m2): `formProgress(facts)` is pure; `QueueFacts` carries the release gates and the unresolved form-field counts **batched** (one query each, never one per edition); the Forms tab's progress loads only the kinds it needs and never computes release gates per view.
* **D6 · One open extension capture per person, form and portal (M3; Q3 answered yes).** Key = workspace, person, form code after `formCode` and the library lookup (`forms.ts:109-114`), portal, `way: extension`, status OPEN **or RETURNED**; one advisory lock per key and a re-check in one transaction; a second start (from the Studio or from the panel) returns the existing capture (200, `reused: true`) and keeps its combination. The panel says "Started in the Studio · Visitor visa" when the capture has a combination.
* **D7 · The release warning (M4):** "PDF sections not seen on any captured screen yet: Marital status and spouse (11)…" is a validator **warning** (never an error) from the snapshot's PDF and online entries and the decisions, tagged with `forms`; shown once in Review and release.
* **D8 · Capture-mode re-capture tasks get their own token route (M5):** `GET /api/extension/capture/recapture-tasks` (capture token); the Studio's `GET /api/extension/recapture-tasks` (x-actor, review duty) is unchanged. The token route returns screen, kind and differences only, never the affected cases (STANDARDS §5).
* **D9 · Names and scaffolding (m5–m7):** the online "screen coverage" (`screenCoverage`, `pdfSectionsNotSeen`) is named apart from the runtime lane's `engine/coverage.ts` (`coverageGaps`, facts nobody is asked for). PDF editions are compared with `compareEditions`, never by label text (`forms.ts:409` today); a new edition that renames a subform shows the group as new, and its old decision is not carried. The screen-map draft file is Scaffolding (labelled in the build notes); a demo reset clears it (checked, `demo.ts:173`).
