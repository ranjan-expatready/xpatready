## Issues (Must = Blocker/Major, Should = Minor)
**M1 (Major, Must): raw action code on the second person's page.** Every B88 change page is titled "SET_FORM_FIELD_QUESTION when a form field is filled: …". This includes the approver's page. Cause: `api/src/library-changes.ts:29` `ACTION_WORD` has no entry for the new action, so `actionWord` returns the code. This breaks EXPERIENCE §5 (no IDs or codes on the main path) and D10. The browser test missed it because its `CODES` (`tests/check_forms_b88_panel_browser.cjs:15`) does not look for upper-case codes. **Fix:** add `SET_FORM_FIELD_QUESTION: "Change"`, or better wording. Add `/\b[A-Z]+(?:_[A-Z]+)+\b/` to `CODES` and check the page's `h1`.

**M2 (Major, Must): WCAG 2.5.3 Label in Name (level A; EXPERIENCE #12 and the WCAG 2.2 AA bar).** `web/src/components/form-field-conditions.tsx:49` shows "Asks the same question", but its accessible name is "Asks the same as “Whether the person has ever used … (IMM 5257 p. 1, Question 2 A)”". The new Undo at `:50` shows "Undo" but is named "Make … worked out from other answers again". A person using speech input cannot say the visible words. axe's `label-content-name-mismatch` flags it (it is an experimental rule, so the test's tag set never runs it). **Fix:** start the name with the visible words ("Asks the same question as “…”", "Undo: make … worked out from other answers again"). Update the test's role-name regexes and add `label-content-name-mismatch` to the B88 axe run. B86's own "Undo" / "Take the condition off …" has the same fault; tell the B86 lane.

**M3 (Major, Must): the closeReplaced fix leaves a false record when the later change does not go through.** Judgement on the B86 fix: it does end the 409. The spread lines for BR-7 Undo and ask-again pass, and the index (`library_change_one_open`: WAITING or APPROVED) explains the bug correctly. The problem is that `closeReplaced` (`api/src/form-field-condition.ts:71`) closes the approved change **at proposal**. On my copy I approved an ask, proposed an Undo, returned it, then withdrew it. The first change, whose draft is still applied and still goes out with the next release, now reads `WITHDRAWN: "Replaced by a later change of this form field."`. Its page chip says **"Released"** (`web/src/pages/review-items.tsx:70` maps every other status to "Released"). `releaseFormFieldCondition` (`:109`) looks only at APPROVED, so it will never mark the change released. This breaks P-188 (records keep their facts) and D2/D6. It hits B86's condition changes through the same door too. **Fix:** keep the id it closed in the new change's `matches.replaces`. When a `form_field_condition` change is returned or withdrawn, put the closed change back to APPROVED if the form field's draft still holds its `after`. RETURNED is outside the index, and a returned form-field change can only be withdrawn (`library-changes.ts:190`), so this is safe. Add a test: ask → approve → Undo → return → withdraw → the first change is APPROVED and the release marks it RELEASED.

**M4 (Major, Must): approval re-checks with no test (STANDARDS §5 [M]: a rule's test fails when the rule is removed; D16).** `applyAsk` refuses "Changed since" when the form field changed (`:96`) and when the question's condition or the deciding field changed (`:101`). BR-3 and BR-7 rely on this. No test reaches it: removing either line leaves every suite green. Concept §6 promised `tests/check_forms_b88_door.ts` for "BR-1 to BR-4, BR-7 pass and fail", and that file is not in the diff. **Fix:** in the spread test, or the promised door test: propose an ask, then get a second person to approve a change to that question's condition (or removal of it), then approve the ask → 409 in words, map unchanged. Likewise, Undo after the form field changed → 409.
