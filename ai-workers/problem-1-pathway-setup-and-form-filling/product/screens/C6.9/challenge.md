Challenger: a fresh agent that did not write `concept.md` (P-223 (4)). 2 Nov 2026, branch `claude/runtime-c69-concept`. Read: `concept.md`; `acceptance/C6.9.test.ts`, `acceptance/lib/m3.ts`, `acceptance/lib/setup_vv_m3.ts` (S5–S8), `acceptance/M3-CONTRACT.md` C6.9, `acceptance/PACK-4-visitor-visa.md` (FQ list); `DECISIONS.md` (P-164, P-141, P-223), `decisions/P-74-P-78.md` (P-77), `STAND-INS.md` (SI-1, SI-2, SI-9), `ASSUMPTIONS.md` C6, C8, C9, `compliance-trace.md` VV-R01, `EXPERIENCE.md`, `STANDARDS.md`, `WAY-OF-WORKING.md`; AG-03 v1.4 §3.3, §3.7–3.9, §7, §9, §10; code `prototype/contracts/rules.ts`, `studio/engine/validate.ts`, `engine/render.ts`, `engine/snapshot.ts`, `engine/runtime/case.ts`, `api/src/runtime.ts`, `api/src/rule-facts.ts`, `api/src/studio.ts`, `prisma/schema.prisma`. canada.ca was not re-opened (same network limit as the concept, §10).

## Verdict: **Ready after fixes**

There is 1 Blocker and there are 4 Majors. All are small text changes to the concept, plus one label change to setup S7 that the tech lead owns. The design holds up: gates as data on the release, judgement lines kept apart from gates, three outcomes and no score, frozen runs with out-of-date worked out when read, and overrides kept beside the result. Most of its code claims check out (see "What is sound").

## Objections

### Blocker

**B1. S7's gate conditions would be refused by the check BR-2 names, so S7, and with it every C6.9 line, cannot go green.** *Needed for the proof.* Confidence: high.
* Evidence: BR-2 refuses "a condition that `checkCondition` rejects". `engine/validate.ts:33-35` `checkCondition` calls `validatePredicate`, and `prototype/contracts/rules.ts:147` pushes "root needs an UPPER_SNAKE subjectKind" when the root has no `subjectKind`. S7's conditions have none (`acceptance/lib/setup_vv_m3.ts:76-77`: `{ op: "and", args: [...] }`, `{ op: "eq", field: "person.criminal_history", value: false }`). S6's conditions in the same file do carry one (`:57`, `subjectKind: "PERSON"`). As designed, the PUT returns 400, S7 fails, and release 2 has no gates. C6.9-2 then gets 409 "no eligibility rules yet", and C6.9-3…15 fail after it.
* Fix: add to BR-2 that a gate condition is stored with a root `subjectKind`. If the PUT gets none, it sets `PERSON` when every field read is `person.*` and `CASE` when every field is `case.*`, and refuses a mix on the field. Only then does it run `checkCondition`. Alternatively, ask the tech lead to add `subjectKind: "PERSON"` to S7. The first fix is better, because the stored rule is then always valid. `engine/render.ts:111` `evalCondition` already strips `subjectKind`, so the adapter works either way. Add a unit test for "no subjectKind given → stored with PERSON".

### Major

**M1. The list route must work without `?person=`, but the contract writes it as if it were required.** *Needed for the proof.* Confidence: high.
* Evidence: §6 lists `GET /runtime/cases/:id/assessments?person=`. C6.9-9 (`C6.9.test.ts:45`), the line that finds `latest` (`:50`) and C6.9-15 (`:58`) call `GET /runtime/cases/${c.id}/assessments` with no query. If a builder makes `person` required (400), three checks fail.
* Fix: in §6, make `person` optional ("omitted: every person on the case, newest first"), and add a list test with no `person`.

**M2. Detecting out of date by answer id gives a false "changed" every time a section is confirmed.** *Needed for the proof (C6.9-9 passes, but the page then misleads).* Confidence: high.
* Evidence: BR-13 says a run is out of date "when any fact it read now has a different answer id". Answers form a chain: every change writes a new `client_canonical_answer` row with `superseded_by_id` (`prisma/schema.prisma:1449-1470`). **Confirm section also writes a new row with the same value** (`api/src/runtime.ts:406`: `create({... valueJson: a.valueJson, status: "VERIFIED", sourceJson: { channel: "confirm_section", ... from: a.id }})`). So confirming a person's answers marks every earlier run out of date, and §5 would say "Out of date: Passport number changed on 2 Nov". That is false, and it pushes the officer into re-runs with a made-up reason. The team's own pattern compares values, not ids (`AnswerSnapshot`, schema `:1476-1486`: "out of date compares it with today's facts").
* Fix: BR-8 `inputs` records `{fact, about, answerId, value}`, with `value: null` for an unanswered fact. BR-13 compares the **canonical value** (`contracts/rules.ts canonical`), so "added, changed or removed" means the value changed. Keep the answer id for tracing. Say in the out-of-date copy which fact changed and from what. Add a test: Confirm section on the facts a run read → `out_of_date` stays false.

**M3. The precedence "a failed gate wins over a missing one" contradicts AG-03 as written, and the concept says AG-03 supports it.** *Needed for the proof (a team-requirement conflict, AGENTS rule 2).* Confidence: high on the text; the right answer is the founder's.
* Evidence: BR-10 says "Any gate Not met gives NOT_ELIGIBLE … Sources: T AG-3-10…13 (with a fail the outcome is Not, even when another gate is missing)". AG-03 says the opposite. AG-3-13: "When **all gate inputs are present** and any gate fails, the outcome SHALL be NOT_ELIGIBLE". §3.3 step 1 lists the missing branch first: "If a gate-deciding input is missing … → POSSIBLY_ELIGIBLE", then "If all gate inputs are present and any gate fails → NOT_ELIGIBLE". P-164 (1) says we *consume* AG-03's shape and never rebuild it. If the stand-in decides differently, the same facts will show a different badge on the day the team's Qualifier is plugged in. The concept's reading is logically defensible (gates are joined by AND, so no missing fact can rescue a failed one). But it is a conflict settled silently.
* Fix: correct the source line in BR-10 so it states the conflict. Put it to the founder as a question. It is worth more than Q3 (see the questions below). Until it is answered, the test does not depend on the case: C6.9-7 answers every fact. Either way, the result always fills both `failedGates` and `missingInputs`, so the page can say "Not eligible: fails Convictions; also needs Passport" or "Possibly eligible: needs Passport; already fails Convictions".

**M4. Both gate labels claim more than their conditions check, and the conviction gate turns a wider background question into a hard "Not eligible".** *Needed for the proof (immigration fit; AGENTS rule 4).* Confidence: high on what the conditions read; the immigration point is Unconfirmed: no counsel.
* Evidence, travel document: "Has a valid travel document" is `and(exists passport_number, exists passport_expiry_date)` (`setup_vv_m3.ts:76`). A passport that expired last year reads **✓ Met · Has a valid travel document**.
* Evidence, convictions: "Has no criminal or immigration-related convictions" is `eq person.criminal_history false` (`:77`). `compliance-trace.md` VV-R01 and ASSUMPTIONS C9 say that fact is "IMM 5257's wider question (committed, arrested, charged or convicted)". So someone arrested and never charged gets "Not eligible — fails: Has no criminal or immigration-related convictions" (§5 copy). That overstates what canada.ca says, which is "have no criminal or immigration-related convictions". It also hides that IRCC can still decide on criminality (for example rehabilitation, or a temporary resident permit). Unconfirmed: no counsel.
* Fix, without breaking any test (the test checks gate keys and outcomes, never labels; C6.9-5 matches on `key` only):
  * the tech lead changes S7's labels to what the rules check, for example "Travel document number and expiry date on file (Sample)" and "Answered no to the background question on crimes, arrests or charges (Sample)";
  * the page shows the expiry date beside a met travel-document gate;
  * the Not eligible copy says "on this application's rules as written; the representative reviews it, and IRCC decides";
  * add the over-reach to the risk column of ASSUMPTIONS C9, so the immigration expert sees it.

  A real expiry check (`days_until` against the end of the stay) would add a fact that C6.9-8 does not answer, so it stays a follow-up for the expert, not this row.

### Minor

1. **BR-9's pre-check is too strict for gates with "or".** Any unanswered fact makes the gate Not answered, so `or(exists passport, exists refugee_travel_document)` with only a passport would read "Possibly eligible" forever. This is not an issue for Visitor visa (no "or" gate). Fix: before calling `evaluate`, rewrite each `exists f` leaf on a missing `f` as a leaf that returns `cannot_tell` (for example `{op:"eq", field:f, value:"__missing__"}`, which `rules.ts:126` turns into `cannot_tell`, with `f` missing), and take `missing` from `evaluate`. The shared `evaluate` stays unchanged, and Kleene logic decides "or" correctly.
2. **BR-5's "never asks" should mean "never asked on a case", not "has no placement".** A case asks only the facts a form box or a rule needs (P-62, `engine/runtime/case.ts` caseView comment). A gate fact that is placed but read by nothing else would never appear in the case view: it stays Not answered, and the "Answer in case view" link leads nowhere. Fix: the release check uses facts that are both placed and read (`validate.ts derivedRead` ∩ placements). Visitor visa is not affected (all three facts fill IMM 5257 boxes).

## What is sound
* **The code claims check out.** `exists` on a missing fact returns `false`: `contracts/rules.ts:105` (comment) and `:121` (`case "exists": return has(n.field)`). Without BR-9's pre-check, an unanswered passport would fail the gate. That is a real false "Not eligible", and leaving the shared `evaluate` alone is right.
* **Rejecting `check_def` and `predicate` rows is justified.** `render.ts:317-322` fires a check when its condition is `true`. `validate.ts:91` checks check conditions as warnings. `rule-facts.ts:49` lists checks as rules a person can name. `render.ts:263-268` evaluates every rule as a show/hide effect. Excluding a new group (as `document_validity` is) would take edits in four or more readers, and each one could invert silently. One nullable `jsonb` column follows the existing precedent (`combination.participants`, `form_order`, schema `:166`, `:169`). **The migrations are needed and small**: the test reads `assessment.result_json` and `assessment_override.assessment_id` by SQL (`C6.9.test.ts:40,54`), so neither table can be avoided. One migration for all three is fine if the tech lead prefers a single read.
* **Snapshot fingerprints stay the same.** `engine/snapshot.ts:177,192` already spreads optional keys and hashes the canonical content, so a key that is "present only when set" leaves other combinations' `sha256` unchanged, and `reach`'s pin check (`runtime.ts:55`) still passes.
* **Firm isolation works as stated.** `reach(…, "officer")` refuses a client with 403 before it looks up the case, and returns 404 for another firm (`runtime.ts:50-53`). That matches C6.9-1.
* **Every other test line is achievable as designed.** First run with no reason → 201. Second and third runs carry reasons. The 400 after the passport change. Override and review on a run that is already out of date: the concept allows both, and the test needs both, because `latest` is out of date by `:46`. 201 with one override row and the outcome unchanged. Review by the case officer gives `reviewedBy === "user-O"`. The `ai_batch` count stays the same. `stand_in: "SI-1"`.
* **The immigration and product logic is right where it matters.** Only facts settle gates. Money, health, ties and leaving are judgement lines that never change the outcome (FQ-5, VV-R01). Zero gates never read "Likely eligible" (409). The stand-in never scores (SI-1, SI-2). The disclaimer is frozen with the release, the default is labelled Sample, and it is marked Unconfirmed: no counsel. No personal names.
* **The part split works.** Part 1 (data and release) and part 2 (API only) each merge alone with nothing visible half-built. Part 3 brings the page. Part 3 could be split into override and review API, then the page, if it grows.
