## Code judgement
* **Atomic.** `submissionGroup.update({recordedFees})` runs inside the record transaction (`submission.ts:140-141`), after the `filing_record` rows and before the audit line, under `FOR NO KEY UPDATE`, the version check and the already-recorded check. My race test (three PATCHes at once) gave `[200, 409, 409]`, 1 snapshot, 2 records and 1 audit line. A 400 (duplicate numbers), a 409 (stale version) and a 403 (client) each left **0** snapshots.
* **Same view: not held (M2 below).** The snapshot is built from the `view` read before the transaction (`submission.ts:76`). The filed facts come from a second `r.state(c)` read (`:113`). Neither is repeated under the lock (`:123`). `versionOf` covers filings and items, not answers, so an answer written in between is not seen.
* **No mixing inside a group.** For a frozen group, every derived line of its current filings is dropped and the snapshot's lines are added (`case-prepare.ts:235-239`). Membership cannot move after recording: split gives 409 (my check, and `refuseIfRecorded`, `case-prepare.ts:479/490`); adding people or changing who is travelling is refused (`refuseIfCaseRecorded`); filing membership does not depend on age (`engine/runtime/filings.ts:183-201`). An unrecorded split group beside a recorded one stays derived, and each group is priced on its own, so a family maximum never spans them.
* **Old rows.** SQL `NULL` and JSON `'null'` both read as today's pricing, with no error (checked live). There is no backfill, and the migration header says so. That is correct: the recorded amounts of an older group cannot be known.
* **Migration** (`20261108000000_b152_recorded_fees`). It adds one nullable `jsonb` column to `submission_group`, which is additive. Main's code runs on this schema because it never reads the column. The rollback (`DROP COLUMN`) is written in the file, and the header warns that it drops the snapshots. Applied on the copy: `recorded_fees | jsonb | YES`. It merges cleanly with main at `3470dc992`, where C3.16's enum migration landed meanwhile on a different object. The date stamp is tomorrow, which only puts it last in order.
* **Version, stale, split, tasks.** The snapshot is not part of `versionOf`, so a write from an older read is not made stale by it (version identical in the null/restore check). The DOB change made two "Filed with an earlier value" `after_filing_change` tasks, as C8.2 intends. Split is refused before and under the lock.
* **The test's "the date moves".** `ageOn(dob, today)` reads only those two values. Moving the DOB 3 days earlier is therefore the same, for every fee and age rule, as today moving 3 days later, and the server has no clock seam. For the fee read it is a faithful stand-in. It does more than a birthday would: it writes an answer and opens after-filing tasks. So it also proves the "corrected date of birth" case. The comment's "a new fee table later changes nothing" holds by construction (amounts and sources sit in the snapshot), but no test covers it (n3).

## Issues (ranked)
1. **Must (Major) M1. A fee still waiting at recording is frozen as waiting for good.** Reproduced: a principal (40) and a child with **no date of birth**. Both filings reach Ready to file with `blocks: [[],[]]`, the record returns **200**, and the snapshot holds 1 `waiting` line with `total_cents` 28500. When the child's DOB is then answered (age 15, so the child pays CAD 85), the recorded group still reads CAD 285 "so far", with "Waits for Sample Child W1's date of birth …". The right amount is CAD 370, and it can never be reached. B152 causes this: before it, answering the DOB priced the group. Cause: `recordedFeesOf` copies waiting lines and a partial total as they are (`submission.ts:62-65`), and `record()` never checks for them. Fix: refuse the record while any fee line of the group waits (a 409 on `filings`, naming the person and "Date of birth"), with a fail-first test. Or block Ready to file on a waiting fee. Never freeze a `waiting` line.
2. **Must (Major) M2. A DOB change at the moment of recording freezes fees that contradict the filed facts.** Reproduced **3 of 3** (0, 0 and 10 ms): the record and the answer both return 200. The frozen biometrics line is CAD 0 ("Under 14"), while the child's `filing_record.filed_facts` holds the moved DOB (14 today). Cause: the fees come from the view read before the transaction (`submission.ts:76`), the filed facts from a later read (`:113`), and neither is checked under the lock (`:123`). Fix: inside the transaction, re-read the answers the fees and facts depend on (or a hash of them, as the version) and refuse with `stale()` when they changed. Or compute the snapshot and the filed facts from one read taken under the lock. Add a race test.
3. **Should (Minor) m1. One `/prepare` response contradicts itself after the date moves.** The frozen line says "Biometrics fee CAD 0 · Under 14: no biometrics" for Sample Child F1. The same response gives `people[].age = 14` and an active **"Give biometrics"** step for that child on the recorded filing (state `cannot_start`). Ages and items are still worked out as at today (`case-prepare.ts:129`, `:151`, `:459`). Main already shows that step; B152 makes it disagree with the fee line. Fix: a follow-up row for recorded filings' age-dependent items. It is not in this row's "fee lines" scope.
4. **Should (Minor) m2. `GET /runtime/cases/:id/filings` still prices as at today.** On the same recorded case it returns CAD 370 against `/prepare`'s CAD 285. Its comment (`case-filings.ts:25-26`) says the two "never price a case differently". The breaker rates this Major. I keep it Minor because no page reads the route (no `web/src` match) and tests call it only on unrecorded cases (`check_vv_prepare_api.ts:123`, `runtime/check_vv_filings_api.ts:21`). It is a one-helper fix: read `recorded_fees` there too. Doing it with M1 and M2 is cheapest.
