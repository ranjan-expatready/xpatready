# Screen 01 — Programs: challenge of the agreed concept

Builder, 21 Oct 2026. Read: concept.md, PRODUCT.md, PATTERNS.md, MASTERS.md, RULES-MODEL.md, TAXONOMY.md, UX-RULES.md, QUALITY.md, STANDARDS.md; SA-01B v1.5 (snapshot 2026-10-19-1233) SA-1B-50..56, 64..74, 90..91 and decisions SA1B-D3..D6, D24, D34; team code `ERv2-sanitized@22f1d12` (ProgramDef, CountryPackDraft/Version, `pack-authoring/internal/pack-graph-structure.ts`) and `ERv2-frontend@5ccd9fa` (`program-hierarchy-page.tsx` and its components); the current reference app (`prototype/studio/prisma/schema.prisma`, `api/src/catalogue.ts`, `api/src/demo.ts`, `evidence/scale-100/`).

## Verdict
**Build after these changes.** The concept is sound in shape (tree table, combination = last level, pathway as workspace, nothing above a combination, calculated status). It has three gaps that would make the build wrong or slow if built as written — the release unit (O1), the status model (O2) and speed at 400 combinations (O3) — and several missing rules for actions it shows (O4–O9). None needs a rethink.

## Objections (ranked)
### Major
**O1. Which thing gets released — the whole pack or one combination — is not stated, and the reference app and the team's code disagree.** What breaks: the draft bar says "Draft 13 · 6 changes" (one draft for everything), while BR-8 says a combination is Ready when *it* is released. The reference app releases **per combination** (`ConfigRelease` keyed by `compositionId`, schema.prisma line 562). The team releases **the whole pack**: one `CountryPackDraft` (DRAFT → IN_REVIEW → APPROVED) becomes an immutable `CountryPackVersion`, and firms pin a pack version (country-pack-core.prisma lines 29–36, 190–202, 274+; MASTERS.md §0). Example: a publisher has finished the visitor visa and is half-way through the super visa. With a pack release, does publishing the visitor visa also publish the half-done super visa? Evidence: SA-1B-90 already answers it in the team's favour: a row is offered to firms "only when its row is published **and** passes its checks". So publishing an unfinished row is harmless — it is published but not startable. Fix: follow the team. One shared draft per country pack; Review and release publishes a pack version; each combination's status reads "is it in the latest published version, and does it pass the startable check". The reference app's per-combination release becomes a per-row snapshot inside the pack version (an adapter, recorded in build-notes). The draft bar counts **everyone's** changes and says so ("6 changes in the shared draft · 2 are yours"). Founder question 1. Confidence: high on the facts; the choice is the founder's.

**O2. The status chips overlap, and some states are missing.** What breaks: a combination can be Ready (released) *and* have AI proposals to review *and* have unsent draft changes. Chips "Ready", "Needs work", "AI proposals to review", "In setup" are filters over things that are not mutually exclusive, so counts don't add up to "All", and a released row with a broken draft could show "Ready" and hide the problem. "In review" (the reference app has it: 22 rows in the scale fixture) and "Disabled" are not drawn at all. Evidence: concept Layout and BR-8; UX rule 8 (one next action per status); PATTERNS §4; scale run T5 ("released badge never hides a draft problem"). Fix: one **status** per row, mutually exclusive, in this order — *In setup* (never published) · *Not startable* (published but fails the startable check; the chip opens the missing list, SA-1B-91) · *Startable* (published and passes; the concept's "Ready") — plus separate **flags** shown beside it: *Draft changes*, *AI proposals (n)*, *In review*, *Check overdue*, *Disabled*. Filter chips = the three statuses + the flags, each count saying what it counts (BR-10). Each status keeps exactly one next action. Use the word **Ready** on screen if the Lead prefers it, but map it to the team's "startable" in build-notes. Confidence: high.

**O3. The speed budget cannot be met by working the status out on every request.** What breaks: the concept says "status computed server-side" with one request. Today that means rebuilding every combination's full configuration per request. Evidence: `evidence/scale-100/fixture-summary.json`: 105 programs / 371 combinations, uncached server time **19.7 s** (13.6 s of it building snapshots); `check_catalogue_scale.json` T1: first display **1,023 ms even when cached** — over the 1 s budget (STANDARDS §8). `catalogue.ts` lines 15–17 records this as a known gap. Fix: keep a stored **row summary** per combination (counts, status, flags, missing items, checked date), updated in the same transaction as every write that touches that combination (and for every affected row when a shared library item or form edition changes). `GET /catalogue` reads summaries only — no snapshot building. Virtualise the tree past a few hundred visible rows (TanStack Virtual, team stack). Tests: first view < 1 s and filter < 200 ms at 100 programs / 400 combinations, fixed query count, summary equals a full recompute (property test). Confidence: high.

**O4. Adding the first sub-category to a set-up category (BR-7) is a data move, and the concept does not define it.** What breaks: the category is a published combination with lines, sources, AI work, checks and audit history. After the move its key is no longer a combination; if anything stays attached, SA-1B-56 blocks publishing. Open cases are pinned to the old pack version that still has the category as a row. Example: "Open work permit" (published, Ready) gets sub-category "Spouse of a skilled worker". The setup moves into it; the second sub-category "Post-graduation" starts empty. Fix: one server command "Split into sub-categories" with a preview listing exactly what moves (lines, sources, AI proposals, checks, freshness dates) and what stays (nothing); runs in one transaction with a version check; records "moved from Open work permit" in the history; offers "copy setup from …" for the next sub-category (SA-1B-61). Old pack versions keep the category row for pinned cases. Tests: everything moves, nothing is left above the combination, a concurrent edit is refused, pinned cases unchanged. Confidence: high.

**O5. Multi-step journeys: "Follows" mixes up two different things in SA-01B, and Express Entry's shape on this screen is undecided.** What breaks: the concept and TAXONOMY §3/case 8 model Express Entry as separate combinations joined by "follows". SA-01B says something different: **a route is pack content per category** — its levels, their order, and the row each level uses (SA-1B-66) — and "Express Entry is **one category** run as two filings" (SA1B-D4). Separately, SA-1B-54 is a looser *suggestion* that categories "usually follow or support" each other. The concept's "↔ Follows …" and "↔ Supported by …" use one link for both. Also P-13 links combinations, SA-1B-54 links categories. Example: is "Express Entry › Profile" a sub-category, a category of its own, or not a row at all? Where do Federal Skilled Worker / Canadian Experience Class go? The sample data has to pick one, and the catalogue shows it. Fix: two separate records — **Route** (on the category, ordered levels, each pointing at a row; binding; drives "Step 1 of 2 · Followed by …") and **Linked categories** (SA-1B-54 suggestion; drives "Supported by …"). On this screen both are read-only labels under the name. The sample shape for Express Entry is founder question 2. Confidence: high on the conflict; medium on the recommended shape (immigration expert confirms).

**O6. Uploading an IRCC form from a catalogue row writes to the shared library without the governed path.** What breaks: BR-12 lets "+ Add" upload a PDF that "creates the form or a new edition of the same code, then attaches". A new edition of a form used by 120 combinations (the scale fixture has 122 rows filing IMM 5409) changes all of them, from a row in a list. P-15 says manual library additions are proposals approved by a different person. And "attach" + "upload" + "AI estimate" appear in three places (row "+ Add", side panel drop zone, dialog step 2). Fix: "+ Add" on a row only **picks** an existing library form (form, not edition — SA-1B-26). Uploading a PDF goes to the library as a proposal: form code and edition date read deterministically from the file; same bytes → "already in the library"; new edition of a used form → impact list ("used by 122 combinations") before it can enter the draft; unrecognised files held, as the app does today. One upload component, reused in the three places. Uploaded files handled per STANDARDS §7 (type and size checked, never rendered as HTML, text treated as data). Founder question 3 decides whether the extra approver step applies to official forms. Confidence: high.

**O7. Name uniqueness (BR-6) is not enforced anywhere today, and "ignoring case and spaces" needs a definition.** Evidence: the team's `ProgramDef` is unique only on `(programNodeKey, version)` (country-pack-questionnaire.prisma lines 168–173); the reference app only on `(workspaceId, programNodeKey)`. Nothing stops two "Open work permit" siblings. Fix: a stored normalised label (trim, collapse spaces, case-fold, ignore punctuation such as "/" vs "or" — no fuzzy matching) with a database unique index on (pack draft, parent, normalised label) among current versions, plus the service check returning a field error. A disabled sibling with the same name → "Re-enable the existing one" rather than a duplicate. Applies to rename too. Mapping to the team's schema recorded (it would be a new constraint for them). Confidence: high.

**O8. Disable, re-enable and reorder are missing from the layout, though the team's page already has them.** Evidence: BR-9 says "disable, never delete" but no Disable action, disabled state or "Show disabled" toggle is drawn. SA-1-13/14 (no removal while children exist; siblings reorder as a set) and the team's `program-hierarchy-page.tsx` (reorder up/down and drag, disable with a reason, lines 107–110) already cover this. Leaving them out takes away capabilities from the team's screen. Fix: row menu "Rename · Reorder · Disable" on program, category and sub-category rows; disable asks for a reason and shows what it affects (combinations under it; open cases keep their release); disabled rows hidden by default with a "Show disabled (n)" toggle; reorder moves the whole sibling set in one save. Confidence: high.

**O9. Moving "composition" to "combination" is the largest piece of back-end work on this screen, and the concept does not scope it.** Evidence: the reference app's `Composition` (schema.prisma line 111) is "a program's combination of people" with a `participants` JSON, nine child tables keyed by `compositionId`, and no rule that one program node has only one. P-10 and SCREENS.md (audit F1) require the combination to be the leaf node, with roles on lines. Fix (recommended staging): on Screen 01, make Combination exactly one-to-one with a leaf program node (database unique on the node; refuse a combination on a non-leaf), rename it everywhere a user or contract sees it, and keep `participants` behind an adapter that shows "who it applies to". Screen 03 turns participants into role lines and retires the adapter. Migration expand → migrate → contract, existing records preserved (STANDARDS §3). Confidence: high on the facts; staging is the Lead's call.

### Minor
**O10. The new-combination dialog is over the click budget.** Pick program, category, sub-category, Next, attach, Next, locations, filing method, portal, roles, Create, then Draft setup — about 12 clicks against D9's 6. Fix: step 3 (locations, filing method, portal, roles) prefilled and optional — AI proposes them from the sources and the workspace edits them later; the last button reads "Create and draft setup (about US$x)", which *is* the Setup status action (P-07), so there is still one AI place.

**O11. The tree table needs its accessibility pattern stated.** Use the WAI-ARIA treegrid pattern (`aria-level`, `aria-expanded`, arrow keys to open and close rows), so the keyboard test has something to pass. The team's tree view has guide lines and depth badges to reuse.

**O12. "Checked" is a single date for a row that has several sources.** Define it as the **oldest** "date checked" among the row's sources (the weakest link), with next review = that date + 12 months, orange when past.

**O13. Counts need a definition.** "164 questions · 18 sections" — for whom? Define as every question any person on the row could be asked, all answers considered; "Documents 18 · 6 always · 12 if" likewise across all people.

**O14. Search and the workspace switch.** A search for "IMM 5409" while in Individual should say "2 more matches in Corporate and employers" rather than show nothing.

**O15. Fees.** SA-1B-52 lists fees on "each category and sub-category"; BR-3/BR-4 put nothing on a category that has sub-categories. Note for Screen 03: fees live on the row. No change to Screen 01.

**O16. Sample data on screen must use plain words.** Current seed descriptions show decision codes and release names ("D229/D257", "c1-v3") on the main path (`demo.ts` lines 47–51) — UX rule 3. Build fix, not a concept change.

## What is sound
* The tree: Pathway › Program › Category › Sub-category with the combination as the last level present matches SA-1B-50/55 exactly; "Not applicable" is the right way to show a category that is itself a combination.
* Pathway as a workspace switch with separate programs per pathway (P-06, P-16) matches the team's data (pathway stays a PATHWAY node).
* BR-4 (nothing above a combination) is the team's own spec (SA-1B-56) and fixes a gap their code has today (SA-01B audit note: `master-publish-validator.ts:164-173`).
* BR-8's Ready test is the team's startable check (SA-1B-90, SA1B-D34) almost word for word.
* BR-15 (pathway = who is the applicant) matches SA1B-D3; the LMIA case and the household-employer label hold.
* The side panel (summary, one primary action, link to full workspace) and the dialog with duplicate check and "will be created as" follow PATTERNS §3.
* Display-label adapter STREAM → Category, CATEGORY → Sub-category without renaming the enum is right for retrofit.
* Every TAXONOMY §4 case maps onto the tree; only case 8/9 (routes) needs O5.

## Questions for the founder (one at a time, recommendation first)
1. **When you release, does it release the whole set of programs or one combination at a time?** *Recommended: the whole set (one shared draft, one release), as the team's system does; unfinished combinations are released but not offered to firms until they pass the check.* Alternative: release each combination on its own (today's prototype; differs from the team, so they would rebuild it).
2. **How should Express Entry appear in Programs?** *Recommended: one category "Express Entry" with two sub-categories, "Profile" and "Permanent residence application", joined as Step 1 → Step 2 of the category's route (SA1B-D4, SA-1B-66); differences between Federal Skilled Worker, Canadian Experience Class and Federal Skilled Trades are conditions until the immigration expert says a stream needs its own sub-category.* Alternative: separate categories joined by a "follows" link (today's TAXONOMY §3).
3. **When someone uploads an official IRCC form, does it need the second-person library approval (P-15) before it can be attached?** *Recommended: no extra step — the form code and edition are read from the file, an identical file is recognised as existing, and a new edition of a form already in use shows every affected combination and is approved at release by a different person.* Alternative: same governor step as hand-added fields and sections.
