## 1. Correctness against the app: Pass

**What the app's Live round builds.** In `pqr-drafts.ts` `draft()` (line 198), Live mode builds:

`ctx = { trail: g.trail, contextKey: c.combinationKey, inputs: inputsOf(g), mode, wanted, batchId: job.id }`

with `g = this.guide(c)`. It then calls `StepRunner.round(PQR_AI, isCheck, ctx)`. In Live mode, `round` writes `roundJob(step, isCheck, ctx)` (rounds.ts lines 149–151). `roundJob` reads only `trail`, `contextKey`, `inputs` and `batchId` from the context (line 100).

**What the tool builds.** `deriveC47V2Jobs()` builds:

`{ trail: g.trail, contextKey: c.combinationKey, inputs: inputsOf(g), batchId: "track-a-v2" }`

* `g` comes from the same `PqrDrafts.guide(c)`.
* `PQR_AI` and `inputsOf` are imported from the app, and `roundJob` is the app's own.
* So every field matches except `batchId`, which is different on purpose.

## Findings

### Blocker

### Major

### Minor
1. **The tool copies `draft()`'s context by hand.** `deriveC47V2Jobs` rebuilds `{trail, contextKey, inputs}` itself. The J check therefore compares the committed files with the tool, not with a job file that a Live round in the app actually wrote. Today the two match line for line (item 1). If `draft()` later passes something else into `roundJob`, J would stay green while the Live round and the job file differ. A cheap guard would be an assertion in the existing fake-launcher suite (`check_forms_c34_ai_live` pattern): capture the job that `round` writes for PQR_AI and compare it with `deriveC47V2Jobs()`, ignoring `job_id`. This is a follow-up, not a reason to hold this PR.
2. **Every paid run of this pair shares one stem.** The job ids are fixed, and `PqrDrafts.savedRounds` (unlike C3.4's `form-masters.ts`, break B1) uses no `replayWindow`. Suppose the pair is recorded more than once and a later run saves its draft but not a usable checker. Saved would then pair the newer draft with an older run's checker. #530's v1 pair has the same exposure. The runner procedure should record exactly one complete pair, or record both rounds again. The result PR's qa Saved check should confirm that both files carry timestamps from the same run.
3. **The simulated pair is briefly visible to other servers on the same tree.** While the check runs, its simulated v2 pair sits in `p2/runs`, stamped 2000. Saved tries the current prompt before v1, so until the real v2 pair exists, any server on the same tree whose Visitor visa has the same question-list checksum would briefly replay the fake pick (`case.funds_available_cad`). It is cleaned up at the end of the check. The pattern is the same as `check_forms_pa_track_a_jobs` (break M2). It is harmless on CI and on lane copies; avoid running it in the main copy while the demo is in use.
4. **For the result PR: where the v2 pair replays.** The recorded v2 pair replays only where Visitor visa's question list has checksum `a4e1504e5594`, which means a copy set up by `setup_visitor_visa.ts` at this commit. After Demo › Reset to the six alone (no questions asked), or after any edit to Visitor visa's questions, Saved falls back to #530's v1 pair. This is the intended QA-162 behaviour. The result PR and qa's Saved check should set the copy up with `setup_visitor_visa.ts` and say so.
5. **Small gaps in the check's assertions.**
   * The R fail case asserts only that the wrong-key pair is not used. It does not assert that the v1 pair is the one used; the run did show v1 in use.
   * The shared-ledger check compares totals, so a concurrent writer on the Mac could make it fail falsely, but never pass falsely.
   * Both are acceptable as written.
