## Majors
**M1. A returned, withdrawn or rejected change leaves its `change_set` at `waiting` forever, and that breaks "Undo rename".** (BR-5; `ChangeSetStatus` declares `returned`/`withdrawn`, nothing sets them: only rename-door.ts:98, :123 and forms.ts:377 update the table.)
Repro: `ren(user-A, person.date_of_birth, "Birth Date 2")`, user-C approves it (applied). Then `ren(user-A, person.date_of_birth, "Birth Date Withdrawn")` → 202, and `POST /api/library/changes/<change_id>/withdraw {"note":"withdrawing it"}` → 201.
SQL: `waiting|WITHDRAWN`. Same for `return`, and for a merge `reject` (`REJECTED|waiting`).
Actual: `GET /api/change-sets/renames/field/person.date_of_birth` returns the withdrawn set (`status:"waiting"`, `after:"Birth Date Withdrawn"`, `before:null`), not the applied one. The field page (screenshot `ui3-1280-1.png`, same at 1024 and zoomed) says `Renaming to "Birth Date Withdrawn" waits for a second person on To review`, which is false, and shows **no Undo button**. `POST /api/change-sets/<that id>/undo-rename` → 409 "Not applied". The real applied rename can only be undone by calling the API with its id. The same stale rows made the rename's "Undo" disappear on the Languages section in the same way. Expected: the withdrawn set ends (`withdrawn`/`returned`) and "Undo rename" targets the newest applied one. rename-door.ts:160-164 (`latest`).

**m2.
