## Majors

**M1. The shared release `POST /api/pack/release` refuses without `errors[]` and names one item per row (max 5 rows).**
- Repro: Visitor visa with a failing key (unsigned or not) plus With an LMIA with problems; as user-B `GET /api/draft` then `POST /api/pack/release {"expectedChanges": <changes>}`.
- Expected (task promise, concept BR-8): 409 whose `errors[]` lists every blocking item, as Submit (400) and Approve (409) do. Actual: 409, body keys `type,title,status,detail,message`, no `errors`; `detail` is "Nothing can be released yet. <row>: <first problem only> · …" for at most 5 rows. A row blocked by two maps names one. `releaseRows` carries `errors[]`, but it is reached only when the page did not already hold the row, so for Tests lines the real route never has them. `tests/check_g2_answer_key_gate.ts` asserts only the status.
- Evidence: `programs.ts:406` (`problem(409, "Every change is held back", …)`; `why` is `r.firstError`). Fix: have `Programs.release` pass each held row's problems (the gate's `GateProblem[]`) into `errors[]` on that 409, and name every Tests item per row in the Release page's held reason; assert `errors[]` in the API check.

**M2. One author click turns a real combination into a Demo release, and the gate's errors into warnings.**
- Repro (demo workspace): With an LMIA (SOURCE_BACKED, real) with a new IMM 5257 map and no key: Tests lines are `error`, `answer_keys.demo=false`. As user-A `POST /api/combinations/<wp>/checks` with a valid condition and **no** `sourceQuote`. Then `answer_keys.demo=true` and both Tests lines are `warning: no answer-key test: allowed only in a Demo release`. (Submit still failed here on 9 unrelated option-map errors of the sample With an LMIA, so I did not complete the release; the gate judgement itself flipped.)
- Expected: BR-10 "no setting, header or actor skips it"; BR-3 says Sample content, not a stray Sample check, makes a Demo release. Actual: `isDemoSnapshot` is true for any `illustrative` check (`engine/validate.ts:263-268`), a check without a quote is illustrative (`studio.ts:779`), no API deletes a check, so the author alone downgrades the whole combination, permanently. The builder knows this (build-notes discovery 6) and accepts it as G3's rule; I rank it Major because the author acts alone and the promise says there is no off switch. Not possible in the `firm` workspace (`demo` stays false: held).
- Fix: Demo only when the combination itself is ILLUSTRATIVE (`source_basis`), never from a check; or refuse a Sample check on a SOURCE_BACKED combination; or require the approver to confirm a Demo release.

**m2. Refusal copy gives no reason or cannot tell keys apart.** (a) A key whose people have no values (accepted by G4) fails with `failed: 0 of 0 values.` and no cause, twice if two families have that shape (`engine/answer-key-gate.ts:53`). (b) Two families with the same label (labels are not unique) give word-for-word identical lines, 60 of them with 60 keys. Fix: "has no expected values" for 0 of 0; add the key's version or the family key to the line.

**m3. Refused calls store runs and audit lines without bound; no cap on keys.** Approve on a released, unchanged combination with 2 keys, five times: 409 "Not submitted", `answer_key_run` 13 to 23, audit +10 (about 5.6 kB a run). Each refused Submit or Approve with 60 keys stores 60 runs (about 350 kB). No limit on keys per item: Submit took 2.85 s with 60 keys (47 ms a key, linear; 400 keys about 19 s). Fix: run keys in Approve only after the "Not submitted" and stale-draft refusals (as Submit does after "Nothing has changed"); cap keys per item (for example 20); keep only the last refused run per key.

**m4. Release page and per-combination Approve disagree on a key added after Submit.** Submit (unsigned passing key, Demo), then a second key for the same map. Review: error "has not run on this draft"; `/api/draft` row `held: true`; `POST /pack/release` 409. Direct `POST …/approve` (user-B) runs the key and releases (201). Safe direction, but the Release page's advice ("run it on Tests") is not needed for one route and an approver cannot run keys (author or expert only). Fix: run the stored-run check at Submit and show "will run at release", or hold in both routes.

**m5. "Demo release" chip shows in a non-demo workspace.** On `firm`, `answer_keys.demo=false` and the gate refuses as real, but `GET /api/combinations/<vv>` lists all 6 releases `demo:true`, and `/api/draft` row `demo:true` (`studio.ts:386`, `:1057`, `programs.ts:378-379` read the snapshot and combination basis only). Contradicts concept BR-3 "same derivation as the page's flag". Build-notes discovery 5 records it as G3's deferred part.

**m6. `keysUnchanged` ignores a key created after judgement.** `now.length < want.length` plus `every` (`api/src/answer-key-gate.ts:105-109`): a key inserted between the judging read and the transaction (`INSERT` is not blocked by `FOR SHARE`) is neither judged nor refused. A millisecond window; the uncommitted working-tree diff already compares exact id sets, so no extra fix asked.

**m7. Cost per changed combination.** `testableItems` hashes every map twice: 9.6 ms for 6 maps and 461 entries (measured, 400 repeats = 3.8 s synchronous, only for rows with a pending change). On a copy with 370 combinations and 529 nodes the uncached catalogue took 4.0 s with G2 and 4.97 s on 260e9660~1: baseline, not G2 (scale_100.ts is stale on Linux/E2BIG and fails at Submit on the filing rule, so partial load only).
