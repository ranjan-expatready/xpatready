## Major (must fix before Approve)
1. **A new field outside `person`/`case` lands with its area written twice in its library key.** `labelOf` (field-draft-items.ts:40) puts the area into the label, for example "Family name (sponsor)". Line 74 then sets `subject` to that same area. The lander builds the key as `keyFor(subject, label)` (proposals.ts:220), so the area appears twice. My probe accepted a drafted `sponsor.family_name`, and it landed as **`sponsor.family_name_sponsor`**, which then waited for approval as an ADD. The draft prompt (p2/prompts/field-map.v2.md:7) allows the areas `relationship`, `organisation` and `representative`, so this happens to every new field in three of the five areas, for example `organisation.phone_organisation`. That writes keys that break the naming convention into the shared library. Keys are meant to be stable, and the AI's `proposedKey` (kept in `work`) is lost. This fails STANDARDS §5 "stable keys separate from labels" and P-120 "the system builds the system name from the naming convention". Fix: keep the area out of the text that `keyFor` reads. One way is to pass the convention-checked `proposedKey` for the lander to use when it is free, and fall back to `keyFor` otherwise. Add a check that accepts a drafted `relationship.*` or `organisation.*` field and asserts its key.
2. **The P-120 rule "a near duplicate is never Ready" has a test that still passes when the rule is removed** (STANDARDS §6 [M]). I changed line 82 to `plain = REUSE || NEW` in a copy and re-ran the pure part: 11/11 still passed. The check "a field close to a library field is never Ready" (check_c1113_draft_fields.ts:52) passes for another reason: its item is a `decide` reuse of `person.birth_country`, so it never reaches the NEW-with-a-near-candidate branch. Fix: add a case where normalize returns NEW with a candidate scoring 0.55 or more. Assert `confidence === "check"`, that `identity.near` holds the candidate, and that `nearReason` is set.
