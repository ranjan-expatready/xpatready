## Major
**M1. The real earlier case is crowded out: five other same-name cases, including newer empty ones, hide it, and POST then returns 404** (BR-1; `api/src/earlier-facts.ts:22`, `:47-49`)
* Steps: case CA (Visitor visa, name N) has its passport number and date of birth answered and confirmed. Open case CX (work permit, N): the GET lists CA. Then open five more cases named N with no answers (CN0-CN4). Run the GET on CX again. Then POST `{earlierCase: CA, …}` on CX.
* Observed: `earlier` = [CN4, CN3, CN2, CN1, CN0], each with 0 facts, and every one was opened **after** CX. CA is gone, and the POST returns 404 "No earlier case of this client with that id." The card opens on the newest empty case (`list[0]`). Another cause of the same loss: the 500-row scan (`take: 500`) runs before the name filter, so in a firm with more than 500 newer principals an older case is never found.
* Expected (BR-1 "earlier cases … not this case"): only cases opened before this one, a name filter in the query rather than after a 500-row slice, and no cap that drops the case that holds the facts (for example, skip cases with nothing to offer, or page them).
* Fail test: A with confirmed facts, then X, then 5 newer same-name cases: X's GET still lists A and no case newer than X; POST from A → 201.

**M2. Another client login's answers enter this case as "the client's own answer, confirmed", and that client then sees them** (BR-1, BR-4, personal data; `api/src/earlier-facts.ts:47`, `:135`; `engine/runtime/case.ts:89`)
* Steps: case PA (Visitor visa, client login user-P, name N): user-P answers date of birth 1977-07-07 in the questionnaire. Case QB (work permit, client login **user-Q**, same name N). The officer opens QB: PA is offered and the date of birth is usable. Tick it and press Re-confirm.
* Observed: 201. On QB the answer reads `channel: questionnaire, by: user-P, confirmed: true, why: "Declared: the client's own answer"`, so it is off QB's Confirm list. `GET /questionnaire` as user-Q contains 1977-07-07. The match ignores `clientActorId`, which the database already holds on both cases. The copied giver (user-P) is not QB's client, yet `confirmation()` reads it as QB's client's own answer.
* Expected: two cases with different client logins are never the "same person" (or the pick says so and the case is refused). A client's own answer copied from another login arrives as entered by staff, on the Confirm list (P-411 (2)). Another person's values never reach a different client's portal unseen.
* Fail test: same name with different `clientActor` → that case is not listed and POST → 404. With the same login, the copied client answer is `confirmed` only if `source.actor` = this case's `clientActorId`.

## What held
* **Earlier case never written:** `answersOf(A)` was the same before and after every copy, every race and every refused POST. The GET writes nothing: `pg_stat_user_tables` showed 0 inserts, updates or deletes over 3 GETs.
* **Concurrency:** 3 identical POSTs at once gave one 201 and two 409 "Changed since you looked", with exactly one current answer per fact. POST against a PUT of the same earlier answer, 4 times: every time 409/200, 0 copies of a value the officer did not see. POST against a PUT of the same fact on this case, 4 times: 409/200, one current answer each time, no 5xx. A double-click on the button copied once and showed no error.
* **Roles:** user-P, user-Q and user-A get 403 on the GET and the POST, even with a malformed body. user-S (the solo firm) gets 404, and a POST naming the Sample firm's case gets 404. An unknown actor or no header gets 401. user-T (same firm) may.
* **Wrong inputs:** a non-uuid or unknown case id → 404. A non-uuid `earlierCase`, `from` or `subject_id` → 400. `earlierCase` = this case → 404. A take on the `case` subject or a fact not offered → 409 "Not offered", nothing written. 201 takes, 201 seen keys, a 5000-character fact or a 2 MB key → 400. A string or array body → 400.
* **Expiry:** an expired passport is refused with the rule and the Sample label on the work permit; an expiring-soon passport is warned. Status and verifier are kept (B1). Audit text and `api.log` contain no answer values. Blank, 3-space and 5000-character names are refused at Open a case. The GET took 62-93 ms with 5 earlier cases.
* **Screen:** the keyboard tab order is checkbox, chip, chip, next row. Tooltips open on focus, and the checkbox shows a 2 px focus outline. No page errors. No page-level sideways scroll at 1024 px or 720 px.
