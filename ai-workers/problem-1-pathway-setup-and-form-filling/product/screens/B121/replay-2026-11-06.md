# B121 replay: the last 60 PR checks with the reference graph (6 Nov, evidence lane)

Updated after review (M1, M2 fixed): selections grew slightly; every failed suite is still chosen. Facts below come from GitHub's runs API (read-only, US$0) and from running the selector; the predicted minutes are a model, marked as such. Scripts: `replay/` (fetch.sh → replay.sh → model.js).

## Window and method
* **Window:** the last 60 successful `ci` runs on pull requests (no `mergify/*` batches), 5 Nov 11:37 → 23:52 UTC, plus the 12 failed PR runs in the same window. Measured: median **5.8 min**, 75th percentile **28.9 min**, 21 of 60 at 10 min or more (P-376 (4) measured 6.0 / 29.6 on an earlier window: the same shape).
* **Of the 60, 39 are notes or records runs** (no suites; 0.4 to 8 min) and **21 are code runs on 6 parts** (22.7 to 35.0 min). So the 75th percentile is under 10 min only if at least 7 of the 21 code runs drop under 10 min.
* **Replay:** for each code run, the new `select-suites.mjs` reads that run's own changed files (`git diff base...head`, the range in the run's log) **at that run's head tree** (a worktree), as CI would have.
* **Time model:** suite seconds are the median of each suite's own time over the window's ALL runs (else `suite-times.tsv`, else 30 s); units are dealt to the parts as `run-suites.sh --shard` deals them; a part's suite step is 1.12 × its suites' seconds + 4 s; each run keeps its own measured set-up and start-up offset. **Calibration:** the model on the runs' actual selections is within −2.1 to +3.9 min of the measured time, median +0.6 min.

## Two other measured findings
* **Set-up time, not Prisma or the web build:** in these runs the schema step (61 migrations plus `prisma generate`) takes about 3 s and the web build about 1 s per part, so caching them across parts saves about 2 s. The variance is apt: per part the set-up step's median is 46 s, its 90th percentile 208 s, max 360 s (`zsh and locale` 103-140 s and `postgresql 18` 82-193 s when slow). A run waits for its slowest part: the slowest part's set-up per run has a median of 192 s, **about 2.4 min more than the median part in 19 of 32 runs**.
* **The old selector was itself slow:** on the largest diff in the window (98 files) it took 100 s on each part; the new one takes 5 s (pattern tests remembered).

## Schema drift on main (found by check_prisma_schema.ts)
Replaying the 61 migrations does not give `schema.prisma` at 4e26fb229: the migrations still create table `canonical_field_name`, which the schema no longer has, and four tables (`fact_source`, `form_edition_accept`, `person_role`, `validated_copy`) take their `id` default from the database (`gen_random_uuid()`) where the schema gives it from Prisma (`@default(uuid())`). The check lists these five as known and fails on anything new. Fixing them is a migration (one in flight at a time, read by the tech lead): not done here.
