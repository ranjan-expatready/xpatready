## 1. Job and journey
**Job.** *"My client is part-way through a journey: record what was done before we started, and when this application is done, start the next one without asking anything twice."*
* **Who:** case staff of the case's firm (officer duty; the team's `agent/case:create` and `agent/case:edit`). Client 403 on the stage routes (their questionnaire follows the current stage); configuration people 403; another firm 404.
* **When:** (a) opening a case on a combination that is a later stage of a route (SA-1B-212); (b) any time the current stage has a next stage: a manual button (AG-7-45 rule 2; AG07-D26(6) Q111).
* **Demo journey (Sample route "Study, then work"):** Study permit (outside Canada) → Employer-specific work permit with an LMIA (inside Canada), both among the six (`samples/wave1.json`), both released on the checkpoint (`acceptance/C10.1.test.ts:62,73`). **Sample, not a recommended route** (TAXONOMY case 3 has the post-graduation work permit following the study permit, not configured); real routes (Express Entry profile → PR, P-24; nomination → PR) come from the immigration expert. Express Entry is not used: no profile combination (online only, P-152).
* **Not:** the team's delivery stages (AG-7-9/-10, the team's case shell, P-169); decisions, `offersNextOn`, a choice among next stages, repeatable stages, refusal re-routing (SA-1B-66 rules 3-4, 10; SA-1B-68 rules 2-7); removing a stage; route authoring (SA-1B-66 screen); reminders and Needs you (Minder, P-169).

## 3. Business rules
* **BR-1 One case, stages in sequence** (AG-7-45 rule 2; SA-1B-64 rule 2): a stage is one combination on the case's route; one stage at a time (side-by-side programmes stay held, SA1B-D72, P-316 (1)); a combination on no route is a one-stage case with no strip.
* **BR-2 The route is data** (SA-1B-66 rules 1, 2, 9; P-24; Q1): ordered stages {key, staff and client name, combination key, key details (library fields), next stage (one), deadline rule or none}; loaded only with 2+ stages, every combination present and **used once** (no repeats), "next" inside the route; frozen on the case at opening as its stage rows. A stage whose combination is retired or has no startable release reads "Cannot start yet" and is never an opening or next stage.
* **BR-3 Open at a later stage** (SA-1B-212; Q3): earlier stages each "Done before we started" (ticked; untick = not recorded) with optional key details, **stored on the stage row** as the team's `StageRecord.keyDetails` (SA-1B-66 rule 2: scope filing; SA-1B-212 §7), typed by their library field (wrong type: 400 on the field, nothing created) and editable later on the stage panel. A field the route marks **same at every stage** (Sample: UCI) is also written as the person's answer, channel "stage record", by the officer (P-78). A done-before stage gets no pin, application subject, questions, documents, forms or fees (rule 4).
* **BR-4 Start next stage** (SA-1B-67 rules 1, 3, 5; SA1B-D63): a person presses it. Before the click the dialog shows: next stage and release; who comes along and anyone whose role it lacks ("stays on the case and files nothing in this stage"); counts of person answers already given, questions about this application asked again, new questions, forms, documents; the deadline (Sample); the ending stage's key details, pre-filled **only from that stage's own record**; "This cannot be undone". A filing of the ending stage with no `FilingRecord` → a warning names it and a reason is required (P-237). One transaction under `runtime_case FOR UPDATE`: request names the current stage and stage version (else 409); next combination not retired (as `runtime.ts:102`) and startable (as `:107`), else 409 named, nothing changed; pin revision 1 for the next combination; a **new application subject** (`case_participant` role `case`); states move; `Case.combinationId` → next; one audit line (never key-detail values, SA-1B-212 §10).
* **BR-5 What carries** (X-2; AG07-D26(6) Q111; B3): **person answers** are read where they are (no answer written); answers about the application (its number, date, office, country where applying, type) belong to the stage's own application subject and are asked again. The ended stage's rows keep their states: read-only history.
* **BR-6 Documents:** the new stage's lines start fresh; a current upload of the same person and type shows "On file from Study permit, uploaded 9 Nov: check it for this application" (received). The ended stage's panel reads its lines' own documents (`checklistLineId`, uploaded before it ended), never later uploads (m2; `case-checklist.ts:83,178`).
* **BR-7 Forms and copies** (M3): copies, snapshots and assessments belong to the stage whose combination is their release's combination (`FormInstance.configReleaseId` → release → combination); within the current stage B145's "out of date because of the release" applies unchanged. IMM 5476, 5475 and 5409 sit in both releases and never cross.
* **BR-8 Deadline** (Q2; M2): computed on read from the stage's rule and its key detail, shown on the strip, the stage panel, the dialog and the Open-a-case summary, labelled **Sample** everywhere; missing detail → "Can't set: Study permit valid until is missing". No filing item, no reminder, no Needs you (P-169; B11).
* **BR-9 Readers follow the current stage** (B1, M3): `reach()` selects pins `where combinationId = Case.combinationId`, checks `pinChain` and hashes on that chain and every other pin's hash, and returns only the current stage's application subject among participants (so the 16 readers by role `case` follow, `case-prepare.ts:267`, `case-changes.ts:43`); B145's Fill re-check, where-used and recorded-filing refusal filter by the current combination or stage; by stage: `case-prepare.ts:159-160,174,196-197,621-622`, `case-filings.ts:31`, `case-checklist.ts:76-79`, `readiness-inputs.ts:60`, `findings.ts:43,65,89`, `filing-record.ts:28`, `submission-record.ts:80,91`, `fill-case.ts:146,159,244,358`, `sample-validated.ts:72`; by combination: `assessments.ts:64,95,142,172,176`, `form-library.ts:493` (an ended stage's release is not "filed now").
* **BR-10 No write from a stale stage** (M4): Prepare re-reads the current stage under its lock and answers 409 "read again" if it moved (as B145 does for Fill); checklist lines insert with the stage read under `FOR SHARE` on the case row.
* **BR-11 Who:** officer duty for BR-3/BR-4; client 403, configuration 403, another firm 404; no next stage 409.

## 4. Layout
**Workspace** pattern. **Stage strip** under the case header, GOV.UK task-list statuses: "Done before we started" · "Current" · "Ended — next stage started" (ⓘ m5) · "Not started" · "Cannot start yet" (grey, not linked); **Start next stage: <name>** only when a next stage exists; the deadline under the current chip (Sample). **Dialog** pattern for Open a case's step 2 "Earlier stages" and for Start next stage. A stage chip opens a **Side panel** (read only): key details ("entered by the case officer"), filings, numbers, records, its own documents. States: one stage (no strip), loading, warning (reason box), refused (nothing changed), conflict (409), read-only (strip only), done (toast).

| Flowable CMMN manual activation | a person starts the next stage from "a list of buttons" | `flowable/flowable-engine` |
| Temporal Continue-As-New | one identity, a new run with its own history | `temporalio/documentation` |
**Copied:** statuses and "Cannot start yet"; one strip; newest release at the click (SA1B-D85); a person starts it; one identity, the earlier run kept. **Beaten:** Camunda copies variables and Temporal passes state; we copy nothing: person facts are read where they are, application facts are asked again for the new application, so nothing drifts and nothing wrong is carried. The dialog says before the click what comes along, what is asked again, who files nothing and what is unrecorded. **Effort:** one button, one dialog.
