## 1. Job and journey
**Job.** *"My client is part-way through a journey: record what was done before we started, and when this application is done, start the next one without asking anything twice."*
* **Who:** case staff of the case's firm (officer duty; the team's `agent/case:create` and `agent/case:edit`). Client 403 on the stage routes (their questionnaire simply follows the current stage); configuration people 403; another firm 404.
* **When:** (a) opening a case on a combination that is a later stage of a route (SA-1B-212); (b) any time the current stage has a next stage: a manual button (AG-7-45 rule 2; AG07-D26(6) Q111 "the manual button also works earlier").
* **Demo journey (Sample route "Study, then work"):** Study permit (outside Canada) → Employer-specific work permit with an LMIA (inside Canada). Both are among the six (`samples/wave1.json`) and are released by the checkpoint's step 110 when they pass the validator (`api/src/features/checkpoint/110-release-one.ts:20-36`; not run here: the pack fails if either is missing). A new checkpoint step loads the Sample route after release one. **Sample: shows the mechanism, not an IRCC route**; real routes (Express Entry profile → PR application, P-24; provincial nomination → PR, TAXONOMY case 9) come from the immigration expert. Express Entry is not used: no profile combination is configured (online only, P-152).
* **Not:** route stages are not the team's delivery stages (AG-7-9/-10: file started … submitted, the team's case shell, P-169); decisions, the `offersNextOn` event, a choice among next stages, "Start again", refusal re-routing (SA-1B-66 rules 3-4, 10; SA-1B-68 rules 2-7); route authoring (SA-1B-66 screen); reminders and Needs-you entries (Minder, P-169).

## 3. Business rules
* **BR-1 One case, stages in sequence** (AG-7-45 rule 2; SA-1B-64 rule 2; TAXONOMY §3): a stage is one combination on the case's route; the case works one stage at a time (filings on different programmes side by side stay held, SA1B-D72, P-316 (1)). A combination on no route is a one-stage case: no strip, no change (SA-1B-66 rule 1).
* **BR-2 The route is data** (SA-1B-66 rules 1, 2, 9; P-24; Q1, Q3): ordered stages {key, staff and client name, combination key, key details (single library fields), next stage (one in M3), deadline rule or none}. Loaded only when it has 2+ stages, every combination exists, "next" names a stage of the route and every key detail is a single library field; otherwise refused with the reason. A stage whose combination has no startable release reads "Cannot start yet" and is never an opening or next stage. The route is frozen on the case at opening as its stage rows (stays until moved, AG-7-56 rule 2).
* **BR-3 Open at a later stage** (SA-1B-212): choosing a later stage's combination lists the earlier stages, each "Done before we started" (ticked; untick = not recorded) with its key details, all optional (rule 3). A done-before stage gets no pin, questionnaire, documents, forms or fees (rule 4). **Key details are saved as the person's answers** to their library fields (Declared, P-242; source "done before we started"), so the new stage's questions and forms read them and a correction is an ordinary answer change with history (rule 5): one fact, never two. A value of the wrong type: 400 on that field, nothing created.
* **BR-4 Start next stage** (SA-1B-67 rules 1, 3, 5; SA1B-D63): a person presses it. Before the click the dialog shows the next stage and its release; who comes along and anyone whose role the next combination lacks ("Client C stays on the case and files nothing in this stage"); answers already given and new questions (counts); forms and documents it adds; the deadline; the ending stage's key details, pre-filled from answers. If a filing of the current stage has no filing record (C8.2 `FilingRecord`), a warning names it and a reason is required (warn, never block, P-237). One transaction under `runtime_case FOR UPDATE`: the request names the current stage and the stage version it read (else 409 "read again"); the next combination's newest release passes `startableMissing` (else 409 naming it, nothing changed, as `runtime.ts:107`); a pin is inserted; current → "Ended — next stage started"; next → current; `Case.combinationId` → next; one audit line (stages, who, reason; never key-detail values, SA-1B-212 §10).
* **BR-5 Carried, never copied** (X-2; AG07-D26(6) Q111; SA-1B-67 §13): answers are read where they are; the start writes no answer; new questions open in the new release's questionnaire. The ended stage's filings, items, copies, scans, records and reviews keep their rows and states: read-only history.
* **BR-6 Documents:** the new stage's checklist lines are its own and start fresh; a current upload of the same person and type (read by person, `case-checklist.ts:79`) shows on the new line "On file from Study permit, uploaded 9 Nov: check it for this application" (received, not approved). Nothing uploaded twice; no approval for another application carried silently.
* **BR-7 Forms:** the new stage's forms come from its release; copies made on the ended stage's release (`FormInstance.configReleaseId`) stay that stage's history and are never shown as this stage's copies; Fill and the channel look-ups read the current stage's items only (`fill-case.ts:244,358`).
* **BR-8 Deadline** (Q2; SA-1B-67 rule 4; SA-1B-212 rules 3, 6): a stage may carry one rule {label, key detail it counts from, days}; the new stage's filing gets a `step` item (kind exists, `schema.prisma:1793`) "Apply before the study permit expires · due 3 Feb 2027" (**Sample**). Missing key detail → "Can't set: Study permit valid until is missing", worked out again when the answer is given. No reminder, no Needs-you entry (Minder, P-169; B11).
* **BR-9 Readers follow the current stage:** `reach()` takes the pin of the current stage's combination and still checks every pin's hash; prepare, filings, checklist, readiness, fill, assessments and where-used read the current stage's rows (§2 list). With B145: a release move moves the current stage's pin only, and its "recorded filing" refusal reads the current stage's filings (else an ended stage's record freezes the case forever).
* **BR-10 Who:** BR-4 and BR-3 need the officer duty; client 403, configuration 403, another firm 404; no next stage 409; a "Cannot start yet" stage 409 named.

## 4. Layout
**Workspace** pattern (EXPERIENCE §3). **Stage strip** under the case header, GOV.UK task-list statuses in sentence case: "Study permit · Done before we started" · "Work permit with an LMIA · Current" · "Not started" or "Cannot start yet" (grey, not linked); the primary button **Start next stage: <name>** at its right only when a next stage exists. **Dialog** pattern for Open a case's step 2 "Earlier stages" and for Start next stage (one page: what comes along, what it adds, deadline, reason when warned). An ended or done-before chip opens a **Side panel** (read only): its key details, filings, numbers and records. States: one stage (no strip), loading (skeleton chips), warning (unrecorded filing, reason box), refused (not startable: the reason, nothing changed), conflict (409: "This case changed while you read: read it again"), read-only (no duty: strip only), done (toast).

## 4b. Best in class
Read 7 Nov 2026 from primary sources: `best-in-class-sources-2026-11-07.md` (vendor sites and canada.ca do not resolve here).
| Who | Best at | Source |
|---|---|---|
| GOV.UK Design System, Complete multiple tasks + Task list | few statuses, sentence case; "Cannot start yet" grey and not linked; tasks grouped into steps that are stages | `alphagov/govuk-design-system` |
| GOV.UK Step by step navigation | a sequence of steps towards one goal; says which step you are in | `alphagov/govuk_publishing_components` |
| Camunda 8 call activity | the called process binds the latest version "at the moment the call activity is activated" | `camunda/camunda-docs` |
| Flowable CMMN manual activation | stages a person activates: "a list of buttons of potential plan item instances that can currently be started" | `flowable/flowable-engine` docs |
| Temporal Continue-As-New | same identity, a new run with its own history, chained to the last | `temporalio/documentation` |
**Copied:** sentence-case statuses and "Cannot start yet"; where you stand on one strip; the newest release at the click (SA1B-D85); a person starts the stage; one identity, the earlier run kept. **Beaten:** Camunda copies variables into the child and Temporal passes state; we copy nothing: the next stage reads the same person's answers, so nothing drifts or is typed twice. Key details entered once at opening are the answers later forms read. The dialog says before the click what comes along, what is new, who files nothing and what is not yet recorded. **Effort:** one button, one dialog; nothing typed but optional key details and a reason when warned.
