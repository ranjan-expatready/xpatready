# B139 · C6.17 A multi-stage case: challenge

Fresh challenger (did not draft it), 7 Nov 2026. Read against `concept.md`, `design/draft-multi-stage.html`, `best-in-class-sources-2026-11-07.md`, the app on `origin/main` (worktree at b16464f11; studio the same as c1007beb4), and B145 on `origin/claude/exciting-mccarthy-up4u21` @ 50f1a67d1 (migration, `reach()`, where-used, Fill and the move are already coded there). Team sources: `domain/requirements-2026-11-02/` SA-01B v2.1 (SA-1B-64, -66, -67, -68, -212) and AG-07 v3.12. `ai-workers/tools/freshness.sh` cannot run in this copy (no `code/`: `README-copies.md` missing), so team code claims are **Unverified**. canada.ca is not reachable: every immigration value stays **Sample**.

## Verdict
**Build after these changes.** The job, the "done before we started" record, one person pressing Start next stage, the newest release at the click and a transaction that is all or nothing are right. Three things break as written. First, B145's code makes every case with a second pin unreadable. Second, a unique index the concept missed refuses the second stage's family group. Third, "carry answers" also carries the first application's own answers (its number, date and office) onto the next application's forms. Five reader and race gaps would let one stage's rows leak into the other.

## Objections

### Blocker
**B1 · B145's `reach()` refuses any case with pins on two combinations. "PackWorkPin unchanged; it composes" holds for the index only.** *Needed for the proof.* Confidence: high (fact).
* What breaks: on the B145 branch, `reach()` orders all of the case's pins by revision (`api/src/runtime.ts:69`). It then requires `pinChain(...).ok`, meaning revisions n…1 with no gap and rising versions, across **all** pins, and refuses any pin whose release is not of `Case.combinationId` (`:75`; `engine/runtime/release-update.ts:221-223`). After Start next stage the case has a study-permit pin (rev 1) and a work-permit pin (rev 1). The chain reads [1,1] (not ok) and the study pin fails the combination check, so **every case route answers 409** "pin does not match". The same mistake is in three more places: Fill's re-check takes the newest pin by case only (`fill-case.ts:243-244`), so its revision comparison picks an arbitrary pin; where-used keeps "the last pin per case" across combinations (`where-used.ts:241`); and the move refuses once any `filing_record` exists on the case (`release-update.ts:116`), so the ended stage's record freezes the new stage. The insert trigger is fine: a new combination's first pin is revision 1 (`20261107180000_c95_pin_revisions`).
* Example: C6.17-8 starts the work permit, then C6.17-9 `GET /runtime/cases/:id` returns 409, so the pack fails at step 9.
* Fix: build B139 **after** B145 merges (B139's migration timestamp later than `20261107180000`). In B139's PR, `reach()` selects pins `where combinationId = Case.combinationId`, checks `pinChain` and the hash on that combination's chain, and checks every other pin's hash. Fill's re-check, where-used and the move's recorded-filing refusal filter by the current stage's combination or stage. Test: a case with sp rev 1, then wp rev 1, then wp rev 2 reads wp rev 2, and B145's move refuses only for a record on the current stage.

**B2 · `submission_group_one_family` allows one FAMILY group per case, so the second stage's prepare fails.** *Needed for the proof.* Confidence: high (fact).
* What breaks: the migration widens `filing` and `checklist_line` to the stage and adds `stage_id` to `submission_group`, but it misses the partial unique index `ON submission_group (case_id) WHERE kind='FAMILY'` (`prisma/migrations/20261102030000_c612_c116_prepare_items/migration.sql:42`; it is SQL only, so `schema.prisma:1719` does not show it). Prepare on stage 2 finds no FAMILY group for that stage and creates one (`case-prepare.ts:180`), which is a unique violation and a 500.
* Fix: replace it with `(case_id, stage_id) WHERE kind='FAMILY'` in the same migration. Test C6.17-9 asserts one FAMILY group per stage.

**B3 · "Carried, never copied" also carries the first application's own answers onto the second application.** *Needed for the proof.* Confidence: high (fact). Immigration effect: wrong values on an IRCC form.
* What breaks: each case has one application subject ("The application", `subjectKind: "case"`, `runtime.ts:121`), and readers find it by role `case` (`case-prepare.ts:267`, `case-changes.ts:43`, 16 places). Its answers are facts about one application: `case.application_number`, `case.application_date`, `case.submission_office_name`/`_location`, `case.country_where_applying`, `case.application_type`, `case.applying_for_pgwp` (`p3/releases/c1-v3/configuration.json` canonical_fields). After the start, the work permit's forms read the study permit's application number, date, office and country where applying. The toast counts them as "answers already given".
* Example: the study permit was applied for from India and the work permit is inside Canada, but the work permit's IMM 5710 gets the study permit's "country where applying".
* Fix: each stage gets its own application subject, created at the start, linked from `case_stage`, as one more `case_participant` with role `case`. Readers take the current stage's subject. Person answers carry; application answers are asked again, and the dialog counts them ("5 answers about this application asked again"). Test: after C6.17-8 the current application subject has no answers, and Client A's person answers are unchanged.

### Major
**M1 · Key details are saved as person answers. The team's are stage-record facts, and one of the two Sample details changes meaning between stages.** *Needed for the proof.* Divergence from the team without a mapping. Confidence: high for the spec, medium for the field (Unverified until the study permit's release is read).
* The team: key details are "library fields of **scope filing**" (SA-1B-66 rule 2) and are stored on `StageRecord.keyDetails` (SA-1B-212 §7). "Later rules read them", for example the deadline (rule 5). `person.uci` is a person fact, so saving it as an answer is sound. `person.residence_status_to_date` is the person's *current* status "to" date, the date a form asks about when it is filed. In the in-app path (C6.17-5), the study permit's own IMM 1294 records the home-country status there. BR-4 then pre-fills "Study permit valid until" from that answer, so the deadline counts from the wrong date. Saving the permit's expiry over it leaves status "citizen of India, valid to 3 Feb 2027" on the next form.
* Fix: store key details on the stage row (`key_details` jsonb, as the team does); the deadline reads them. Write a person answer only for a field the route marks as the same fact at every stage (UCI). Pre-fill the ending stage's details from that stage's record only, never from answers given before the stage started. Every answer written records the officer and the channel "stage record" (P-78), and the side panel shows "entered by the case officer", not "Client A's answer" as the board does.

**M2 · The deadline as a `step` filing item is switched off by the next prepare.** *Needed for the proof.* Confidence: high (fact).
* Prepare's sync sets `active=false` on every item that is not in `wanted` (`case-prepare.ts:203-205`). `wanted` comes from the release (`engine/runtime/prepare.ts:18-41`), so the deadline line written at the start disappears on the first Prepare. It would also sit beside biometrics as something to do for filing (`case-prepare.ts:296`).
* Fix: compute the deadline on read from the stage's rule and key detail. Show it on the strip and in the stage panel, labelled **Sample** everywhere (the strip, the Open-a-case summary and the toast), with no filing item. This also keeps P-169 (Minder) and B11 (M4) untouched. If the founder wants it as a government step (Q2), it must enter `wantedItems`.

**M3 · The reader list in §2 is incomplete. The concept adds `stage_id` to three tables, but rows that hang off the case and not a filing need a stated rule.** *Needed for the proof.* Confidence: high (fact).
* Readers by case alone that are missing from §2: `findings.ts:43,65,89` (review findings, `filingId` nullable), `filing-record.ts:28` (C8.2 lists the ended stage's filings as this stage's), `submission-record.ts:80,91` (case tasks), `assessments.ts:95,142` (latest per person: the study permit's eligibility shows as "release changed"), `fill-case.ts:146,159` (copies by case and form number; IMM 5476, 5475 and 5409 are in **both** releases, `samples/wave1.json`), `sample-validated.ts:72`, `case-prepare.ts:621-622` (the version token), and `form-library.ts:493` (it says "an open case files it now" for the ended stage's release).
* BR-7 says to separate copies by `FormInstance.configReleaseId`, which clashes with B145: after a move, revision 1's copies must still show as "out of date because of the release", not vanish.
* Fix: the rule is "by filing → stage; form copies, snapshots and assessments by the release's **combination** = the stage's combination; case-level findings and tasks without a filing stay on the stage current when they were made (add `stage_id`)". BR-2: the loader refuses a route that uses one combination twice (repeatable stages are Not built). Test: C6.17-9 asserts that each listed reader shows no stage-1 row.

**M4 · Prepare and the checklist write stage rows from a stage read before the lock.** *Needed for the proof.* Confidence: high (fact).
* Prepare reaches the case and computes `wanted` from the pin outside the lock, then writes under `FOR NO KEY UPDATE` (`case-prepare.ts:210-212`). The checklist's GET `createMany`s lines with no lock at all (`case-checklist.ts:76`). A prepare or checklist read that races the start writes study-permit items or lines after the stage ended (or under the new stage). Test 11 covers Fill only.
* Fix: Start next stage takes `FOR UPDATE` on `runtime_case`. Prepare re-reads the current stage under its lock and returns 409 "read again" if it moved (as B145 does for Fill). Checklist lines insert with `stage_id` from the row locked `FOR SHARE`. Add both races to C6.17-11.

**M5 · The backfill is never exercised by the pack, and new one-stage cases are not specified.** *Needed for the proof.* Confidence: high.
* The checkpoint loads after the migration, so C6.17-12's "pre-migration case" and the family case are both created by the new code: the step passes on nothing. The concept says nothing about `createCase` writing a CURRENT stage for a combination on no route. With `stage_id NOT NULL`, every new case's Prepare fails. `tests/runtime/check_runtime_r1a.ts` inserts rows directly.
* Fix: `createCase` always writes one stage row (route null, stage key = combination key). Add a migration test in the style of `tests/check_forms_channels_migration.ts` that seeds cases with filings, lines and groups before the migration and asserts one CURRENT stage each, every `stage_id` set, and prepare unchanged. C6.17-12 then reads the family case's stage row rather than claiming a pre-migration case.

## What is sound

A person presses the button; the newest startable release is chosen at the click (SA-1B-67 rules 3 and 5, SA1B-D85). An unrecorded filing warns and asks for a reason, never blocks (P-237). One transaction with a stale-version 409. Forward-only states with a trigger. The ended stage's rows are kept. AI off at US$0. The pack's rules (fresh cases, fail never skip, picked by state, P-319). Scope cuts that match the team (choices among next stages, `offersNextOn`, repeatable stages, Needs you).
