## Verdict
**1 Blocker, 1 Major, 6 Minors.** The permissions hold everywhere I tried. The server holds as well: stale saves, duplicates, limits, other subject kinds, round-trip. The Blocker is in the dialog: several buttons that are not Save save the draft anyway.

## Blocker
**B1. Buttons that are not Save save the whole set and close the dialog.** `Button` sets no `type` (`web/src/components/ui/controls.tsx:33-36`), so inside the dialog's `<form onSubmit={save}>` (`eligibility-gates-editor.tsx:155`) every button is a submit button. A button that is still on the page after its own click runs `save()`. That covers "Add a comparison" and "Remove this comparison" (`conditions.tsx:134,145`), "Add a gate" (`:187`), "Add a line" (`:198`) and "Reload" (`:156`). Buttons that remove themselves from the page do not submit: the gate's Remove, Keep, Edit as JSON and a line's Remove.
* Repro 1 (unintended write): as user-A, open Edit on the checkpoint. On gate 1 ("Passport number and expiry date answered", two comparisons), click the bin icon "Remove this comparison" on the **first** comparison. Expected: one comparison is gone from the dialog and nothing is saved. Actual: PUT 200 and version 17→18. The dialog closes with the toast "Eligibility rules saved to the draft…". The stored rule is now only `exists person.passport_expiry_date`, and Save was never pressed.
* Repro 2 (a core task cannot be done): add a gate "Passport number and expiry both on file" with rule "Passport number is answered", then click "Add a comparison" to add the second comparison. Actual: the gate is saved with one comparison (v8→v9) and the dialog closes. The same happens on every reopen. With the rest of the form valid, the simple editor cannot build an "all of these" gate such as S7's (BR-3). The only way around it is Edit as JSON.
* Repro 3: "Add a gate" or "Add a line" sends a PUT that is refused with 400. A new, untouched row then shows "Give the gate a label…", "A gate needs a rule…" and "Some details need fixing" before the person has typed anything.
* Each stray save also adds an audit row and raises the version. A second tab then hits a 409 that nobody caused on purpose.

## Major
**M1. An empty value box makes a gate nobody can meet, and the screen says "Condition is valid".** Pick a question and leave the comparison on "is". If the value is left empty, the builder emits `{op:"eq", field, value:""}` (`conditions.tsx:96`, which keeps any row that has a field). An empty "is one of" emits `value: []`.
* Repro: add gate "Passport number on file", type the question "Passport number", keep "is", leave the value empty and save. Expected: refused under the gate, as an empty label is. Actual: 200, and the section shows "Met when: Passport number is · If not met: Not eligible". `draft.problems` has no Eligibility line, so the release check passes it. Review shows `rule: person.passport_number is ""`. I checked it with the engine (`gateResult`/`outcomeOf`): a person who answered `AB123456` gets **not_met → NOT_ELIGIBLE**, and an unanswered person stays Not answered for ever. `in []` behaves the same way. `checkGates`/`valueProblems` (`engine/eligibility-gates.ts:55-60,74-80`) accept `""` for text, and `/conditions/check` returns no errors.
* Why Major and not Blocker: the content reviewer sees the rule's words before release. Still, after release every case that answered the question gets a wrong Not eligible.

## Minor
* **m1. The live status says "valid" for rules the server or release refuses.** With Edit as JSON set to `{"subjectKind":"EACH_APPLICANT",…}`, the builder shows "Condition is valid". After "Use the simple editor" it also reads "Checked for each person", although the value is still EACH_APPLICANT. Save then refuses it under the gate ("…about each_applicant, not each person"). A calculated value typed by hand (`person.age_years`) shows the gate warning and "Condition is valid" side by side; it saves (200) and is refused only by the release check, which does show under the gate. Cause: `/conditions/check` does not know about gates (`conditions.tsx:86-90`).
* **m2. Errors stay on row positions after a Remove.** Errors are stored by index (`errors["gates.N.…"]`, `:144,164`). Save rows 0–7 with row 4 a duplicate label, then remove new rows 7, 6 and 4. "Gate 1 already reads "passport NUMBER…"" now shows under the "Rule 1" gate, which moved into position 4.
* **m3. Cancel and browser Back discard edits without asking.** Escape, the X and the overlay ask "Discard your unsaved changes?", and reload asks (beforeunload), all as BR §4 says. Cancel calls `close` directly (`:154`), and an in-app Back (`history.back` from `/c/<id>/questionnaires` to `/c/<id>`) unmounts the dialog. Either way the edits are gone without a word (checked: the label was not kept after Forward).
* **m4. Keyboard focus is lost on Remove.** Enter on "Remove the gate <label>" swaps the button for the confirm, and focus falls back to the dialog container. The next Tab goes to the dialog's Close (X), not to the confirm's Remove or Keep. Confirming has the same effect (`:178-184`). The ⓘ tip (`:48`) is a `role="img"` span and cannot be focused, so a sighted keyboard user never sees it.
* **m5. A retired-while-open save shows as "Changed by someone else".** From reading the code; not walked: retiring needs a pack release. Every 409 goes to `setStale` (`:141`). The server's retired refusal is also a 409 (`api/src/eligibility.ts:39`), so it shows under the stale title with a Reload button that cannot fix it.
* **m6. Type code and truncated names at 200 %.** At 640 CSS px (200 % zoom) the question box shows "Criminal histo", and the line under it ends "· yes_no", a type code on the main path (the builder's existing words, now on this screen). No sideways scroll at 1024 px or 200 % (section 750/750 and 606/606, dialog body 894/894 and 606/606).
