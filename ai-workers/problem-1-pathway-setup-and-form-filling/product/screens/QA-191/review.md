## Answers to the five questions
1. **Does a failing rule keep an item out of Ready? Yes.** `sources.ts:634` sets `ready` on the library comparison alone. `insertProposals` then runs `p121Rating` (`proposals.ts:187`): `failed.length` gives `check` with "A rule did not pass (…)" (`agreement.ts:53-54`). `bulkWhy` re-rates from the stored rules (`proposals.ts:497-499`), so an item stored before the fix cannot be ticked either. Seen in the data: after B4 on `xr_studio_rvr`, `person.given_names` is agreed, `checker_quote_on_the_form:false`, `confidence=check`. Reason: "A rule did not pass (The words it quoted ("zq") are not printed on this form.), so a person checks it."
2. **False negatives on real forms: none for the quote that is checked.** I ran the same steps (`checkedOutput` → `normalize` → `quotes[0]` → `quoteOnForm(formWords(inv.fields))`) on 15 saved whole-form live runs: IMM 0008, 1294, 1344 (×8 incl. reconverted), 5257, 5406, 5532, 5562, 5604, 5646 and 5710. 0 misses across all first quotes (0008 93/93, 1294 95/95, 5710 95/95, 5532 22/22…). **False positives are the problem (Major M1).**
3. **Duplicates: a sound reading, and no false flags.** Entries carry one fact each (schema `field-map-output.v2`), so a box id (`data_path|person|row`) is claimed twice only by two entries for the same box. Composite parts are separate data_paths; people and rows are in `boxId`. Result: 0 duplicates in all 15 runs, so legitimate shared boxes are not flagged. The other P-121 meaning, the same meaning under two names, is already handled: `flagNearDuplicates` plus the near rule in `insertProposals` sends those items to Check. Gap: m2.
4. **References and options.** *Options:* not applicable to this step. The field-map output has no choice list (schema `value_type` only); choices come from the PDF box (P-162). *References:* not covered. `normalize.ts:68` turns a fact that an entry uses but nobody defined into an item with meaning "(used by a form field but not defined by the draft)" and type `text`. That item passes all five rules, and if both rounds do the same it can be Ready. 0 cases in the 15 runs. A follow-up row (m3). *Coverage:* QA-191's Expected names it, but the PR does not say how it reads it. A checker that leaves a field out already sends that field to Decide (`compareMaps` "Only the draft round named"), so run-level coverage cannot make an item Ready. Say so in the PR (m4).
5. **Anything weakened? No.** No production caller calls `mapRules` without `more`; only the test does. `field-draft-items.ts:61-63` keeps the same meaning (`!!q && squash(q) && formText.includes(squash(q))`). c1113_draft_fields 42/42 on my run. `quoteFound` was hard-coded `true` before and is now computed, so it is stricter.

## Issues
**Major**
- **M1: the quote check is a raw substring match, so QA-191's own repro still mostly works.** `engine/field-map-rounds.ts:44`, `words.includes(squashWords(quote))`, has no word boundaries and no minimum. Against IMM 5257's words, "na", "am", "ab", "e", "x" and "ily nam" all count as "printed on this form", as do **252 of 676 two-letter strings**. QA-191 says "an item whose quote is any 2+ characters is Ready". That is still true for over a third of 2-character quotes and for any single letter, so an agreed item quoting "na" is Ready. The fail test uses "zq", one of the strings that happens to miss, and its name "(any two characters were enough before)" claims more than the code does (`tests/check_gcore_b4_field_map_check.ts:97`). The repo's own rule for quotes is word-bounded (`engine/masters-ai.ts:150`, `p.includes(\` ${w} \`)`). **Fix:** match whole words, ``` ` ${words} `.includes(` ${squashWords(q)} `) ```. Add option labels to `formWords` (see m1). Add fail cases "na" and "e" to the pure test and one end-to-end. I measured the word-bounded match on the same 15 runs: **0 misses on first quotes**. Re-run c1113 (the matcher is shared).

**Minor**
- m1. `formWords` (`field-map-rounds.ts:40-42`) leaves out the inventory's `options` labels. The AI reads only the inventory, so it quotes them: IMM 1344 run `…20261022t034944757z` quotes "the province of Quebec", the label of the `LiveQC` option, and this matcher does not find it. The miss is safe (the item goes to Check) and today it is only a second quote. Add `options[][0]`.
- m2. `twiceCheck` (`sources.ts:628`) is built only from checker fields that match a draft key, so `cmp.checkOnly` is left out. A box that both an agreed field and a checker-only field fill is not flagged in the checker round. Include `cmp.checkOnly`.
- m3. References (P-121): a fact used by an entry but defined nowhere passes every rule (`normalize.ts:68`). Follow-up row: a rule "the field is defined in its round".
- m4. Coverage: write in the PR how coverage is read (per item, form fields on the form plus checker agreement), so the gap is not left silent.
- m5. Only `quotes[0]` is checked (`sources.ts:639-640`); a field keeps up to 4 distinct quotes. Check all of them, or say why one is enough.
- m6. Plain words: a failing checker rule shows "The words it quoted…" (`field-map-rounds.ts:53`). The `checker_` prefix stays in the rule id, so the person cannot tell which round quoted it. Say "The checker round quoted…".
- m7. The duplicates and type rules have only pure tests (`tests/check_gcore_b4_field_map_check.ts:98-101`). Breaking the `twiceDraft`, `twiceCheck` or `valueTypes` wiring in `sources.ts` fails no test. The schema enum makes the type rule unreachable from real runs, so this is acceptable if the PR says so.
