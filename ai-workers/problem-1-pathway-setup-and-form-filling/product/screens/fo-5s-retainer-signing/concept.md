## 1. Job and journey
**Job:** a firm turns a working prospect into a signed client: it keeps its own retainer templates, prepares a retainer with the client's details and fees already filled, sends it with one click, the client signs on a phone, the representative signs last, and both files are kept. **Personas:** Owner/Admin (templates), Case Officer and Case Manager (prepare, send, withdraw), the representative (licensed; countersigns), the client (public page, no account). **Journey (AG-05 A3; trace t5 §1):** Retainer templates → prospect screen (FO-4 screen 4) → Prepare retainer → Check and send → client: email code (P-564) → consent → sign → representative: Sign as the firm → Signed: files kept, "Your signed agreement" emailed, prospect Won (E-signed) → case side's "Open a case?" (FO-8, not here). Side paths: Edit (new version), Withdraw, Signed offline, Declined. **Cards:** AG-5-4, -7, -8, -9, -20, -26, -27, -31, -34, -39, -49, -55, -57, -62, -64, -65, -68, BR-21.

## 3. Business rules (each a pass and a fail test)
* **BR-1** Templates: Owner/Admin upload a `.docx`; placeholders found are listed; an unknown placeholder refuses the upload and names it ("{client.passport} is not a placeholder we know"); a missing client-name or fee placeholder is a plain warning, not a refusal ("This template never prints the client's name"); an unreadable file → "We could not read this file."; the empty state and the upload panel offer **Download a starter template** (one Sample `.docx`, Unconfirmed: no counsel, fee-row loop in place) (M5); a new file for the same template makes version n+1; Inactive templates are not offered for new drafts; a retainer keeps the template version it was made from (FO-5 row; AG-5-4 r1, AG-5-7).
* **BR-2** Prepare retainer is offered on a prospect (FO-5 "draft from a prospect"; a lead is Engaged first, FO-4 BR-7). No active licensed person → no draft: "No active licensed consultant — add one" with a link to Team (AG-5-49, BR-4).
* **BR-3** Representative picker lists only active people with a licence and the case-manager keys (FO-5; contracts §7 §1.2); it pre-selects the preparer when eligible, else stays empty (AG-5-57 r2, without the firm-default step, which no row holds). The retainer's representative may open that retainer page and the prospect's header whatever the visibility setting (B2).
* **BR-4** Signer: Individual → the prospect's person; Corporate → one `SIGNATORY` contact of the company; with none, a warning and a pick from the company's other contacts, never a block (AG-5-50, "Never a block") (FO-5; contracts §7 §2.1). A signer needs an email. For Corporate, "client name" is the company's name (m7).
* **BR-5** Fee rows: label, amount CAD, When (On signing · On a date (date) · When submitted · When decided · When done); a new draft starts with one row "Deposit on signing", On signing, which staff may change or delete (FO-5; AG-5-64 r1-r3).
* **BR-6** Before Send (M3), two kinds: **choices** that must be made — template, one signer with an email, one representative (field errors); **merge values** — only client name and fee (at least one fee row with an amount) block, on the field and in the summary ("Fee is missing. Add a fee row."); every other empty value shows "missing" and does not block (FO-5; AG-5-9 r2).
* **BR-7** The values and fees are copied into the version; a later change to the person never alters a sent version (FO-5; AG-5-3, BR-5).
* **BR-8** Send is one person's click (`agent/retainer:send`); the button disables on click and the server refuses a send unless the version is Draft (m5); the client gets one email from us, never from the vendor, Reply-To the firm's contact address (FO-6; P-561 condition 2; m1).
* **BR-9** Edit is offered on Draft, Sent, Viewed, Declined and Expired. On a sent one the primary is **Send updated version to Client B**: version n+1, the end of the old request, the new request and one "Updated agreement — please sign this version" email happen together or not at all; leaving without sending changes nothing; the old link says "This agreement was updated. Please use the latest email." Once the client signed, Edit is gone and a racing save is refused (FO-5, FO-6; AG-5-65 r2-r4, r7) (M1).
* **BR-10** Withdraw needs a reason (1-200), from Sent, Viewed or Client signed; the link stops and the client gets "Agreement withdrawn"; refused on Signed or Signed offline (FO-5, FO-6; AG-5-34 r2, r3). After Withdrawn or Expired, **Prepare retainer** comes back (a new retainer; the old one stays readable) (M2).
* **BR-11** Signed offline needs an uploaded PDF (AG-5-47's size limit) and a reason; from Draft, Sent, Viewed or Client signed; ends the open request; no email; filed "Signed on paper", no seal; the prospect becomes Won (Signed offline) once; the panel says it cannot be undone (FO-5; AG-5-39 r1, AG-5-47; contracts §2.6; m3).
* **BR-12** Signing page: when the firm setting is on (default), an email one-time code comes first: single use, short expiry, limited tries; too many tries lock the link for 15 minutes (Sample) — "Try again in 15 minutes." (M2). Verify starts a **signing session tied to this browser** (http-only cookie on the door's path, Sample 30 minutes); consent and the signing view refuse without it, so a forwarded link still needs the code (M4). Off: the session starts at consent (P-564; FO-6). One input with `autocomplete="one-time-code"`, numeric keyboard, paste allowed (WCAG 2.2 AA 3.3.8; m2).
* **BR-13** Consent: "I agree to sign electronically" must be ticked before the signing view loads; the consent text version is stored (FO-6; AG-5-20 r4). Untick → "Please agree to sign electronically first."
* **BR-14** The firm signs last: **Sign as the firm** shows only to the retainer's representative, only when the client has signed; it opens the same consent step and embedded view in a right panel on S5, then "Finishing signing…"; the route declares `agent/retainer:show` and checks "is this retainer's representative" on top; the server refuses an earlier signature (FO-6; AG-5-26, AG-5-27; AG05-D4(1)) (B2). If the representative is deactivated: "The representative is no longer active. Withdraw this retainer or record a paper signature." (M2).
* **BR-15** Completion: signed copy and audit file stored with us, downloadable by `agent/retainer:download` through short-lived links; "Your signed agreement" emailed to the client signer; prospect Won (E-signed) once (FO-6; AG-5-31 r4; contracts §2.6). Payment is never a condition (P-560).
* **BR-16** Decline: Declined, the link stops, shown on the prospect, one "needs you" mark for the prospect's owner (m4) (FO-6; AG-5-68 r2-r4). A request never expires once the client signed (FO-6; BR-21).
* **BR-17** (FO-5b; question 4 decided) the **template panel (S1)** shows "24 of 26 items marked in this template", each unmarked Code s. 24(3) item with its section and a "how we check" tooltip, where Owner and Admin can fix it; the draft keeps one quiet line with a link; **never blocks Send**; labelled "Unconfirmed: no counsel" (FO-5b; t8 §1) (M6).
* **BR-18** Buttons follow keys and state (table in §6); nothing for a module not built. **The signing door gives two kinds of answer (B1):** an unknown or malformed token, or another firm's → one plain "This link does not work."; a real token whose request has ended → its state (updated, withdrawn, declined, signed, expired) and the firm's name, no personal data. A link stays usable until its signer signs or declines (AG-5-21). "Thank you" comes from our own state after the hook lands, with "Finishing…" until then, never from a signal inside the vendor's frame (m6). Times on the client page name the firm's zone (m8).

## 4. Layout (P-473: calm work app, summary + one next step, sub-pages and right panels)
* **S1 Retainer templates** (Library list; Settings › Retainer templates; Owner/Admin): table Name · Version · Placeholders · Status (Active/Inactive) · Updated; primary "Upload template". **Upload panel** (right): name, `.docx` file, then "Placeholders found" (known ✓, unknown refused, named) and a "Placeholders you can use" list. **Template panel**: versions (each downloadable), Make inactive/active, Upload a new version.
* **S2 Retainer card on the prospect** (FO-4 screen 4, right rail): status chip, one line of reason, one next step: none → **Prepare retainer**; Draft → Continue the draft; Sent/Viewed → (no primary; "Waiting for Client B"); Client signed → for the representative only, **Sign as the firm** (orange "needs you" mark); Declined → orange for the prospect's owner, Edit and resend; Withdrawn/Expired → Prepare retainer; Signed and Signed offline → links to the files; all nine states drawn (M2). Month one's "needs you" is the representative's email (its link opens S5) plus the orange mark on this card and the pipeline card; no task list is claimed (B2). The pipeline card shows the same status in words.
* **S3 Prepare retainer** (Workspace sub-page, path Sales › Client B › Retainer): left: Template · Signer · Representative · Fees (rows table, Add a row); right: **Check before sending**: every filled value with its source, "missing" marks, errors linked to their field; FO-5b checklist panel (non-blocking). Primary "Check and send".
* **S4 Send panel** (right): "Send to Client B to sign": to (email), what happens (one email from <firm>; code by email when the setting is on; the representative signs after the client), version n. Primary "Send to Client B".
* **S5 Retainer page after sending** (same sub-page, read view): header status + next step; who has signed (client, then firm); **Versions** (each: made by, when, sent, ended or current, download original); **Activity** (sent, viewed, consent, signed, declined; from the timeline view, contracts §7 §0); actions: Edit (BR-9), Withdraw, Signed offline, downloads when signed.
* **S6 Panels**: Withdraw (reason), Signed offline (file + reason); both name what happens; confirm button names the action.
* **S7 Client signing page** (public, 375 px first): firm name and document title → (code) "Email me a code" → 6 boxes → consent tick → the vendor's embedded signing view inside our page → "Thank you". States: wrong code, code expired, too many tries, updated, withdrawn, declined, already signed, expired.
* **S8 Emails** (Sample text, sent by MailPort, Reply-To the firm): "Please sign your agreement", "Your code", "Updated agreement — please sign this version", "Agreement withdrawn", the representative's "Client B has signed — your signature is needed", "Your signed agreement" (m1).
* **States** (EXPERIENCE §4): empty templates ("No retainer templates yet. Upload your firm's .docx to start."), loading skeletons, must-fill errors, conflict (client signed while editing), read-only (no key or signed), refused (no licensed person), finishing ("Finishing signing…" until files land, AG-5-31 field 6).
