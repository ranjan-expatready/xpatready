## What I checked, with evidence
**Migration.** Additive: two `CREATE TABLE`, indexes, FKs, a function and a trigger; nothing existing is touched, so main's code runs on it (it reads neither table). Rollback is written in the file; I ran its statements inside a transaction on the migrated database and they executed in the right order (tables, then function, then the `_prisma_migrations` row), then rolled back. Constraints hold by direct insert: `key` outside the four steps refused; `print` without a copy refused (`sign_step_print_copy_check`); `media_type` outside PDF/JPEG/PNG refused; a second current row for the same item and step refused (partial unique index `sign_step_one_current`); an UPDATE on `signed_scan` refused by the trigger. Deleting a case with a printed step cascades cleanly (the `RESTRICT` on `copy_id` does not block it); a form copy cannot be deleted anyway (`runtime_copy_no_delete`). Note for the record: the trigger blocks UPDATE only. DELETE (and TRUNCATE) stay open, said in the migration so a case Reset works. That matches C8.1-14 as written.

**Scoping, three routes (GET item, POST step, POST scan), same results on all three.** Officer of the case's firm: 200. Other firm (solo firm user): 404 "No such case." Client who owns the case, and another client: 403 "Only the case officer can do this." Author and content reviewer: 403 "…works on configuration, not on cases." No actor or an unknown actor: 401. Representative: allowed (same duty as the case officer; the step records `done_by`). A document item: 422 "Only a form on this application is signed." There is no `sign-for-client` route (404).

**Order and refusals, in words.** "Signed by hand comes after "Printed": print IMM 5476 first." · "Signed scan received comes after "Signed by hand": mark IMM 5476 signed by hand first. Nothing was stored." · "Uploaded to IRCC comes after "Signed scan received": upload the signed scan of IMM 5476 first." · "Upload the signed scan…: that marks it received." (the step route refuses `scan_received`) · "…uploaded to IRCC only once its filing is Ready to file." · a step done twice: "Printed is already done for IMM 5476." Print with another form's copy, a garbage id, or no body: 409 naming what to do. An unknown step key: 404 listing the four steps. I set the filing to `READY_TO_FILE` by hand to walk the held half: the route answers 200, the prepare view shows the item `done` with the reason in words, a repeat is 409. So the code path C8.1-13 will need works, once C7.6 sets that value (see M3).

**Scan upload.** Type is judged by bytes: a `.pdf` name on text, HTML, `MZ` or SVG bytes: 422, nothing stored (row count and files on disk unchanged). Empty: 400. Over 20 MB: 413, nothing stored. Two files, a wrong field, or no body: refused, nothing stored. A scan sent before the steps are done is refused after the type check and leaves no file. Hostile name `../../../etc/passwd.pdf` is stored as `passwd.pdf`; the file is `cases/<case>/signed-scans/<uuid>.pdf`, named by the row id, so the name never reaches the path. The stored sha256 equals `sha256sum` of the file on disk. Audit lines exist for each step and the upload.

**Who signs vs SH3 R7.** `signersOf` calls `formSigners` from `engine/resolver.ts` and holds no copy of the `parent_for_minor`, `principal_for_family`, `none` logic (the pure check asserts this). Child's IMM 5257: `["parent"]`; adult: `["person"]`; IMM 5476: `["person","representative"]`. One exception, see M4.

**Concurrency.** Three simultaneous `print` posts: one 200, two 409, one row. Three simultaneous `signed`: same. Three simultaneous scan uploads: `[201, 409, 409]`, one `signed_scan` row, one file on disk (the two losers' files were removed; the transaction rolled the extra scan row back when the unique index refused the step). The partial unique index is what decides, and it holds.

## Findings
No Blocker. No Major.

* **M1 Minor** `api/src/main.ts:178-186` (outside this PR's file list): the global 413 filter has special wording for `/checklist-lines/…/documents` and `/validated` but not for `/items/:id/signed-scan`. A file over 20 MB is refused with "A file is larger than 25 MB. Nothing was added; add files up to 25 MB each." and a second file with "Add at most 20 files at a time." The limit here is 20 MB and one file. Status and "nothing stored" are right; the numbers are wrong. Fix: add a branch for `/items/[^/]+/signed-scan` worded like the C6.4 one ("The file is larger than 20 MB. Nothing was stored." / "Send one file at a time. Nothing was stored.").
* **M2 Minor** `api/src/sign-steps.ts:31-36` (`item()`): steps and a scan are accepted on any form item, including IMM 5257 (signature `TYPED_NAME`), where I posted `print` and got 200. The prepare view only acts on `HAND_SCANNED`, so no state is wrong, but the read shows four steps on a form that is not signed by hand and a scan can be filed against it. The concept is "a signed by hand and scanned line has the steps". Fix: refuse in words ("IMM 5257 is not signed by hand and scanned, so it has no signing steps.") when the item's current signature is not `HAND_SCANNED`, and return no `sign_steps` for it.
* **M3 Minor** `api/src/sign-steps.ts:66`: `item.filing.status === "READY_TO_FILE"` is a guess at a value nothing writes yet. The C7.6 pack says the status is `ready_to_file` (C7.6-19, lower case), and `Filing.status` today is stored upper case (`NOT_STARTED`, `engine/runtime/filings.ts:207`). If C7.6 stores the lower-case form, "Uploaded to IRCC" stays refused for ever and C8.1-13 will not turn green. Fix: one exported constant used by both lanes, or compare case-insensitively; say it in C7.6's first line.
* **M4 Minor** `engine/runtime/signing.ts:23-26`: for `person_and_representative` the representative is added by a literal check on the SIGNED_BY value, because the representative of record is not among the case's people. That repeats one branch of R7 outside the resolver, against "nothing here repeats it". Fix: pass the case team's representative to `formSigners` as a person with role `representative` (R7 already names them), and drop the special case. The pure check does not catch it because it only forbids the string `parent_for_minor`.
* **M5 Minor** Tests: the acceptance row proves the client 403 only. Nothing fails if firm scoping, the author refusal, the unique-index race, or the file removal on a refused scan is removed. Fix: add to `tests/check_c81_signing.ts` (or a small API check on the builder's port) an other-firm 404, an author 403, three parallel `print` posts giving one 200, and "no file and no row after a refused scan".
* **M6 Minor** `api/src/sign-steps.ts:30-31`: the item is looked up by id across all firms before `reach`, so an unknown id answers 404 "No such item.", another firm's item 404 "No such case.", and any client or author 403 for a real item. A person can tell whether an item id exists. The ids are random UUIDs, so the risk is low. Fix: answer the same 404 "No such item." in every case where the caller cannot reach it.
* **M7 Minor (note, no action)** The migration and schema comment say the file is "checked by its sha256 before it is read". No route reads a signed scan in this PR, so that check has nothing to attach to yet; C8.1-14 says nothing more. Keep the comment honest when the reader lands.
