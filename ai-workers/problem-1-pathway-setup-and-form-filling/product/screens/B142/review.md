## Issues, ranked
1. **Major (Must): a relative's or the application's value is judged against the wrong subject. A flagged CRITICAL warning is silently missed.** `engine/runtime/must-verify.ts:30` uses `f.about.split("/")[0]`, but a parent's answers are stored under `<person>/parent_1` (runtime.ts:349, resolver.ts:116), and an application fact has `about = "case"`, which no answer's `subjectId` equals. *Failing scenario (run on rev142):* the expert flags `person.date_of_birth` (v4 released). On Visitor visa, IMM 5645 writes `person.date_of_birth` for `<spouse>/parent_1` (MotherDOB). The client types the spouse's mother's date of birth and no one on staff checks it. **No must-verify line** appears for IMM 5645. I ran `unverifiedOf` on the real v4 snapshot: with the mother's DOB declared and the person's own DOB staff-entered it returns `[]`. The reverse case (mother's DOB verified, own DOB declared) returns a line on the mother's box. This breaks SA-1B-261 r7 and "duplicate beats a miss" (AG16-60). The same bug was fixed in out-of-date.ts and answer-sheet.ts ("the whole about", #926 / Review N1). *Fix:* match answers on the whole `about` (map `"case"` to the case participant, as knownOf's `about()` does), name the relative in the label, and add a pack step for a parent's value.
2. **Major (Must): a returned change leaves the author at a dead end, described in wrong words.** This is the expert's main alternate path. *Failing scenario (walked at 1440):* the author proposes on Full Name and the expert returns it. (a) The field page still enables "Propose: must verify before filing…" (`must-verify-panel.tsx:39` allows RETURNED). Send fails with 409 "…already **waits on To review**" (`must-verify.ts:66`), which is false. (b) "Open it" shows "Correct it and send it again" with the field's **Name** and **Meaning** inputs (`review-items.tsx:141` falls through to `<Correct>`). "Send again" is always refused ("withdraw it, then propose it again"). (c) The only way out is a red **"Withdraw the new field"** button on an existing shared field, so a person would hesitate. *Fix:* mirror the supplies branch: on `x.must_verify`, show a "Propose it again" notice and `<Withdraw label="Withdraw it" />`. On the field page, for RETURNED, say "withdraw it first" with the link instead of offering Propose. Make the 409 say "was returned: withdraw it first".
3. **Minor (Should):** answers of removed repeating rows are counted. `unverifiedOf` gets no `rows`, while knownOf skips them (case.ts:276, "a removed row's answers … are never read"). For a flagged fact in a group, the officer's Confirm section (which sees only live rows) cannot clear the line; it can only be passed. *Fix:* pass `rows` and skip answers whose `rowKey` is not live.
4. **Minor (Should):** the line key is a 48-bit unsalted SHA-256 prefix of the value. It is stored in `readiness_pass.keys` and in the audit `detail` (seen: `…|fef8a4bb9174`). A 9-character passport number is recoverable by brute force, against SA-1B-260 r9/r10 ("never the value"). *Fix:* key by the unverified answers' ids (a new version gives a new id).
5. **Minor (Should):** an author cannot withdraw a WAITING must-verify change from the UI (`review-items.tsx:155` lists only ADD/RENAME/form fields), and there is no UI for withdrawing an APPROVED one. The server supports both.
6. **Nit:** `case-prepare.ts:571` calls `formCoverage` uncached for every form and person, even with nothing flagged. Use `covOf(form, subject)` and return early when nothing is flagged. Prepare measured 0.35–0.55 s, so this is not over budget.
7. **Graph:** both `/library/fields/:key/must-verify` routes show `testedBy: []` in `qa/graph.json`, because the pack's template paths are not indexed. C7.9 is named by `tests/check_c79_must_verify.ts`. Informational.
