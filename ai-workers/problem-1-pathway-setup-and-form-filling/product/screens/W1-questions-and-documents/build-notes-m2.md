# Build notes, M2 queue (runtime lane): continued from build-notes.md, which is at its length limit

## Preview by person and by channel (M2 queue item 4; C4.3, C4.6; plan.md "Preview by person and by channel"; Lead answers 29 Oct)
* **Three sets per person (C4.3, board v2 frame 4):** `engine/runtime/preview.ts previewFamily` now returns `sets` (contract `PreviewSets` in `contracts/workspace.ts`):
  * **Pre-qualification:** the person's ticked questions (`prequalification(snapshot)`, the application's ticks with the principal), each with where it comes from; questions only, no verdict (P-77). A case officer's fact never shows, even when ticked.
  * **What the client is asked:** the shared renderer, with the new option below. Above it, the information line only (Lead Q1): "Passport … fills 10 answers", with the answers behind a disclosure. Upload, proposals and "please check" come with W5.
  * **Case officer's view:** every question for the person (agent mode), each with its source in words (Client, Case officer, Document · its name).
* **One count (journey item 8):** the person chip's number is now the case officer's view count, which equals that person's chip on the Questionnaires tab (146/111/12/15 on the sample). What the client is asked is the second number (`asked`) and the client set's heading.
* **Renderer option (Lead Q2):** `caseView(…, opts.skipDocumentFacts)` skips a fact a document supplies, and lists what it skipped in `from_documents` (`contracts/runtime.ts`, optional). Only Preview sets it now. Preview skips a fact when its source for that person's role is Document (W1-15, P-130), the document supplies it about this person, and the document is Needed (not Cannot tell yet) from the holder or the partner. Otherwise the question is the fallback and is asked. **It becomes the case default with M3's documents-first intake (C6.5).** A case pinned to an older release keeps asking these facts until then.
  * On the sample, every document-supplied fact is placed as `verified_document`, so the client view already left them out. The option changes the client view only for a client fact a document supplies; the check proves this on a changed copy.
* **Outputs per channel (C4.6):** each form carries `group`. A form filed for the application (its rule is about the case, e.g. IMM 5475, IMM 5476) is "Filed once for the application", shown with the principal. A `couple_once` form (IMM 5409) is "Filed once for the couple", shown with the spouse or partner. Every other form is grouped by its filing channel: "Filled on the portal (Online)", "Filled PDF to upload" or "PDF to print and sign". The channel comes from the forms lane's data (read only; `engine/channels.ts` and `forms.tsx` untouched).
* **Q3 (checked first):** on the sample, who each form applies to is right. IMM 5409 is `couple_once` with a SPOUSE rule and shows only under the spouse; children get no form in the largest family (IMM 5707 is 18+, IMM 1295 each applicant). The journey review's "a child gets all 7 forms" did not reproduce on Load sample, so there is no rules fault to report.
* **Screen:** `web/src/pages/workspace/preview.tsx`. At 1280 px and above the three sets sit side by side; below that, one set shows with a switch (`?set=pqr|agent`, the client's set by default) that is kept when the person changes. The case officer's list scrolls inside its card and is keyboard-focusable (axe scrollable-region). Documents and the grouped forms sit below.
* **Small engine addition:** `render.ts` checklist lines carry `document_type_key`, so a line is matched to a document type by key.
* **N-2 (S6 slice 1):** `acceptPqrPick(tx, actor, item)` takes the queue's transaction client. It writes the tick and its audit line through that client, so the item's status and the tick change together. It is exported for the lander registry. There was never a route or button of its own (unrouted since PQR part 1), so nothing else is dropped: the queue's Accept is the one Accept once 1c registers it. `check_pqr.ts` calls it inside a transaction and adds a rollback case (38/38).
