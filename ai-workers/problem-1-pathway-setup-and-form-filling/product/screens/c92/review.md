## Correctness: what holds (verified live)
* **Scope.** Only items that read the fact go Out of date. When the principal's family name changed, the principal's validated IMM 5257 and signed IMM 5476 went Out of date, and so did the spouse's validated IMM 5257 (it reads that name: "fills IMM 5257 for 2 people"). The spouse's signed IMM 5476 stayed Ready, because it does not read the name. Nothing goes Out of date before an item is finished: a print with no scan stayed To do after a change, and could be printed again (200).
* **Two entries for an out-of-date signed form.** One is the record, with the signed scan's own id, `item` and `record: "signed_scan"`. The other is the item itself, To do, with its own id and "A new signed IMM 5476 is needed". All ids are unique. `version` still comes from the stored rows (`versionOf`), so other writes are not made stale by the extra entry. An item already uploaded to IRCC stays a single Out of date entry.
* **Undo on the server.** It only adds rows: the current answer is superseded and a new row carries the earlier value, its status (VERIFIED), its verification and its source, plus a `restored` stamp. It takes the case row lock, and the `updateMany … supersededById: null` guard refuses a race (409). Refusals: client, reviewer and approver 403; another firm 404; no subjectId 400 on the field; unknown fact 404; a list entry 422; nothing to undo 409 with no row written; a declaration 403 (read in the code). Access is the same as the answer PUT (firm officers). The audit line carries no values.
* **Re-print supersedes the steps.** It runs only when a fact on the printed copy changed and the form is not yet uploaded to IRCC. It supersedes all steps in one transaction and keeps the scan. A print with nothing changed is still refused. A concurrent re-print hits the partial unique index (P2002 → 409).
* **Words** follow the contract: fact, person, old and new value, date. For example: "The validated copy of IMM 5257 read back 4 Nov 2026 is out of date: family name … of Sample Client W changed from "SAMPLE" to "SAMPLEWZ" on 4 Nov 2026. … or undo the change before filing." A change of representative names the date and each firm-record fact with its old and new value (BR-20).

## Issues, ranked
**M1 (Must, Major): the Undo button promises a value it does not restore.** The button reads "Undo: … back to SAMPLE", using `changes[].was`, the value the item read (`out-of-date.tsx:51`). The server restores `undoTarget`, the newest earlier value that differs (`out-of-date.ts:95`). Probe: SAMPLE was validated, then changed to VONE, then to VTWO. One Undo gave **VONE**, the items stayed Out of date, and the same "back to SAMPLE" button came back. Fix: the button and the server must name the same value. Either label it with the value Undo will actually restore, which the view can work out the same way, or let the request name the value the item read (optional fields beside the fixed `{subjectId, fact}`).
**M2 (Must, Major): no stale check from the screen** (STANDARDS §4 [M] optimistic concurrency; concept §6 "Every write carries a version (409 → Reload)"). The screen sends only `{subjectId, fact}` (`out-of-date.tsx:39`), and `changes[]` carries no answer id, so the server's optional `expectedId` is never used. Two officer tabs: tab 1 clicked Undo and SAMPLETAB went back to SAMPLE. Tab 2, still showing "back to SAMPLE", clicked and **re-applied SAMPLETAB** (rows: …, SAMPLE VERIFIED, SAMPLETAB VERIFIED current). Fix: put the current answer id in each change (`case-prepare.ts:224` `changeList`) and send it as `expectedId`. On 409, say "Reload" and refetch.
**M3 (Must, Major): axe fails on the new state** (STANDARDS [M] "axe-core on every screen state"; WCAG 2.5.3 Label in Name, level A). `label-content-name-mismatch` fires on all 3 Undo buttons at 1440 and at 400 px. The visible text "Undo: Family name (surname) as shown on passp… back to SAMPLE" is not inside the aria-label "Undo this change: put …". No suite runs a browser or axe check on this state. Fix: make the accessible name start with the visible words (or drop the aria-label and use `title` for the full text), and add a browser check with axe for the list.
**M4 (Must, Major): a raw key on the main path** (EXPERIENCE "no hashes, IDs … on the main path"; D10). The toast after Undo reads "Undone: **person.family_name** is back to its earlier value…" (`case-changes.ts:47,70`): `question_text` is null for this fact, so the key is shown. The 409 "…has no earlier value" message does the same. Fix: use the label chain the Prepare view already uses (question label → placement text → meaning).
**S1 (Should): Undo is offered where the server always refuses.** `changeList` sets `undo` only by `about !== REPRESENTATIVE`. A changed list entry (server 422, `case-changes.ts:46`) or a client's declaration (403, l. 45) therefore gets a button that always fails. Fix: `undo: false` for `per_row` and declaration facts. I read this in the code; I did not reproduce it live.
**S2 (Should): sideways scroll at 400 px.** The Undo button keeps the shared `whitespace-nowrap` and overflows its card (scrollWidth 487 at a 400 px window). The same case with no list scrolls 0. 1024 px and 200 % zoom (720 CSS px) are fine. Fix: let the button wrap (`whitespace-normal`, `h-auto`) or shorten its words.
**S3 (Should): focus is lost after Undo.** When the list unmounts, `document.activeElement` is BODY. Fix: move focus to the "Prepare application" heading, or to the next Undo button.
**S4 (Should): the scope rule's test cannot fail** (STANDARDS [M] "a rule's test fails when the rule is removed"). In the pack, -7's spouse IMM 5257 is never finished, so it passes whatever the scope logic does, and its premise is wrong (the spouse's IMM 5257 does read the principal's family name). Fix: in `check_c92_undo_api.ts`, a finished item that does not read the fact (the spouse's signed IMM 5476) stays Ready. Tech lead: correct -7's premise.
**S5 (Should, words):** the reason uses the full question text ("family name (surname) as shown on passport or travel document of …"), where the concept §5 has the short form ("date of marriage changed on 29 Oct"). Prefer the fact's short meaning.
