# Workflow — roles, two stage paths, layered checks; nobody marks their own homework

## Roles
| Role | Where | Does | Never |
|---|---|---|---|
| **Founder** (product owner; RCIC reviewer for now, P-17) | The Lead chat only (`/lead`) | Decides product choices (one question at a time, recommendation first), walks built screens as author and RCIC, approves paid AI and installs | Relays work between agents |
| **Lead** (Claude Code in the main copy, skill `lead`) | `/lead` | Designs (`screen-concept`, helped by the `screen-designer` agent), answers challenges, runs every lane session, checks on the exact commit, merges (standing OK), records decisions, requests and state | Edits app code or a lane's files |
| **Builder** (Claude Code in a lane copy, `LANES.md`) | `/next <lane>` | Challenges, builds, tests, launches reviewer and breaker, fixes, commits each stage on its branch | Builds before agreement; edits rules, skills or Lead files (stop hook refuses); pushes anything but its own lane branch (push guard gates) |
| **Reviewer / Breaker** (fresh agents launched by the builder) | `.claude/agents/` | Score (the one journey score per check) and attack | Fix anything; ask for new features |
| **Tester** (qa lane, skill `qa`) | `/qa <mode>` | Tests what is on `main` like a person and underneath; coverage; bugs, questions, suggestions | Fix app code; build suggestions |

## The loop
A lane does one stage, commits, updates `lanes/<lane>.md` and ends with one **Paste to Lead** block; it reaches the Lead by itself (the Lead started the session). The Lead checks, records, writes the lane's **"From the Lead"** note and continues the lane. State lives in files (`lanes/*.md`; `STATE.md` is generated by `lane.sh state`), never in chat. Parallel lanes, guards, ports and file ownership: `LANES.md`.

## How we work: see it, agree it, build it, show it early (P-36, P-42)
* **Design first.** Every screen is a clickable board (team look, real Sample data; `design/journey-v2.dc.html`) plus a one-page `concept.md`; the builder's short feasibility challenge comes before the founder agrees. The Lead designs N+1 while N is built; the `screen-designer` agent drafts, the Lead decides.
* **Definition of Ready** (all true before any code): board or plan agreed · every element labelled Needed for the proof / Not built and Capability / Scaffolding · data and API needs known · every decision it relies on agreed by the founder · no open questions.
* **The board is intent, not pixels (P-44).** Flow, structure, words and behaviours are fixed; details improve with the team's components; deviations listed at EARLY-LOOK; flow, scope or wording changes are proposed, not applied.
* **Show early; change control; stop the line.** First slice shown before tests and polish; a change after READY goes to the board first; anyone who sees it going wrong says so and the builder pauses at the next safe point.
* **Demo and retro.** Each screen ends with the founder's walkthrough and a 5-line retro in `RETRO.md` (at most one workflow change).

## Two stage paths (the lane file holds the current stage)
**Screen path** (anything with a page the founder will see):
| Stage | Owner | Output | Exit |
|---|---|---|---|
| DESIGN | Lead (+ builder challenge) | board, `concept.md`, `challenge.md` | Founder clicks through and agrees → READY |
| READY | Lead | Definition of Ready ticked | → BUILD |
| BUILD | Builder | slice 1: real data, main path, screenshots | → EARLY-LOOK |
| EARLY-LOOK | Founder + Lead | Go, or board changes; meanwhile the lane re-checks or challenges its next item, no code, no merge (P-126) | Go → FINISH |
| FINISH | Builder | all states, a pass and a fail test per rule, scripted journeys, axe, build-notes | → CHECK |
| CHECK | Reviewer + breaker, then Lead | `review.md` (journey score), `break-report.md`, `lead-check.md` (suites rerun on the exact commit) | Clean → DEMO, else FIX |
| FIX | Builder | fixes + a test per break (incl. qa bugs for the lane) | → CHECK |
| DEMO | Founder with Lead | walkthrough in `lead-check.md`; retro | Accept → DONE → MERGE, else FIX |
| DONE / MERGE | Lead | merge into `main`; `/qa after-merge` | Next item |
**Backend path** (P-68; slices with no new page: forms, runtime backend, evidence): PLAN → BUILD → CHECK → FIX → MERGE. PLAN = `plan.md` with a fresh agent's challenge, back-end table, team-model mapping, slices; Lead agrees. BUILD = the whole slice, a pass and a fail test per rule, a scripted API journey. CHECK = reviewer and breaker on contracts, data, migrations, roles, concurrency and hostile files, then the Lead reruns the suites on the exact commit and reads the diff. MERGE after the Lead check. The founder sees it at the first screen that shows it, and decides any product change on the way. Every check of the screen path stays except screenshots of a page that does not exist.

## Milestone gate — no scope cuts, no blind progression (P-54, P-55)
Milestones sequence the full journey in `PRODUCT.md`; they never reduce it. Before the next milestone starts, the current one passes all of these:
1. Each in-scope capability (`qa/CAPABILITIES.md`) works end to end for its user; no scaffolding presented as capability.
2. Scripted checks and a browser walkthrough cover main, alternate, empty, error, permission and recovery states; accessibility and screen sizes on every affected screen.
3. The qa lane's `/qa milestone` report: no open Blocker or Critical, coverage at or above the floor, every suite green on the exact commit; reviewer and breaker findings fixed and rechecked.
4. Every applicable `QUALITY.md` dimension at least 4/5 with evidence, no averaging; D17 and D20 at least 4/5 from an intended user's unaided walkthrough (never self-awarded).
5. The founder walks the milestone (author and reviewer roles for M2) and accepts it; the outcome and the next milestone go in `STATE.md`.
At a milestone boundary report the gate evidence and stop; never start the next milestone silently. The thin slice (P-67) proves direction early; it does not pass M3's gate.

## Checks — layered and independent
1. Concept or plan: a fresh challenger agent, then the builder's challenge.
2. Build: the builder's tests and scripted journeys; a fresh reviewer (D1–D20 + the journey score) and a fresh breaker.
3. Lead check on the exact commit against concept, `STANDARDS.md`, `EXPERIENCE.md`.
4. The qa lane on `main` after every merge and at every gate: human-style tests, data underneath, coverage.
5. The founder's walkthrough, not optional: the AI checkers share blind spots.
Checkers flag correctness gaps, standard violations and concept mismatches only; over-engineering is a defect too. **Scope test (P-26):** every objection, finding, suggestion and feature is *Needed for the proof* or *Not built*; agreed full-journey scope stays scheduled in its milestone.

## Capability or scaffolding (P-33) — label everything
**Capability** = what the product does in production for its users. **Scaffolding** = setup, seeding, Sample data, test inputs, dev tools, replayed AI answers. Scaffolding is never shown as capability, never ported, never replaces the capability's path in a demo. Test: "In production, who does this, and on which screen?"

## Keeping files true
* **One home per fact** (`PRODUCT.md` §6); other files link, never restate. Status lives only in lane files; decisions only in `DECISIONS.md` (+ `decisions/`); requests point to the decision.
* **Every founder request** goes into `REQUESTS.md` the same day; every product decision into `DECISIONS.md` **and, the same day, into capability rows (or the backlog), the owning lane's note and the Programme map (P-74; `tools/decision-impact.sh` must pass).** Logs keep 10 lines; older lines move to `history/`.
* **Small and current:** rules files under 100 lines and 12 KB, skills and agents under 7 KB (`tools/check-docs.sh`, in the stop hook).
* New asks during a build are logged and scheduled for the next item, not squeezed into the current one. No revision manifests or hash handoffs for routine work: git and the snapshot hook keep the history.
* AI runs state their cost first and stay inside the caps (`PRODUCT.md` §5). Team sources are checked for freshness at challenge time (`ai-workers/tools/freshness.sh`).
