## 0. Principles (the page's contract)
1. **Management by exception.** Everything quiet and green unless a limit breaks; every limit is written here (§7). Two minutes to read when all is green.
2. **No new tabs.** Additions live inside the existing strip, Overview, Factory and Capabilities (P-595 layout stays).
3. **Every number shows its source and "as of" time** (hover or small print). A missing input shows **"not measured"** with the reason, never a guess, a default or a carried-over value (A62).
4. **Thin data is labelled thin** (fewer than 5 days or fewer than 10 events behind a rate): the number shows with a "thin data" mark, and no colour stronger than amber.
5. Built only from `tools/cockpit-data.py` output + hand-kept JSON (`plan.json`, `risks.json`, `lead-input.json`). The page computes nothing (P-591).

## 1. Overview: Plan and pace (frameworks: burn-up with forecast; flow metrics, ProKanban / Vacanti "Actionable Agile Metrics")
**Unit:** a Release 1 Build row of `MVP-CHECKLIST.md` (scope = Build rows, baseline 101, P-586). Two counts per day: **built** (its PR merged to `main`) and **proven** (qa Works on main, P-592).
* **Burn-up chart** (one small SVG): x = days from 13 Nov to the plan date; lines = scope (Build rows total, changes visible as steps), built cumulative, proven cumulative; a dashed forecast line from today at the last-7-day built rate to where it meets scope.
* **Pace line** (one sentence + light): "Need **R** rows a day to finish by **<plan date>**; last 7 days we built **A** a day (proven **P** a day) → forecast **<date>**."
  * R = (scope − built) / working days left to `plan.json` H1 `date` (calendar days; the plan has no non-working days).
  * A = rows built in the last 7 full IST days / 7. P likewise for proven.
  * Forecast = today + (scope − built) / A days; "not measured" when A = 0 or fewer than 5 days of history.
  * Light: green forecast ≤ plan date; amber ≤ plan date + 7 days or thin data; red later.
* **Roadmap timeline:** the existing plan section shows `plan.json` dates as a horizontal timeline by module (high and mid level), committed vs forecast styled differently, today marked. No new data.

## 2. Overview: Capacity and parallel use (Little's Law: throughput = WIP / cycle time)
One line + light: "**L** lanes working · **Q** rows ready with nobody on them · **B** ready but held by a baton or dependency · we could add **min(Q, room)** lanes now."
* L = sessions in `team.sessions` with state running whose last push is under 90 min (P-326). A session over 90 min quiet counts as **idle**, listed.
* Q = BACKLOG rows marked ready (brief exists or status Ready), no owner in Owners, no open PR, dependencies merged.
* B = ready rows waiting on a baton (`schema.prisma`, `case-prepare.ts`, P-438 (2)) or an unmerged dependency.
* room = Mac preflight caps (≤ 2 Mac builders) for Mac work; cloud has no cap besides P-462 independence.
* Cycle time = median days from a row's first commit to merge, last 14 days; WIP = open app PRs. Shown small under the line.
* **Sizes:** counts of S / M / L where BACKLOG rows carry a size; the rest "unsized N". No invented sizes.
* Light: green when Q = 0 or every ready row has a lane; amber when Q ≥ 1 and an idle lane exists or Q ≥ 2; red when Q ≥ 3 for over 2 checks.
* "Enough lanes for 20 capabilities in 5 days?" is answered by the pace line (R vs A), not by a separate widget.

## 6. A62: data trust (DAMA data-quality dimensions: accuracy, completeness, consistency, timeliness, validity; dbt / Great Expectations style tests; data-observability pillars: freshness, volume, schema, lineage)
1. **Data contract:** `cockpit/data.schema.json` (JSON Schema, `jsonschema` 4.26 already installed). `cockpit-data.py` validates its output against it and exits non-zero on a violation; the page is not republished on a non-zero exit.
2. **Lineage:** every displayed number is a `V(value, src, as_of)` object; the schema requires `src` and `as_of`; `value: null` requires `reason`.
3. **Unit tests** `tools/test_cockpit_data.py` (pytest-free `unittest`, stdlib): frozen fixture inputs under `tools/fixtures/cockpit/` (BACKLOG and CAPABILITIES excerpts, GitHub JSON) with **hand-worked expected numbers** for every formula in §1-§5 (pace, forecast, capacity, health, Works count, the 93/98 fix); edge cases: zero history, missing lead input, stale input, duplicate rows, a row in two states.
4. **Independent reconciliation:** `tools/cockpit-reconcile.py`, written by a **different agent from this spec only, without reading `cockpit-data.py`**, recomputes from raw sources: Works on main (M2+M3+M4+T), R1 rows built and proven, open app PRs, R and A, lanes working, ready rows. It compares with `data.json`; any difference → `data.json.trust = {status:"mismatch", items:[...]}` and the page shows a red **"Numbers not checked: <which>"** banner above the strip. Tolerance: exact for counts; ±0.05 for rates.
5. **Formula sheet** `cockpit/FORMULAS.md`: each number, formula, source, threshold, owner. A fresh reviewer audits it against the sources before each version is published, and weekly (P-591).
6. **Freshness:** each source's age shown; over its limit (GitHub data 1 h, lead input 2 h, flow-measure 6 h) → amber and listed in Health item 7.
7. **CI:** a workflow runs the unit tests and the reconciliation on fixtures when `tools/cockpit-*`, `tools/test_cockpit_data.py`, `tools/fixtures/cockpit/**` or `cockpit/**` change (path filter; Linux; minutes kept low, P-528/B190). The Lead reads the `.github/` diff before labelling (P-423).
8. **Known fixes in this change:** proof count 93/97 → 93/98 (progress.sh omits M4); Needs you must not list asks already decided.
