# Module card: api-cases (P-615)
The runtime: a client's case on a released combination, from answers to a recorded submission. Read this before editing these files; update it in the same PR when an entry point, invariant, table or test below changes (or say `Card unchanged: <reason>` in the PR body).

**Purpose.** `runtime.ts` creates and reads cases, people and answers; `clients.ts` the case's client record (CS-K1); `case-count.ts` the firm's active-case count (`CaseCountPort`, `ports/case-count.ts`) for the plan limits (`EntitlementPort`, `ports/entitlement.ts`: PF-15's, the allow-all fake bound until PF-15); `case-*.ts` stages, checklist, documents, filings, changes and the Prepare view; `fill-case.ts` the case's forms; `readiness*.ts` Ready to file; `review-rounds.ts`/`review-runs.ts` the representative's review; `sign-steps.ts` signed PDFs; `submission*.ts` recording the submission; `person-link.ts` adult privacy and links (since PF-19r its link and code emails go through MessagePort for the case's platform firm, with a `demo_message` copy only after a QUEUED answer); `release-update.ts` adopting a newer release; `stage-scope.ts`/`routes-data.ts` multi-stage cases.
**Owner area.** runtime lane, with screens for B138, B144 (Unconfirmed: no lane map in code).
**Entry points.** all under `/api/runtime`: `GET|POST cases`, `GET cases/:id/stages`, `GET cases/:id/checklist`, `POST cases/:id/documents`, `GET cases/:id/prepare`, `GET cases/:id/forms`, `POST filings/:id/ready`, `POST cases/:id/reviews`, `POST items/:id/sign-steps/:key`, `PATCH groups/:gid/record`, `GET|POST cases/:id/release-update`; behind PF-4's guard (staff session and keys, not `x-actor`): `POST cases/:id/{decisions,withdraw,close,reopen}` (`case-close.ts`, CS-C1a), `GET clients`, `GET clients/:id` (`clients.ts`, CS-K1).

**Invariants (set by).**
- A case is pinned to its release; every read uses the pinned release, never the newest (P-67, STANDARDS §3.7).
- One current answer per person per fact, append-only; deny by default by duty (P-72).
- A declaration is always the client's own; the officer never makes or restores one (P-97, P-130).
- A form is filled from declared and confirmed answers through `fill.ts`, never overwritten (P-242, P-411, P-65).
- An identity document is read by a person, never by AI; other reads replay saved runs only (P-134, P-175, P-295).
- The representative reviews a filing before it is recorded (P-155 (1), P-412).
- The only hard stop on Ready to file is a barcode form failing its own Validate; the rest are warnings passed with a reason (P-237).
- A never-waivable line cannot be marked Not applicable (P-172); a line of an ended stage is history (P-444).
- A case reads only its current stage's pins and rows (B139).
- A stage deadline is the calendar date its rule gives, never moved by hours or closed days; the view adds its weekday, "(weekend)" / "(closed day)" and Missed (before today in the firm's zone, clock port), from `platform/calendar/` (CS-DL1 part 1; AG-7-94, AG-7-96 r2). Only a cited route reminds (`case-deadlines/`, part 2): keyed jobs `deadline:<case>:<stage>:<offset>:<date>:<run time>:r<reopens>` counted back over open days, cancelled by `case.closed` and armed again by `case.reopened` (read from the outbox by the sweep); a job whose key today's state and calendar no longer give, whose day has passed or whose firm is not the case's tells nobody (AG-13-14, -15).
- A case is OPEN or CLOSED; a decision needs a recorded submission, `case_decision` is insert-only, close and reopen need a reason and write `case.closed`/`case.reopened` in the same transaction (CS-C1a; AG-7-33, -34, -13, -50).
- An opening checks the plan limit in its own transaction: a per-firm advisory lock, the active count by group, then `EntitlementPort.check`, all before the case number is taken; a refusal is 409 `PLAN_LIMIT_REACHED` and writes nothing (CS-C1b; SA-3-4, -39, -47; P-588 (3)). Active: OPEN and not every active filing decided since the last reopen; the group is the Pathway's client type (CORPORATE, else individual).
- `case_party_index` (area file `case-search.prisma`, CS-S1 part 1) holds one row per participant, kept only by database triggers on the answer, profile and participant tables. No answer-write site writes it. A relative is never indexed, and neither is an employer without a name. A row's id is stable per person. Its firm comes from the case (contract v0.1 §3.1; AG-7-88).
- A won prospect makes one client (FO-8, `case-clients/prospect-won.ts`): `onProspectWon` is idempotent on the prospect id (an advisory lock, then the unique key), writes the client, one audit line and `client.created` last in one transaction, and opens nothing. The "Open a case?" offer is no table: it is that client while it has no case, read from the prospect's newest `prospect.won` in `module_event`, withdrawn while a later `prospect.unconverted` stands; `openCaseFromOffer` opens through `createCase(…, inTx)` and writes `case.opened` in the opening's transaction. While the app runs, `case-clients/live.ts` (CS-K1 part 2) runs the catch-up at start and every `PROSPECT_WON_POLL_MS` (Sample 10 s), single-flight, listing on the one bypass use `cases.prospect-won.catch-up` and making each client as its own firm.
- Every case has a client (`runtime_case.client_id` NOT NULL, CS-K1 part 1; contract §5): a `case_client` of the same workspace and firm, matched by `(client_id, workspace_id, firm_key)` and by `(client_id, firm_id)`. The opening reuses a client of the opener's firm or makes one named after the principal (`clients.ts newClient`, after the limit check, in the opening's transaction); a case written straight to the table gets one from the database (`case_client_for_case`, ENABLE ALWAYS: for fixtures and restores only; application code always passes a client, so a code path that forgets it is not caught by NOT NULL — test it); the client follows its case when CS-W1's backfill fills the firm id (`case_client_follow_firm`). Client numbers are per firm from `case_client_counter` ("Client code" `CL-00001`), never reused. COMPANY when the Pathway is CORPORATE, else PERSON. No foreign key into the front office; every client of a platform firm is linked to its party through FoPersonPort (CS-K1 part 2): a new one in the opening's transaction (`newClient`), existing ones by the job `case_clients.link` (`case-clients/client-link.ts`); `case_client_front_office_link_check` (PERSON → `fo_person_id`, COMPANY → `fo_company_id`) refuses any other row unless `fo_link_pending`, which only the two triggers above set (`case_client_pending_guard`). The opening runs as the opener's platform firm (`withFirm`, CS-W1's lookup). Another firm's client is 404, on the routes and as `clientId` at opening.
- A case's platform firm is `firm_id` (`platform_firm.id`) beside `firm_key` on `runtime_case`, `case_stage` and `firm_case_counter`, filled only by the database (triggers `case_firm_from_key`, `case_firm_fill`; the one lookup `case_lookup.case_firm_id_of_key`, `firms.ts` `firmIdByKey`); a firm id that is not the key's (or the case's) is refused. Nullable until CS-W1 part 2, which also switches the identity comparisons from `firm_key` (CS-W1 part 1). Every case-side request runs as its own firm (CS-W3 part 1): `features/case-firm-door.ts` tags `/api/runtime/*` (staff: their firm; a simulated client: the case in the path, else their cases' one firm, two firms 409) and `/api/link/*` (open, code/send and code by the body token's case; every other link route by the session's) through the four `case_lookup.case_firm_of_*` definer lookups, never reads a firm the caller typed, never overwrites a firm already set (404), and refuses a case list with no firm (403).

**Tables.** case, caseParticipant, caseTeamMember, clientCanonicalAnswer, filing, filingItem, formInstance, caseDocument, answerCheck, reviewRoundFiling, reviewFinding, personLink, caseDecision, caseClient, caseClientCounter (case_client_next_number only), casePartyIndex (triggers only), moduleEvent, auditEvent.
**Tests.** `tests/check_c76_readiness.ts`, `tests/check_c65_document_rules.ts`, `tests/check_m3s4_never_waivable.ts`, `tests/check_c95_release_update.ts`, `tests/check_c81_signing.ts`, `tests/check_a24_case_number_api.ts`, `tests/check_csw1_firm_id.ts`, `tests/check_csc1_close.ts`, `tests/check_csc1_count.ts`, `tests/check_csk1_client.ts`, `tests/check_css1_index.ts`.
**Row lists (P-712).** Never hand-edit this card's frozen `Tests.`, `Tables.` or `Entry points.` line: put your row's items in `MODULE.cases.rows/<ROW>.md` next to it (one file per row; `module-cards.py` fails the PR otherwise).

**Do not.**
- Read the newest release from a case route.
- Send an identity document to AI, or make a live read.
- Edit an answer in place; append a new one.
- Write `case_party_index` from application code; the triggers keep it.
- Record a filing the representative has not reviewed.
