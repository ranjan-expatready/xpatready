## 1. The rule this follows (D220)

D220: design best in class per capability; the team's stack is evidence of what exists, not a constraint. For Problem 1, D220 says the AI skills run:

- in the product's language: **TypeScript today** (`ERv2-sanitized`: pnpm workspace, Node ≥ 24);
- with the provider SDK, typed outputs and tool calls into a draft;
- with an evaluation set per skill and versioned prompts.

PDF and XFA filling use the strongest library for the job, in a small separate service if that library is Java or .NET. One runtime per concern. D147 and D139 are unchanged.

**Model calls and D147:** at P0 no exception existed (D257) and P2 waited for a compliant route. The founder then recorded a **prototype-only exception (AIW-D260)**: P2 prompts may contain only the hashed public official forms and their read-only P1 inventories, never client data, the made-up family's values or the answer keys, and drafted output carries the D260 label. **AIW-D261** sets the route: the Anthropic API through `@anthropic-ai/sdk` with the founder's key file (`.tools/solution-1-prototype/secrets/anthropic.env`), about US$15–40 for the comparison and US$5 per run. **Production stays on a commercial D147 route.** Enforcement is on one launch path, not in the schemas (revision P1-4, answering P1R2-M2): `p2/launch.ts` admits the job's route and inputs (`p2/guard.ts`: manifest-listed, hash-checked official files and their inventories only; one route, model and budget), screens the maker-written template and output schema against the answer key and family values, and starts `p2/draft.ts` under Node's permission model with the hashes of the screened text. `draft.ts` first checks its own isolation (it cannot read `expected/` or the family files, write outside the spend ledger, or start processes; `p2/isolation.ts`), refuses text other than the screened bytes, builds the request with the one fixed builder (`p2/prompt.ts`) and uses the one experiment ledger at the fixed US$40 cap (`p2/ledger.ts`; each attempt's worst case, retries included, is reserved before the call). The paid caller refuses to exist outside that process and refuses any other ledger (`p2/runner.ts`); a live call needs a recorded stub pass of the same launch-path code. Executed here with a stub caller, no network and no key: `tests/check_p2_launch.ts` 21/21 (including the reviewer's case: a template carrying a family value is refused before any process starts) and `tests/check_p2_guard.ts` 36/36. **R4-M1 (20 Oct 2026):** a hash proves identity, not screening, so `draft.ts` no longer relies on the hashes it is given. It screens, itself, the template, the schema, every reused AI draft and the finished request against a salted-hash digest the launcher writes before each run (`p2/screen.ts`; the plain strings stay unreadable to it). It also checks the live stub gate itself (`p2/pathcode.ts`), and a paid call refuses an unscreened request. Started directly with the true hashes of a leaky template, it now refuses: `tests/check_p2_launch.ts` 32/32, `tests/check_p2_guard.ts` 46/46. This is a contamination guard for our own code and files, not a privacy classifier or an operating-system sandbox. Inside the isolated process the ledger line is written without fsync, because the permission model disables fsync: it survives a crash of the drafting process, not a power loss. No AI call has been made. `p2/check_route.ts` shows only that the key works and the model is listed; it is not a retention or policy qualification. P0 and P1 make no AI calls.

## 3. Portable configuration contracts (to define in P1–P2, before code)

JSON Schema files under `prototype/contracts/`, versioned:

1. `combination-config` (draft and released): canonical fields with person and relationship, sections, documents, form field maps (form edition, field ID, person, relationship, row, transform), collection settings (Client or Case officer, D8 row), conditions, checks with severity per D253, and a citation per item.
2. `release-record`: configuration hash, reviewer decisions, author, submitter, approver and (optional) publisher; the author or the submitter never approves or publishes, whatever their role, the Platform Owner included (D254).
3. `case-facts`: one stored value per fact, with provenance, status and confirmation history (D251), plus form-only corrections and their reason (D252).
4. `expected-answers`: already in use, `expected/*.json` (schema `expected-answers/v0`).

Contracts carry no language-specific types, so a Java or .NET filling service, the TypeScript engine and the team's product can all read them.

### 6.3 Recommendation and its limits

- **Simplest eligible approach (baseline): A.** It meets AIW-D220 as written (product language, provider SDK, typed outputs), fits the team's adapter rule, and leaves state, review and recovery to mechanisms the product already has. **Not yet shown:** that it maps the slice accurately. That needs the AI route and the comparison (§7).
- **Strongest justified challenger: C (LangGraph TypeScript with the Postgres checkpointer).** It is the only candidate whose documented features target requirements the baseline leaves to our code: pause for human review, resume after a stop, durable checkpoints. If those features let us drop custom code without a second state store causing conflicts, C wins on those requirements.
- **B is not the challenger:** structured output is equal; its main extra is switching across providers, and the Anthropic SDK already has clients for the Anthropic API, Bedrock, Vertex and Foundry. B becomes the challenger only if the founder wants non-Anthropic models. Its two-week-old major version is a churn risk.
- **D is not in this bounded comparison, by scope, not by eligibility.** Anthropic documents it for production agents ("Build production AI agents with Claude Code as a library"), with structured output and production hosting guidance (`code.claude.com/docs/en/agent-sdk/overview`, `…/structured-outputs`, `…/hosting`). For one bounded mapping call its agent loop, built-in file, shell and web tools and its own session files are unnecessary breadth beside the product's tables, so the comparison stays A versus C. D can be reconsidered for a multi-step capability such as a co-pilot.
- **Material challenge answered (Codex M1):** "TypeScript direct SDK" is no longer stated as the winner; it is the baseline a measured challenger must beat. **(M2):** the selection uses one shared slice with the same model, prompt, inputs and budgets (§7), and every trial is kept. **(P1R2-M4):** orchestration is compared with replayed identical model responses on equivalent durable storage; model quality is measured separately with repeated live trials; model choice is not part of the orchestration test. **(M3):** the smallest slice and the reusable contracts exist now (§7, `contracts/`).
- **AIW-D220 reconciled:** "best in class per capability" is applied to the capability that is actually open, durable review and recovery, by testing C there. Developer reuse favours A: same Zod and TypeScript versions, the existing adapter and draft/outbox seams.
- **Future AI capabilities (not proven here):** document reading into confirmed facts (module 1, README rule 1) has the same shape: typed output, a source quote per item, "unresolved" instead of a guess, and a human confirms. It can reuse the adapter, contracts and run record. A conversational co-pilot would need a tool loop (the same SDK's tool runner). One slice does not prove either; parked Problem 2 is not started.
