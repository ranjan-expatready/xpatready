# P1 report: combination 1's real forms, and can we write into them?

19 October 2026 · Claude Code (the Lead) · AIW-D246 P1, under AIW-D257–D259. Read-only on the official files (now in `official-sources/ircc/`); every write was on copies, kept in `prototype/p1/runs/` and `prototype/p1/adobe-test/`. Legal: Unconfirmed: no counsel (AIW-D94). **Updated 19 Oct evening:** inventory fix (468 boxes), Adobe test results (§4), folders reorganised at the founder's request. **Revision 3 (19 Oct, after review):** barcode comparison by position from the form's own manifests (§4).

## In plain words

- **We now know every box on combination 1's seven form editions**: 468 data boxes across 7 forms, each tied to the exact place the form stores its data. Every one of the 468 matches a place the form itself ships, so the map is the form's own, not a guess.
- **The forms hide traps a mapper must handle**: the same fact is coded differently on different forms; two parent blocks both say "mother or father"; children are a repeating row that starts empty; date of birth sits in a different position for parents than for the applicant. These are now test cases (the comparison slice).
- **Writing data into the forms works at file level, but not with the library we installed, as shipped.** A full rewrite reads back perfectly but destroys IRCC's usage-rights signature. pypdf's append-only mode keeps the signature but writes data nobody can read, because pypdf does not encrypt what it appends. A small correction of about 25 lines (encrypt with the document's own key, carry the encryption entry) works on all seven forms: every value reads back, through a second decryptor written from the PDF specification; the original bytes stay untouched; both IRCC signatures still verify.
- **Proved in Adobe (§4):** the values show in the right boxes, IRCC's certification stays recognised, the form's own Validate passes on a complete IMM 1295, and the barcodes it makes match the saved data box by box (186 positions). Not yet: portal upload, Windows, the other five forms in Adobe.

## 2. Experiment E5: write and read back (actual)

Setup: pypdf 6.19.0, cryptography 49.0.0 (hash-locked, AIW-D259), OpenSSL 3.6.0, poppler; run `e5-20261019T165914Z`. Two value sets: **generic** (every data box gets a distinct test value, repeating rows two deep) on all 7 forms, and **family** (the made-up family; given names name the person, so a wrong-person write is visible) on IMM 5707 and IMM 1295. 9 value sets × 3 methods = 27 outputs.

| Method | Read back (pypdf) | Read back (independent decryptor) | Original bytes kept | UR3 / DocMDP verify | poppler | Encrypted |
|---|---|---|---|---|---|---|
| Full rewrite (pypdf) | 587 / 587 | n/a (unencrypted) | No | **Broken** | 0 errors | **No** |
| Append-only (pypdf as shipped) | **0**: data unreadable | **fails** (not encrypted) | Yes | verify | **3–737 errors** per file | trailer lacks `/Encrypt` |
| Append-only, diagnostic correction | 587 / 587 | **587 / 587** | Yes | **verify** | 0 errors | Yes |

Also checked for every successful output: the form's template, configuration and other parts byte-identical; no other data value changed; the appended update holds exactly two objects (the new data stream and its cross-reference stream). Full-rewrite and as-shipped outputs are byte-identical across runs; diagnostic outputs differ only by their random AES initialisation vector. The R2 fallback data file (`*.r2-data.xml`) was produced for every value set.

The independent read-back (`e5_independent_readback.py`) derives the key from the PDF specification (ISO 32000-1 Algorithm 2) and decrypts with `cryptography`'s AES and zlib; it uses pypdf only to find object numbers and the unchanged encryption parameters.

## 4. Adobe test (actual, 19 Oct 2026; copies and evidence in `adobe-test/`)

Software: Adobe Acrobat Reader 26.001.21662 (Homebrew, Adobe-signed and notarized; licence accepted on the founder's instruction), which Adobe's own updater migrated mid-test to **Adobe Acrobat 26.002.22031 in free Reader mode**. macOS on Apple silicon.

| Check | Result |
|---|---|
| IMM 5707, family copy (corrected append) | All values in the right boxes; codes shown as labels (Common-law, Married, Daughter, Single); spouse block shown by the form's own condition; the appended child row rendered (plus the form's 3 empty default rows). Validate: no message (form has no mandatory boxes) |
| IMM 1295, family copy | Values shown; **IRCC certification banner** ("Certified by Immigration, Refugees and Citizenship Canada … You can save data typed into this form"); no change warning; Validate runs and stops at the first empty mandatory box (the family set is partial) |
| IMM 1295, complete synthetic set | Six iterations against the form's own messages (v1→v6): telephone goes in the international number box (the full number is calculated); intended city is a **code from a province-dependent list** (Toronto = 3812 under ON); address; offer-of-employment number. **v6: "Validation completed successfully"**, barcode page added (5 → 6 pages), five PDF417 barcodes generated |
| Barcodes decoded (`decode_barcodes.py`, zxing-cpp 3.1.1) and compared by position (`barcode_positions.py`, revision 3) | 5 of 5 decoded. The form's own barcode1–5 manifests list 186 boxes (61/46/37/13/29), all bound to data boxes through the inventory; slot by slot against the data Adobe saved: **180 exact, 6 months without the leading zero, 0 differences**. Of the 91 values written: 81 at their own slot; 5 feed calculated slots by the form's rules (three full dates split into hidden year/month/day boxes; country code and number into the full phone number +919800000000); 1 cleared by the form's own rule ("language most at ease" applies only when the person speaks both English and French); 2 telephone-format switches are not encoded; 2 answers are not in any manifest (Question 2 A other names yes/no; Question 6 background). Barcode 5 records `Reader.26.00222031.Full.MAC…ENU-09-2023`. *Corrects revision 2's value-membership count ("80 of 91 exact; 7 in the form's own format"), which credited values from unrelated slots; that file is kept in `adobe-test/evidence/superseded/`* |
| After Adobe's own save | Official bytes still a prefix; **DocMDP and UR3 still verify**; ApplicationValidatedFlag = Yes; 90 of 91 written values in the data (the cleared one aside) |

Findings for the design: some answers are cleared or recalculated by the form's scripts (conditional questions, calculated phone and dates), and some answers (for example background Question 6) are in the saved form data but not in any barcode, so the filler must apply the same rules, and the system compares the person's validated, saved file with the case facts before submission. Dependent lists (province → city) need codes from the form's own lists. Not tested: Windows; Reader 11.0.10 on Mac (IRCC's advice); IRCC portal upload; the other five combination-1 forms in Adobe; negative tests (stray spaces, special characters); R2 import. Research on how others do it: `../../../research/ircc-barcode-form-filling-2026-10-19.md`.
