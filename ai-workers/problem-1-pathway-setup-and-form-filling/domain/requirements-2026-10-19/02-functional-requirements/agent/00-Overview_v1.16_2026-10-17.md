**Rules**

1. **Every change creates a new file** with the next version and today's date; the previous file moves to `_archive/`; a row is added to the change log at the top of the new file (version, date, change, decision IDs).
2. **Minor version** (e.g. 2.0 → 2.1) for review changes; **major version** (e.g. 2.1 → 3.0) for a restructure.
3. **Requirement IDs are permanent.** A changed requirement keeps its number and is marked "(changed vX.Y — decision ID)". A withdrawn requirement stays as a one-line entry. New requirements continue from the highest number. Numbers are never reused.
4. **Decision IDs are module-prefixed** (e.g. `SA3-D1`, `SA2-D1`). Decisions that another module must apply are listed in the deciding module's §0.2 as **Pending** until that module's review applies them.
5. **Share as soon as a module review closes:** send the changed file(s), with their change-log entries, to the development team. The team updates the matching Confluence page (title with the new version and date) and comments on the affected Jira tickets.
6. The combined files `FINAL-SuperAdmin-FR.md` and `FINAL-Agent-FR.md` (in this folder's parent and in `ERv2-sanitized/Docs/`) are **superseded** by the per-module folders and must not be edited. Developers read Confluence, not those files.
7. **Verify against same-day `dev` (DOCS-6).** Before writing or updating a "what exists today" section (§12), download the latest branches (`git fetch`) and read `origin/dev` of both repositories; record both commit ids in §12. A §12 older than the current `dev` must say so.
8. **One requirements source (DOCS-7).** When a module review closes, tell the tech lead which older documents it supersedes, so any Spec Kit feature built on them is re-based.

## Document Summary

This is the **build-ready functional specification for the Agent/Firm console** — the day-to-day application an immigration firm's staff (RCICs, lawyers, case officers, intake/sales, accounts, managers) use to run their practice end to end. It spans **18 modules (AG-1 to AG-18)**: firm setup, sales/CRM, pathway assessment, booking, retainer/e-sign, billing, case delivery, smart questionnaire, documents, communications, automation, templates, tasks/notes/audit, reporting, client-portal management, firm settings, corporate cases & LMIA, and data import & migration. The console is **multi-tenant (firm-isolated by `firm_id` + RLS), country-aware (driven by Super-Admin Country Packs — never hardcoded), with its core built in-house (the client record and the "Doers"); outside providers are used only for AI/OCR, WhatsApp and mailbox connections, each approved by Super Admin.** Read the **Detailed Scope Index** next for module-by-module scope at a glance; each module then specifies functional requirements, user stories with acceptance criteria, permissions, entities, a current-state reference note, priority, and a **Scalability · Security · Performance** block.

## Cross-Cutting Mandates — Scalability, Security & Performance (at every level)

These three concerns are **mandatory and apply at every level** — globally (see the Architecture and Data/NFR/Security companion documents) **and in every module and requirement in this document**. They are never bolted on later. Accordingly, **each module below carries a `Scalability · Security · Performance` block** stating how that specific feature satisfies them.

- **Scalability & Expandability.** Every feature scales with growth (more firms, users, records, documents) and is **extensible without rework** — new entity types, destination countries (added at the **platform** level as Country Packs — never by a firm to itself, FD-68), or fields added by configuration, not re-engineering (polymorphic `(entityType, entityId)` model; country-pack-driven behavior; stateless services; read-replica-friendly queries).
- **Security at every functional level (security-by-design).** Security is enforced **on each feature, not only platform-wide**: the correct `agent/*` permission on every action; mandatory `firm_id` tenant scoping (DB Row-Level Security as backstop); least privilege; PII handling appropriate to the data the feature touches (passports, financials) *(changed v1.10 — AG7-D10)*: personal data is never masked and has no reveal action, so anyone allowed to see a record sees it in full; exports need only the module's export permission and are audited; personal data is never written to system logs or traces; passport and financial numbers are never put into the content of emails, WhatsApp messages or notifications; field-level encryption at rest where specified; secrets (API keys, passwords, tokens, webhook secrets) are write-only; schema validation of all input; audit of sensitive actions.
- **Performance (highest priority).** Every feature is designed for speed: indexed, paginated queries (no unbounded fetches); heavy/slow work pushed to background jobs (never blocking the request); caching of hot/reference data; performance budgets honoured. **Performance is called out explicitly in every module.**

**Per-module block format** (added to each module):

> **Scalability · Security · Performance**
> - *Scalability/Expandability:* how this module scales and extends (config-driven, polymorphic, country-pack).
> - *Security (this level):* permissions, tenant scoping, PII/validation specific to this feature.
> - *Performance:* indexing / pagination / async / caching specific to this feature.

## Agent-native operation (2026-10-04)

*Added in v1.9 (AG11-D1–D7, AG18-D1–D8; extended same day by AG11-D9–D13 and AG18-D9, D10; decided by the product owner, product owner, 4 Oct 2026; extended 5 Oct by AG11-D14–D18 and AG18-D11–D12). Detail lives in AG-11 (automation and the AI Doers) and AG-18 (data import); this section states the principles every module follows.*

- **We work for the firm, not the regulator.** ExpatReady ships safe defaults and keeps a record of what happened; **the firm decides**. It never reports to a regulator, never declares a firm non-compliant, and never blocks the firm's own licensed judgement. Product copy talks about "protecting your practice", never a regulator's code section, "violation" or "non-compliant". The few fixed **product floors** protect ExpatReady's own product, not regulation: a human approves AI-written text before it reaches a client; nothing is fabricated; nothing is submitted to an authority by ExpatReady; AI processing waits until the provider terms are recorded, and happens only in Canada (AG11-D13, AG11-D15). ExpatReady assists firms; it does not monitor them (AG-11 §3.4).
- **One record per client.** Every fact about a client lives once, on the client's file, with provenance. Doers work around that record; they never keep a second copy.
- **Doers do the work; people approve what matters.** Doers read documents, sort inbound messages, draft replies, check for inconsistencies, chase, remind and prepare forms. A person approves what matters: AI-written client text, government forms and values nobody has checked; firm-approved templates send on their own; approving AI-written client text uses the sending permission (SR-Q10); licence-based approval is withdrawn (R5) *(changed v1.14)*.
- **Autonomy levels and product floors (AG11-D1, revised same day).** Every automated action carries a level: `AUTO` (runs), `APPROVE` (prepares a draft and waits), or `OFF`; the firm sees "Send automatically / Ask me first / Off". Internal actions default to `AUTO`; so do **template messages** (a message from a firm-scope published template with only its merge fields filled — the firm approved the template once; seeded client messages run from day one with ExpatReady's neutral wording and nothing waits for a review — the Automatic messages page (AG-12) lists them; a message missing a firm detail is not sent and the firm sees a note, AG-12-109; the dashboard shows a one-time notice, AG-12-110; AG12-D23) *(changed v1.14 - AG16-11; v1.13 - SA05-R9a)*. Product floor, never lowered below `APPROVE`: one-off AI-written text sent to a client, any government form, any value written into the verified profile without a human having looked at its source. ExpatReady never submits anything to a government authority on its own. A template whose body AI edited is approved once, when the firm publishes it (AG12-D25), not per send *(changed 14 Oct, same-day audit)*.
- **"Needs you" and "Done for you" are the staff home screen (AG11-D2, AG11-D7).** Staff land on the **home screen**: Needs you (drafts waiting for them - work a Doer prepared with no human present, or work waiting on a different person; when the approver is the person acting, approval happens inline and creates no item), then My Tasks due today or overdue, Waiting on us, Payments to record, Unmatched, and a feed of what the Doers did. Empty sections are hidden *(changed v1.15 - AG16-40; spec home AG-11)*. Module dashboards (AG-14) sit behind it (pending knock-on to AG-14).
- **Easy for solo, safe for teams.** Our job is to make life easier for tenants, especially solo and small ones. *Withdrawn v1.14 (SR-Q1c, R5, AG16-8, AG16-9):* the Team safeguards switch (four-eyes, routing to supervisors, backup approver, on at 5 staff), Supervised client messages and the "who approves AI-written client text" setting. Instead: one **Escalation** switch and a separate at-risk-marks switch under Advanced (Owner or Admin, `agent/firm-capability:manage`; AG16-22); the "Self-approved" record on a government form stays (AG11-D9).
- **Approving a Reader value is verifying it (AG11-D10).** In its review view, with the document region beside the value, approving a Reader-proposed value is the verification — one act, not two. It needs `agent/sqr:verify`, which the firm gives to the roles it chooses (AG11-D11).
- **Never fabricate.** Every Doer output is a proposal with provenance and confidence. Unreadable or missing is flagged, never guessed (AG-07 BR-7 applies to all Doers).
- **AI is optional per firm, and off until the terms are recorded.** One firm switch covers all four AI Doers. It is locked off for every firm until Super Admin has recorded the provider, the processing region (Canada only, AG11-D15) and a no-training / no-retention agreement; the Owner then switches AI on once, with an audited acknowledgement (AG11-D13). **AI and OCR processing of client data happens only in Canada (AG11-D15).** Every AI path has a manual fallback; every model call is logged; client data is never used to train models.
- **Waiting times belong to the firm (AG11-D17).** The missing-document chase goes first after 5 days, then every 7 days, at most 4 reminders; an approval waiting in Needs you is overdue after 2 working days; anything linked to a government deadline must be approved at least 2 working days before it (if less remains, it is due immediately and marked urgent). A firm can change all of these in its settings in Release 1 (AG-16).
- **Bringing the firm's existing work in (AG-18).** A firm can import its clients, cases, key dates, documents and history on day one. Imported records are **quiet**: no client-facing automation reaches them until the firm switches it on, per client or per batch, after a preview by recipe and action type (AG18-D9, D10); the screen says "Not started". Past key dates are recorded without reminders unless the case is open and the date is expired or due soon; an import never triggers escalation or at-risk marks. Imported values stay unverified until "Verify imported values" or Reader approval; imported correspondence is historical and never sent. Assisted migration by Expat Ready staff is included free for every firm at launch; a running import cannot be stopped, the firm undoes it in one click afterwards (AG18-D11). Officio and CaseEasy imports are Release 1, each built after a checked real export sample; until then the firm uses the CSV/Excel templates (AG18-D12).

## Purpose of This Document

This document defines the functional requirements for the **Agent/Firm Console** of Expat Ready — the tenant-facing web application that immigration firm staff use every day to run their practice end to end: capture and qualify leads, assess immigration pathways, book consultations, sign retainers, collect payment, deliver cases, and serve clients through a portal.

**Plane.** Expat Ready has three planes. The **Super Admin** plane (Expat Ready's own team) operates the platform globally and is specified in its own companion document. The **Agent/Firm** plane — specified here — is the paying tenant: an immigration firm (an RCIC or lawyer plus staff). The **Client** plane is the firm's immigrant end-customer, who interacts only through a separate portal (the firm-side management of that portal is Module AG-15 in Part 2).

**Scope boundary.** This document covers only the Agent/Firm console. It references — but does not specify — Super Admin capabilities (country packs, plans, global templates) and the client portal's own UI. *(Added v1.10 — AG7-D2:)* the client portal's own UI is specified in `FINAL-ClientPortal-FR/CP-01-client-portal-app` — the third console document.

**Design doctrine for the Agent plane.**

- **Everything is firm-owned and tenant-isolated.** Every record a firm creates belongs to that firm and is scoped by `firm_id`, enforced in the database by Row-Level Security (see the Architecture and Data companion documents). A firm can never see, query, or mutate another firm's data. Tenant isolation is a platform guarantee, not a developer convention.
- **Country-aware, never country-hardcoded.** All immigration specifics — programs and streams, eligibility rules, calculators and scoring grids, government forms, document checklists, case stages and workflows, reference/occupation data, and the regulatory body — come from the **active Country Pack** that Super Admin configures and publishes. The Agent console reads packs; it never embeds Canada-specific (or any country-specific) immigration logic in code. See "How Country-Awareness Works in the Agent Console" below.
- **We work for the firm, not the regulator.** The Agent console gives the firm safe defaults and a record of what happened, and the firm decides. It never reports to a regulator or declares a firm non-compliant (see "Agent-native operation" and item 7 below).
- **Extensibility-first cross-cutting modules.** Notes, tasks, documents, reminders, communications, e-sign, audit, and automation attach to **any** entity through a generic `(entityType, entityId)` pattern. A new record type inherits all of these by configuration, not by new engineering. These shared modules are specified in AG-9 (Documents), AG-10 (Communication), AG-11 (Automation), and AG-13 (Tasks/Reminders/Notes/Activity) in Part 2; modules AG-1 through AG-8 reference them.

**A note on the current-state references.** Each module carries a **Reference Note** that maps the requirement against the existing codebase (audited read-only): what exists today, what is genuinely new, and what changes. This is a ground-up build — the existing system is a reference for good patterns and known gaps, not a constraint. Where today's code hardcodes Canada (notably the assessment calculators) or duplicates structure (notably individual-vs-corporate cases), this specification deliberately corrects that.

## How Country-Awareness Works in the Agent Console

Expat Ready is a global immigration platform that launches with Canada and is designed from day one to serve many destination countries. **The platform is multi-country; a firm is not** (FD-68 — *one agent, one account, one country*). The Agent console is built around this principle so that the same product serves a Canada firm and an Australia firm with no code change — and offers neither of them a country switcher.

**1. A firm operates in exactly one country.** Super Admin records which country an account is *for* as a single **`FirmCountryEntitlement`** grant, set when the account is provisioned (see Super Admin Module SA-2) and **immutable thereafter** — not by the firm, not by an operator (FD-68). A firm provisioned for Canada sees Canadian programs, forms, and workflows, and nothing else. A practice that genuinely works two destination countries holds **two accounts**, one per country. There is no activation step, no *primary country*, no country switcher and no active-country set: the Agent console reads the firm's one country and scopes every country-specific surface (program pickers, calculators, form libraries, checklist templates) to it.

**2. Every case and assessment is tagged with a destination country.** The concept survives; the *choosing* does not. When a firm user starts a pathway assessment, opens a case, or builds a questionnaire, the record's **destination country** is stamped as the account's one country (FD-68) rather than picked from a list. That stamp does everything it always did: it binds the record to a specific Country Pack and determines every downstream behavior — which programs and streams are offered, which eligibility rules and scoring grids run, which government forms and field mappings apply, which document checklist is loaded, and which case-stage pipeline and workflow blueprint drive delivery.

**3. The active Country Pack drives the behavior — code does not.** Programs/streams, eligibility rules, calculators, government forms and their field mappings, document checklists, case stages and workflow templates, reference and occupation data, the regulator definition, and the supported languages all come from the published Country Pack for the firm's one country. The Agent console contains **no** hardcoded immigration logic for any country. When Super Admin publishes a pack update (for example, a revised scoring table), firm behavior changes without a deployment.

**4. Results are stamped with the pack version that produced them.** Every assessment, generated government form, and checklist instantiation records the **Country Pack version (and the specific content-domain versions)** in effect at the moment it was produced. This makes every result reproducible and auditable: a firm can always demonstrate exactly which rules and tables were applied to a given client on a given date, even after Super Admin publishes newer versions. Re-running an assessment against a newer pack version is an explicit, logged action — never a silent change to a finalized record.

**5. The workspace is single-country by construction.** Because a firm has exactly one country, lists, dashboards and search need no country segmentation and no country filter — every record in the tenant already shares the same destination country (FD-68). Country remains a first-class *stamped* attribute on prospects, assessments, cases and questionnaires, because it is what binds each record to its pack version and it is the dimension the **platform** rolls up across firms (Super Admin SA-9). Within one firm's own console it is a constant, not a facet.

**6. Localization follows the pack and the firm's locale.** Each Country Pack declares its supported languages (for Canada, English and French). The firm's configured default locale and each client's language preference select which localized content (program names, stage names, document names, client-facing questionnaire and email copy) is shown. Bilingual support is a first-class requirement, not a retrofit.

**7. We work for the firm, not the regulator.** The Country Pack names the regulator; the firm records its own credentials and links its staff to them, so the console can tell a licensed user from an unlicensed one (AG-01 §3.5). ExpatReady never checks, tracks or warns about a licence's validity or expiry (AG1-D19). That is as far as it goes: ExpatReady keeps a record of the credential; it no longer routes approvals by licence (R5); the firm decides. Packs do not make ExpatReady a regulator's product — it never reports to a regulator, never calls a firm non-compliant, and never blocks the firm's own licensed judgement.

## In-House by Design — "The Doers" (Core In-House, Approved Providers)

**Founder directive (revised 5 Oct — AG11-D14):** every product tool in the Agent console is built **in-house** as a **Doer**, and the client record and all Doer logic are built and owned by ExpatReady; no third-party *product tool* is integrated in a Doer's place. Each Doer replaces a SaaS the firm would otherwise leave the platform for: **Signer** (e-sign, replaces DocuSign), **Scheduler** (booking, replaces Calendly), **Mailer** (email, replaces Outlook/Mailchimp), **Messenger** (SMS/chat, replaces Twilio/WhatsApp), **Biller** (invoicing, replaces QuickBooks), plus **Tasker**, **Reminder**, **Minder**, the immigration-only Doers (**Qualifier**, **Filler**, **Binder**, **Reviewer**), and the four **AI Doers** — **Reader**, **Sorter**, **Writer**, **Checker** (AG11-D4; renamed from Drafter, AG16-4; off until the provider terms are recorded, AG11-D13) *(final alignment)*. The engine that runs them is the **Conductor** (Workflow) — an engine, not a Doer.

Outside providers are allowed for only three things, each **approved by Super Admin (SA-08)** before any firm uses it (AG11-D14): **AI and OCR processing** for the four AI Doers (processing happens **only in Canada**, AG11-D15), **WhatsApp** (inbound and proactive outbound with provider-approved templates, AG11-D18(a); SMS stays Release 2), and the **connection of a firm's own mailbox** (Gmail, Microsoft 365 and IMAP for other providers, all Release 1 — AG11-D16, AG11-D18(c)). Beyond these, the only third parties are **infrastructure rails — NOT tools** (they physically cannot be built in-house): a **payment processor** (the card rail under *Biller*), an **email-delivery relay + SMS/WhatsApp gateway** (the pipes under *Mailer*/*Messenger*), and **cloud/object storage**. Separately, a firm may **optionally connect its *own* accounts** — its own mailbox (*Mailer*, firm and personal — AG16-15) and each person's own calendar (*Scheduler*, personal only — AG16-18) — which is connecting to the firm's own data, not integrating a competing tool, and can be disabled for a fully self-contained ER.

## Agent Console Sub-Roles

The "Agent" persona is an umbrella over the distinct staff roles inside an immigration firm. All operate within the firm's tenant under the **LOCAL** permission scope (permission keys prefixed `agent/*`). Every firm starts with the same **starter roles published by Expat Ready in Super Admin** (six at launch) on every plan *(changed v1.12 — SA6-D12)* — Owner, Admin, Case Manager, Case Officer, Billing / Finance, Read-only (SA6-D5, SA6-D7; permissions in SA-06 Appendix C). The job personas below are how people describe their work; each maps to a starter role, or to a firm custom role copied from one. The firm's one provisioning-set country (FD-68) is a resource-availability filter layered on top of permissions: holding a permission never overrides what the firm's country entitlement makes available.

| Sub-Role (job persona) | Maps to starter role | Responsibilities | Typical Actions |
|---|---|---|---|
| **Owner / Principal RCIC** | Owner | Full access to the firm's tenant; the firm's master account. Accountable for the regulated work and the firm's compliance posture. | Firm setup and branding; manage staff, roles, and permissions; configure automation; oversee all cases; final sign-off on regulated work. (The firm's country is *not* among these — it is set by Super-Admin at provisioning and is immutable, FD-68.) |
| **Licensed consultant (non-owner)** *(fixed 18 Oct — AG07-D12, SA6-D5)* | Case Manager (holds the professional approvals) or Case Officer | A licensed consultant (or lawyer) who owns and delivers regulated immigration work but does not administer the firm. | Author and finalize assessments; own cases; review documents; prepare and verify government forms; manage compliance and deficiencies; countersign retainers. |
| **Case Officer** *(fixed 18 Oct — AG07-D12, SA6-D5)* | Case Officer | Day-to-day case execution under the lead representative's supervision. | Collect documents; manage questionnaires; execute checklists; draft forms; log correspondence; advance case stages; manage tasks. |
| **Intake / Sales Representative** | A firm custom role copied from Case Officer (for example "Intake / front desk") | Front of the funnel: convert inquiries into retained clients. | Capture and qualify leads; manage the pipeline; run preliminary assessments; book consultations; follow up; convert prospect to client. |
| **Accounts / Billing** | Billing / Finance | The firm's money operations (client-to-firm). | Generate invoices; configure payment plans; record and reconcile payments; manage retainer/trust deposits; run financial reports. |
| **Manager** | Case Manager or Admin | Oversight and analytics across the firm. | View dashboards and reports; monitor pipeline, case load, and finances; manage staff workload; identify bottlenecks. |

**Permission model.** Permissions are additive and default-deny: a user holds one or more roles, each granting a set of `agent/*` permissions; anything not granted is absent. There is no deny-list. The starter roles are published and maintained by Expat Ready in Super Admin (six at launch) *(changed v1.12 — SA6-D12)*; a firm uses one as is, or copies it and edits the copy to make its own role (SA6-D3); the copy does not change when the starter role changes. **Owner and Admin** create, edit and give roles; an Admin can only give a role whose permissions the Admin holds, and a written reason is required for every role change. A person can hold several roles. Custom roles contain only `agent/*` permissions, checked by the server on every save. ~~Five~~ Six actions are Owner-only and can never sit on a custom role *(changed 18 Oct — AG16-90)* (allow Expat Ready support to make changes, cancel the subscription, edit the firm's legal profile, export all firm data, connect the client-payments payout account, and switch AI on and off — `agent/ai:switch`, AG16-80). The professional approvals (override a critical warning, approve a government form, sign off a file, countersign a retainer) default to Owner and Case Manager; the system never checks licence (SA6-D9). **Visibility is open by default**: the "see all" permissions for clients, cases, prospects and tasks are on every starter role (all six at launch), and a firm can make any role own-only (SA6-D1). Firm RBAC is specified in AG-1 and AG-16 and, in full, in SA-06. GLOBAL-scope permissions (Super Admin) are never available to firm users.
