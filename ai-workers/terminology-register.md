# Business terminology register

Version 0.1 · 17 Oct 2026 · **Proposal for the next concept revision.** Current numbered keys and approved area names remain unchanged. This is a naming cross-reference, not 43 additional skills, a new architecture, an implementation claim or a production-provider selection.

## 1. How to refer to the parts

| Term | Meaning | Example |
|---|---|---|
| Area | Where the work belongs and who owns it | Product Studio; Case Flow |
| Component | A product function inside an area | Pathway Configurator |
| Assistant role | A plain name for the AI responsibility in that area | Configuration Assistant |
| Skill | One bounded capability, with an input/output and limits | Form Field Matcher, key 11 |
| Rules function / calculator | Repeatable calculation, selection or transfer | Eligibility Calculator, key 22c |
| your assistant / co-pilot | The on-request interface to the same permitted functions | “Read this upload” |
| Avatar / character | Optional visual/brand identity | Separate naming work; Xpato/Xpartian remain parked |

**Name the job, then define its limits.** Use familiar object-and-action names: Document Reader, Client Message Writer, Form Consistency Checker. A Reader extracts proposals; a Writer prepares text; a Checker flags findings; a Filler transfers confirmed values by rules. None of these words implies approval or autonomous execution. “Verify” is reserved for a defined completed check, not an AI confidence score.

Avoid vague or overstated names such as Helper, Librarian, Expert, Brain, Autopilot or “AI engine” when the reader needs a specific responsibility. Some old names survive as aliases in §4 so earlier discussions remain traceable. Keep PQR and SQR in the main explanation; expand them once in the glossary. Always distinguish **agent = firm staff** from an AI skill.

## 6. Information every catalogue entry must carry

- One stable existing key, or an explicit “unkeyed product function / proposed capability” label.
- One preferred business name; earlier names recorded as aliases.
- Area and component; who uses the output.
- What starts it, what it reads and what it produces.
- AI, rules or a split between them; who confirms/approves the result.
- What it never does and what happens on failure.
- **Definition status** and **build status** separately, with evidence. Retire vague “exists”.

The earlier Engine/Status columns must be recovered in this clearer form. Naming should make the AI/rules/person distinction more predictable, not hide it behind a character name. Use one agreed reference wherever the component appears: story, stage cards, catalogue, diagram, appendix and requirement cross-reference.
