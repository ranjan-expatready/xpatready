## Blocking

### B-1. The worked example does not run under the document's own rules

**Where:** doc L309 (14:00), doc L305 (09:05), doc L37 and L105.
**What is wrong.**
(a) §1 says the question must be one of the fixed shapes, and "a question outside them is refused with the plain refusal wording" (doc L37). Catalogue W-24 L414 says "**v1** structured question shapes only". At 14:00 the expert answers *What is Client A's passport number and when does it expire?* and labels it "2 (a field question)". But shape 2 is *what is missing, and which rule says so*, and its records list (doc L117) has no client profile field. The one Restricted-field example the gate requires therefore runs through a shape the document does not define.
(b) The shape 1 answer format is "one line per file the asker may see" (doc L105). The 09:05 answer to *which of my files are at risk this week* gives two lines. One is Client A's retainer expiry on Monday 14 December, four weeks away. Client B gets no line at all.
(c) Nothing defines "this week": a calendar week, the next seven days, or the firm's time zone per AG-14 BR-6 (L418). Rule 4 forbids the model to "add, subtract, compare or extrapolate" (doc L84). So the date window must be a retrieval rule, and none is written. Without it, the example's selection is the model's choice.
**Fix.** Either add a fifth shape, *a field's status on a client file* (records: the client profile field and its status only; Restricted fields by status, IMP-21), list it in §2 and §9 and in §11 decision 1, or re-run 14:00 as a refusal and move the Restricted-field demonstration into shape 2 (for example, *what is missing on Client A's file?* with the passport line answered by status). Write the shape 1 window rule: "deadlines whose stored date falls in the next seven calendar days in the firm's time zone (AG-14 BR-6), plus anything past and unmet". Label it Proposal. Re-run 09:05 so it shows one line per file, Client B included ("no watch"), and the December item only if the rule admits it.

### B-2. Nothing says what turns a typed question into a shape, a client and a window, so "the model never selects which record is read" is unsupported

**Where:** doc L27 ("A signed-in staff member types a question"), doc L75 (the retrieval "is a rule over product data …; here it never selects which record is read either, Proposal"), doc L37, doc L310 ("outside the shapes, refused").
**What is wrong.** Every shape needs parameters before the retrieval rule can run: which shape, which client or file (*Client A*, *the Case Manager's files*), which period. The document never says who extracts them. If a model parses the typed text, then a model chooses which records are read (only within the asker's keys, but it still chooses). That contradicts doc L75, and IMP-10's principle that "a model never selects which action runs" (`ws2-improvements.md` L154) would no longer cover reads. If a rule parses it, the rule is missing. The catalogue's own word is "**structured** question shapes" (W-24 L414), which reads as a form with pickers, not free text. The same gap decides how the 15:30 refusal ("outside the shapes") is reached, and whether that refusal costs a model call (§6).
**Fix.** State the mechanism and label it Proposal. Recommended, because it keeps doc L75 true: in version 1 the asker picks a shape from a fixed menu and picks its parameters with the product's own record pickers (the Finder's permission-filtered search, Doc 1 §8.8 L2536–L2545). Free typing is version 2. If the founder wants typed questions in version 1, then a model call proposes a shape and parameters, the asker confirms them before any record is read, and the confirmation is logged. Add the mechanism to §9 and to §11 decision 1, and remove "types" from doc L27, or qualify it.
