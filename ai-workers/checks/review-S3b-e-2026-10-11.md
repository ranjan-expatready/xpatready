**n-34. A Triager fix line for a cancellation points to a change note no version 1 recipe can draft.**
- *Where:*
  - AW-2-65 (L418): "Where the mapped fix is any change SA-4-89 lists (a change of plan or billing period, a discount, a cancellation or its undo), the fix line SHALL say only *ask the account manager for a change note*";
  - §3.6 (L318);
  - AW2-D12 (L175);
  - AW2-BR-12 (L449);
  - §9 (L757): "the change reaches a person only through that note and the second person".
- *Evidence:*
  - AW-2-71 (L424), §0.1 (L204) and Q39 (L1029) say: "No version 1 recipe drafts a cancellation or its undo" (plan L91). So for a cancellation fix the account manager cannot get a note from the assistant.
  - The account manager then cancels by hand, which is "a person's change … as today" with no second person (AW-2-72 L425; §9 L768).
  - So §9 L757 is false for cancellations. A tester following it would write a case that cannot pass.
  - AIW-D59 is not breached: the assistant proposed nothing.
  - The cause is that two Lead's calls, plan L100 and plan L91, each list cancellation the opposite way.
- *Fix (Lead's call):* pick one and apply it to the six places above.
  - **(a) Recommended.** In version 1 the fix menu names no cancellation or undo fix at all, and a cancellation request shows the diagnosis only. This matches L91, and the Triager proposes nothing that SA-4-89 would need.
  - **(b)** Add a cancellation note recipe. This reverses L91, and CN-SA-04 change 3 already covers it.
  - Either way, record the call in the plan under L100 (plan L64).

**n-35. The per-assistant-run cap is called "platform-only" with "no firm value", which the change notes do not say.**
- *Where:*
  - AW2-D14 (L177): "these two caps have no firm value: they are platform-only values";
  - §3.3 (L300);
  - AW-2-29 (L374);
  - §0 AIW-D62 row (L58): "the two platform caps are platform-only values";
  - §0.2 CN-SA-12 row (L232): "the platform's own caps are platform-only values";
  - §11.5 Govern (L897).
- *Evidence:*
  - CN-SA-12 SA-12-33 (c) lists four caps. Only the fourth is "**platform-wide per month, for Expat Ready's own assistant calls** … This is a platform-only value; no firm has a value for it."
  - "Per assistant run: a runaway run is stopped and parked for a person, from day one" is one general default for every assistant run.
  - CN-AG-16 change 4 gives each firm "one optional firm value for each … spend cap (per firm per month, per Practice expert user per day, per assistant run …)".
  - Plan L104 calls only "Expat Ready's own platform-wide cap" platform-only.
  - A builder reading AW-02 could build a second, platform-only per-run cap. A tester could not tell whether a firm's stricter per-run value applies to Expat Ready's own support run on that firm's ticket.
  - The S3b-d review introduced the wording in its own evidence for n-26 ("The per-run cap and the platform-wide monthly cap have no firm value"). That was the reviewer's error, and v0.5 copied it.
- *A smaller wording point in the same lines:*
  - AW2-D14 (L177) and AW-2-29 (L374) say "until the founder's post-pilot decision (AIW-D62) only the Platform Owner MAY change a default". This reads as if the Owner-only rule ends at that decision.
  - CN-SA-12 "Defaults" makes the Owner-only rule permanent; what ends at AIW-D62 is that "no founder decision is needed for such a change".
  - Q24 (L1007) opens "Until then and until …", which mixes the deployment deadline with the post-pilot decision.
- *Fix:*
  - Say that the per-assistant-run cap is SA-12-33 (c)'s one default for every assistant run, platform runs included.
  - Say that the platform-wide monthly cap is the only platform-only value.
  - Say that a firm's stricter value (CN-AG-16 change 4) governs only that firm's own assistants, never an Expat Ready assistant's run on its ticket (**Proposal**, for the Lead to confirm).
  - Reword the time phrase: "only the Platform Owner changes a default, with a recorded reason; until the founder's post-pilot decision (AIW-D62), no founder decision is needed for such a change".

**n-36. The platform delegation lifecycle has no transitions out of PENDING_ACCEPTANCE (declined or withdrawn), and its "no one else" guard contradicts §7 and §9.**
- *Where:* §6 delegation diagram (L477–L479) and table (L484–L489); §7 `Delegation.endReason` (L526); §9 (L733); AW2-D26 (L189); §10 E `system/ai-delegation:manage` (L840).
- *Evidence:*
  - v0.5 made §7 carry "DECLINED (the person declines a pending delegation) or WITHDRAWN (the person who set it up withdraws it while pending, AW-01 §6)". §9 L733 says "the person who set it up may withdraw it while pending".
  - AW-02's own §6 has no PENDING_ACCEPTANCE → ENDED row for either. Its only ending row reads "the person ends it …; the person is deactivated (SA-7-22) — **no one else**" (L488). On the platform, the person who set the delegation up is the Platform Owner, who is "someone else".
  - AW-01 §6 settles this in one line that AW-02 lacks: "the person who set it up withdraws the offer before it is accepted (it never took effect, so no one ends another person's delegation)" (AW-01 L528).
  - The two lifecycles also code a pending end differently. AW-02 L479 lets "person ends" apply to PENDING_ACCEPTANCE (PERSON_ENDED), while AW-01 uses DECLINED (L527).
  - §10 E names no key for the Platform Owner's withdrawal. The key's description is "Set up" only, here and in CN-SA-06 change 4. Plan L110 says that an act named for a role names its key.
- *Fix:*
  - Add AW-01's two PENDING_ACCEPTANCE → ENDED rows to §6 (DECLINED; WITHDRAWN by the person who set it up, before acceptance), with AW-01's reason that it never took effect.
  - Limit "person ends" to ACTIVE or PAUSED.
  - Add to §10 E that the Platform Owner withdraws a set-up not yet accepted under `system/ai-delegation:manage`, and ask the SA maker to add the same words to the key's description (note L-4).

**n-37. AW-02 changes what a shared AW-01 field refers to.**
- *Where:* §7 `HoldoutCheck` (L533): "this plane has no `ApprovalItem`, so `HoldoutCheck.approvalItemId` holds the `PersonaProposal.id` of the accept-all it checked".
- *Evidence:*
  - AW-01 §7 is the one home of `HoldoutCheck` (AW-02 L524: "defined in AW-01 §7, which is their one home; this module adds only the platform values").
  - In AW-01, `approvalItemId` (L573) is a reference to an approval item. Storing another entity's id in it is a change to the field's meaning, not a platform value. A builder who makes it a database link to `ApprovalItem` cannot store a `PersonaProposal` id.
  - The S3b-d fix for n-22 invited this wording ("Name `PersonaProposal.id` as the platform reference in place of `approvalItemId`"); the field itself belongs in AW-01.
- *Fix:* the AW-01 maker gives `HoldoutCheck` a reference that names its kind, for example an optional `personaProposalId` beside `approvalItemId` with exactly one of the two set. AW-02 cites it. Until then, add it to Q12's "still open" list.
