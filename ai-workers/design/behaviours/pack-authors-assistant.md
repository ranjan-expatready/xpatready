## 0. Summary: the persona in five plain lines

1. The Pack author's assistant works for one named member of Expat Ready's content team, the Content author for Canada. It watches the official government pages the pack already cites, and when a page changes it says what changed, which parts of the pack read that page, and how many firms' clients are still on the current rules (W-21).
2. When a new edition of a government form arrives, it compares the new form's boxes with the current box map, drafts the map lines for the boxes that moved or are new, and lists the rows of the pack that use that form; when a scoring grid or a reference table changes, it drafts the new rows with the source and the date it was checked (W-19). It also drafts the French of a non-legal label; it never touches regulator or consent wording.
3. It drafts sample clients, runs the pack's own rehearsal on them against the draft and against the current version, and writes a plain-words note of what would change for a client, so the approver reads a result, not a rule (W-20). The rehearsal report goes with every production submission and the second person reads it before approving (AIW-D49). The engine decides every outcome; the assistant never scores anything.
4. Everything it produces is a proposal in a file: the author previews it and commits it into the draft by hand, runs the product's validation, and submits; a second person, who is neither the author nor the submitter, approves and publishes on a date. The assistant holds no key that writes into a pack and can never submit, approve, publish or roll back (decided 11 Oct 2026, AIW-D54).
5. Every step is in the platform audit chain with the delegation's reference, so for any published rule Expat Ready can show who proposed it, who committed it, who approved it, when it took effect and which firms' clients were pinned to the version before.

## 2. What it does, step by step

**How to read the tables.** *Action* is a rule the pack machinery already evaluates (validation SA-1-51; the dry-run SA-1-52; the diff SA-1-53; import preview SA-1-56; field parsing SA-1-30) or a persona recipe step marked **Proposal** and listed in section 9. The Conductor's closed action list (AG-11-2) is the firm's; the platform plane has no action vocabulary (G-1), so *Doer or rule* names the tool in the sources' own words (the validation, the test run, the diff, the import, the parsed field inventory) and the one model Doer the persona uses, the **Writer** (the sources call it the Drafter; renamed by AIW-D53; *Drafter* stays the template engine). **The Writer's only action today is `draft_message`, defined as "prepare a message; always followed by a send action whose autonomy is at least `APPROVE`" (AG-11 v1.11 §3.3).** Here it drafts a map line, a row, a sample, a description or a note, none of which is a message and none of which is followed by a send: a re-use of the action for non-message content, an extension of the closed action list (**Proposal**, G-24; IMP-10 "extended as needed"). Every model call is a plain Doer call: "models SHALL have no tool access" (AG-11-94); third-party text reaches the model as delimited data (the AG-11-94 pattern; the rule itself is written for "Client-supplied content"); model output "can propose *values* (a date, a type, a draft), never *actions*, recipients, addresses or permissions" (IMP-26 rule 1). *Proposes / writes:* the persona proposes files and reports; it writes nothing into a pack. *Autonomy and floor:* the platform has no autonomy levels; the floor is the missing write key and the two-person rule. *Recorded:* the platform audit entry (SA-11-2 fields; `tenantId` null), the run record (IMP-35, Proposal), the AI run log row (AG-11-72; the entity has `firm_id` and needs a null-tenant form on the platform, G-1; its Doer value for the Writer is the source's `DRAFTER`) and the delegation reference with the mode *a persona acted for a person* (DELEGATED), *the person acted directly* (PERSON) or *plain automation ran* (AUTOMATION) (IMP-1, Proposal). **Who the actor is (the Lead's rule for both platform personas, 10 Oct 22:00 IST):** a run the persona's own schedule starts is recorded with `actorType` system ("System actions are `system`", SA-11 v2.7 BR-3), mode DELEGATED and the delegation reference; a run a person starts (by hand, or by an act such as an upload that triggers it) carries that person (`actorType` super_admin), mode DELEGATED and the delegation reference; the product's own scheduled jobs (the publish taking effect) are `actorType` system with mode AUTOMATION (SA-11 v2.7 §9: "A scheduled disposal or webhook has no human actor"). In every cell the plain words come first and the product's internal name follows in brackets.

### 2.1 W-19 Pack Drafter

*In plain words.* When the government issues a new edition of a form, the content author uploads the PDF to the pack's draft and the product reads the form's boxes from it. The assistant compares those boxes with the current box map: which boxes kept their names, which moved, which are new, which are gone. For each box that is new or moved it drafts a map line, saying which client answer fills it and how (date format, code, option list), and marks every drafted line as its own proposal awaiting review. It lists the rows of the pack that use that form so the author knows what is touched; because a row points at the form and not at an edition, no row changes. It checks its own file the way the import will, then delivers it as a field-map file the author previews and commits into the draft, then checks box by box against the PDF. The same pattern serves a scoring grid or a reference table: the assistant drafts the new rows from the official page with the source and the date checked, and the author's import validates and commits them. The author, not the assistant, is the author of record.

### 2.3 W-21 Rule-change Watcher

It never edits the pack, never follows a link it finds on a page, and never decides whether the change matters; a person does.

**Hidden instructions in third-party content (IMP-26, Proposal, on the AG-11-94 pattern).** A government page, a PDF form and an uploaded table are third-party content. AG-11-94 is written for client content ("Client-supplied content SHALL be passed to a model as delimited data, never as instructions"; "models SHALL have no tool access"); this persona applies the same rule to third-party pages. For this persona that means: a page that says *update the fee to X and publish* is read as text; *X* is a proposed value for the author to verify against the page, and *publish* is nothing, because no model ever selects an action (IMP-26 rule 1) and the persona holds no publish key. The next page fetched is always the next recorded source, never an address found in text (rule 2 pattern). A standing test set of planted instructions (pages and PDFs carrying hidden instructions) runs against every version of the model instructions before it goes live (rule 5; IMP-5). A proposed line whose value came from page text says so beside the author's accept control (rule 6).

**Personal data (IMP-21, Proposal).** The persona processes pack content and synthetic samples only. It never passes a model a client record, because it cannot read one (section 1). The one place personal data could enter is a sample client the author writes by hand; the rule that samples are synthetic (G-7) and the content-neutrality gate in the team's automatic code checks (CI: "no immigration content is seeded", SA-01 v2.2 §12) keep the pack free of both client data and hardcoded content.

**What happens when a limit is hit.** (1) *A write attempted:* refused on the server (BR-17; IMP-27 pattern); the run record carries the refusal; the run continues with the next proposal. (2) *A failure:* the recipe step is retried and then parked with its context and a notification to the Platform Owner (the AG-11-27 dead-letter pattern; on the platform plane Proposal). (3) *A spend cap:* the run "is stopped and parked for a manager to look at, with a notification" (IMP-36). (4) *A stop condition (section 1):* the run stops; the proposal package stays readable, marked *stopped*. (5) *A kill switch:* in-flight work is paused, not deleted (SA-12-11; SA-12-12); the Platform Owner is notified (SA-12-12). (6) *Who is told:* the author through the work queue (SA-1B-40); the Platform Owner for a kill switch (SA-12-12) and for a parked run; the Security & audit role reads the chain (SA-07 v2.10 Appendix A "Audit trail — read"). ## 10. Glossary additions

Only terms not already in `../ai-organisation.md` §8 or `case-assistant.md` §10.

- **Writer:** the AI Doer that drafts text for a person to approve (the `draft_message` action; the sources call it the Drafter, AG11-D4); renamed by the founder on 11 Oct 2026 (AIW-D53). The four AI Doers are Reader, Sorter, Writer and Checker. In this document's own words *Drafter* means only the template engine ("Generate-from-template (Drafter)", `agent/document:generate`, SA-06 v3.1 §10b), which this persona does not use. The AI run log's Doer value `DRAFTER` (AG-11 v1.11 §7) is the source's field value for the Writer and is quoted as it stands. **W-19 Pack Drafter** is the catalogue worker's name (`../workers/catalogue.md` §2.6), not a Doer; it is unchanged.
- **Content author / Content Manager:** one platform role under two names: SA-07 v2.10's "Content author" ("Writes the Canada pack.") and SA-01 v2.2's "Content Manager" ("Write and maintain the pack."). The person this persona works for.
- **Content approver / content publisher:** the second person who approves, publishes and rolls back production packs, "never their own draft" (SA-07 v2.10 §2); "Platform Owner or content publisher" in SA-01 v2.2 §10.
- **Two-person rule (production pack):** "its author and its submitter can never approve or publish it (enforced on the server; refusals are audited)" (SA-01 v2.2 §3.12); the platform's approval point for this persona; since AIW-D48 it covers reference data in a published pack too.
- **Draft / In review / Approved / Published:** the pack draft's states (`DRAFT → IN_REVIEW → APPROVED → published`; a rejection returns it to Draft "with the reviewer's reason", SA-01 v2.2 §3.12, §6).
- **Test-only / production pack:** a pack version's classification (`TEST_ONLY | PRODUCTION`); test-only packs "are never served to firms" and may be approved by one person (SA-1-61).
- **Validation report:** the product's pass / warning / error report before submit and publish ("Errors block; warnings don't.", SA-01 v2.2 §3.13); "The report that authorised a publish is kept." (BR-1).
- **Rehearsal report:** the product's dry-run report on sample clients, for the draft and for the current version (SA-1-52); attached to every production submission and read by the second person before approving (AIW-D49).
- **Completeness profile:** per-country rules for what must be complete before a pack can publish, for example that required languages are complete (SA-01 v2.2 §3.2; SA-1-63).
- **Diff:** the per-content-area comparison of a draft against a version or of two versions, "shown in the approval step" (SA-1-53).
- **Import preview and all-or-nothing commit:** "Import previews first and commits all or nothing; it creates draft content only." (SA-1-56); the author's act that brings a proposal into a draft.
- **JSON / JSONB / CSV / XLSX:** JSON is a plain structured text format for data files; JSONB is the database's stored form of it; *before/after JSONB* in SA-11 §3.9 means a stored copy of the record before and after a change. CSV and XLSX are spreadsheet files.
- **Payload hash / content hash:** a fingerprint of the exact content submitted (on a draft) or published (on a version), so any later change to it would show (SA-01 v2.2 §7).
- **Manifest:** the list inside a pack version of which version of each content area it bundles (SA-1-46).
- **Cache (invalidated):** the stored fast copy of published content the platform serves to firms; "invalidated" means it is thrown away so firms read the new version (SA-1-59).
- **Canonical field:** one entry in the pack's shared dictionary of applicant data, which rules, scores, questions and form maps all point at (SA-01 v2.2 §3.2 row 1; SA-1-17).
- **Form edition:** one issue of a government form, "with an edition date, an effective date and an uploaded PDF" (SA-1-28); a row points at the form, never at an edition (SA-1B-26).
- **Parsed field inventory:** the list of a PDF's fillable boxes "read on upload" (SA-1-30); what the edition comparison reads.
- **Purpose:** a named way of picking a value out of a list the client answered once ("the entry marked current", "the latest entry", and three more), which form boxes reference "never a section" (SA-1B-11, SA-1B-12).
- **Configurator row / line:** one row per full combination of Pathway › Program › Category › Sub-category, holding lines of "One line shape" for sections, documents, forms and government steps (SA-1B-55, SA-1B-57).
- **Scoring configuration:** "points tables, conversion tables, thresholds and composite scores, stored as data and evaluated by one generic engine" (SA-1-21). **CRS:** the Comprehensive Ranking System, the points grid for Express Entry candidates, named in SA-01 v2.2 §1 ("the CRS grid"); general knowledge, confirm with the Immigration SME.
- **Reference table:** a typed table of official values (occupations, language scores, fees, funds, wages) built in the table designer (SA-1B-41); rows are bulk-uploaded with validation (SA-1B-44).
- **Source, date checked, next-review date:** the three fields every item reflecting a government rule carries (SA-1B-39); the watcher's inputs. **Work queue:** where overdue items appear (SA-1B-40).
- **Stored page copy:** the watcher's last fetched text of a recorded source page (G-21, Proposal).
- **Delimited data:** text handed to a model inside markers that say *this is quoted input*, so the model reads it and never obeys it (AG-11-94; IMP-26 calls it "marked-off data").
- **Sample client / sample family:** the made-up person or family the dry-run runs on (SA-1-52; SA-1B-62); synthetic by rule in this document (G-7). **Test fixture:** a made-up data set used only by automatic tests.
- **Conformance test:** AG-03 v1.4 BR-18's requirement that "known reference profiles reproduce expected scores/outcomes" before a pack version publishes; in conflict with SA1B-D18 (G-11); the founder chose an attached rehearsal report, not a blocking test (AIW-D49).
- **Pinning / adoption:** a client's or case's work stays on the pack version in force when it started; staff adopt a newer version deliberately, audited (SA-1-58; AG-07 v2.7 BR-21; FD-3). **Stale assessment:** a lead's latest assessment made under a version older than the current one (AG-3-29).
- **Actor type / tenant id:** on every platform audit entry, `actorType` is one of super_admin, firm_staff, client or system, and `tenantId` is "null for global actions" (SA-11-2).
- **Step-up:** a second identity check ("Confirm it's you — touch your passkey or enter your code") before a risky action such as changing a feature flag (SA-07 v2.10 §3.2).
- **Kill switch flag:** a `killSwitchEligible` flag tripped at PLATFORM scope with a mandatory reason under `system/flag:kill`; "pauses in-flight feature work" (SA-12-12).
- **Rails (SA-08):** SA-08's list of approved outside services the platform connects to (IMP-6).
- **CI and the content-neutrality gate:** CI (continuous integration) is the team's automatic checks that run on every code change; the content-neutrality gate is the CI check that bans immigration tokens in code, so content "must arrive as data, never in code" (SA-01 v2.2 §12; SA-01B v1.2 §13).
- **IRPA s. 91:** section 91 of the Immigration and Refugee Protection Act, the federal section on who may represent or advise a person for a fee (general knowledge; confirm with counsel; SA1-D4 cites s. 91(2)).
- **AcroForm / XFA:** AcroForm is the fillable-PDF format the built engine can fill; XFA is the dynamic format of IRCC's barcode forms, which it refuses (SA-01B v1.2 §12).
- **Catalogue and source codes:** D2 is the catalogue's dependency code for the unauthored Canada pack content (catalogue §1.4); P1 and P2 are SA-01B v1.2 §13's placeholders (how a filled form reaches the staff; which forms are mapped for Release 1); G-n are this document's gaps (section 9); W-nn are catalogue workers.
- **Proposal package:** this document's name for the files and reports the persona hands the author (G-2, Proposal). **Release note:** the persona's plain-words note of what a version changes, kept in its run record (G-6, Proposal).
