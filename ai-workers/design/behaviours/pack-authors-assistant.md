## 0. Summary: the persona in five plain lines

1. The Pack author's assistant works for one named member of Expat Ready's content team, the Content author for Canada. It watches the official government pages the pack already cites, and when a page changes it says what changed, which parts of the pack read that page, and how many firms' clients are still on the current rules (W-21).
2. When a new edition of a government form arrives, it compares the new form's boxes with the current box map, drafts the map lines for the boxes that moved or are new, and lists the rows of the pack that use that form; when a reference table changes, it drafts the new rows with the source and the date it was checked (W-19). It also drafts the French of a non-legal label; it never touches regulator or consent wording.
3. It drafts sample clients, runs the pack's own rehearsal on them against the draft and against the current version, and writes a plain-words note of what would change for a client, so the approver reads a result, not a rule (W-20). The engine decides every outcome; the assistant never scores anything.
4. Everything it produces is a proposal in a file: the author previews it and commits it into the draft by hand, runs the product's validation, and submits; a second person, who is neither the author nor the submitter, approves and publishes on a date. The assistant holds no key that writes into a pack and can never approve, publish or roll back.
5. Every step is in the platform audit chain with the delegation's reference, so for any published rule Expat Ready can show who proposed it, who committed it, who approved it, when it took effect and which firms' clients were pinned to the version before.

## 2. What it does, step by step

**How to read the tables.** *Action* is a rule the pack machinery already evaluates (validation SA-1-51; the dry-run SA-1-52; the diff SA-1-53; import preview SA-1-56; field parsing SA-1-30) or a persona recipe step marked **Proposal** and listed in section 9. The Conductor's closed action list (AG-11-2) is the firm's; the platform plane has no action vocabulary (G-1), so *Doer or rule* names the tool in the sources' own words (the validation, the test run, the diff, the import, the parsed field inventory) and the one model Doer the persona uses, the Drafter (`draft_message`, AG-11-2; here drafting a map line, a row, a sample or a note, never a message). Every model call is a plain Doer call: "models SHALL have no tool access" (AG-11-94); model output "can propose *values* (a date, a type, a draft), never *actions*, recipients, addresses or permissions" (IMP-26 rule 1). *Proposes / writes:* the persona proposes files and reports; it writes nothing into a pack. *Autonomy and floor:* the platform has no autonomy levels; the floor is the missing write key and the two-person rule. *Recorded:* the platform audit entry (SA-11-2 fields; `actorType` super_admin; `tenantId` null), the run record (IMP-35, Proposal), the AI run log row (AG-11-72; the entity has `firm_id` and needs a null-tenant form on the platform, G-1) and the delegation reference with the mode *a persona acted for a person* (DELEGATED), *the person acted directly* (PERSON) or *plain automation ran* (AUTOMATION; on the platform SA-11's `actorType = system` for a scheduled job, SA-11 v2.7 §9) (IMP-1, Proposal). In every cell the plain words come first and the product's internal name follows in brackets.

### 2.1 W-19 Pack Drafter

*In plain words.* When the government issues a new edition of a form, the content author uploads the PDF to the pack's draft and the product reads the form's boxes from it. The assistant compares those boxes with the current box map: which boxes kept their names, which moved, which are new, which are gone. For each box that is new or moved it drafts a map line, saying which client answer fills it and how (date format, code, option list), and marks every drafted line "needs review". It lists the rows of the pack that use that form so the author knows what is touched; because a row points at the form and not at an edition, no row changes. It delivers all of this as a field-map file the author previews and commits into the draft, then checks box by box against the PDF. The same pattern serves a reference table: the assistant drafts the new rows from the official page with the source and the date checked, and the author's bulk upload validates and commits them. The author, not the assistant, is the author of record.

(5) *A kill switch:* in-flight work is paused, not deleted (SA-12-11; SA-12-12); the Platform Owner is notified (SA-12-12). (6) *Who is told:* the author through the work queue (SA-1B-40); the Platform Owner for a kill switch (SA-12-12) and for a parked run; the Security & audit role reads the chain (SA-07 v2.10 Appendix A "Audit trail — read"). ## 7. Confirm with counsel / RCIC

One list; each line says why. Where a term is law, this document states general knowledge and asks counsel to confirm (README rule 5).

2. **Whether publishing immigration rules as pack content is "advice" under IRPA s. 91.** SA-01 v2.2 §1 places the content values with "the Immigration SME and product owners"; the Qualifier is deterministic (AG-3-39) and every result carries the no-guarantee wording (AG-03 v1.4 BR-11). Whether Expat Ready, as the author of the rules firms apply, needs a licensed person in its own content chain: counsel / RCIC. **Where the Code of Professional Conduct reaches the platform (the Lead's reading; counsel has not read it).** The Code (SOR/2022-128, current to 2026-09-21, verified by the Lead on 10 Oct 2026 at laws-lois.justice.gc.ca; the words copied from `case-assistant.md` §7 item 5) binds licensees, not software vendors. Two sections touch the platform indirectly. s. 19(2)(e): a licensee must "be able to deliver the services to the client using technology that is appropriate and effective": the pack is part of that technology, so a wrong published value is the licensee's exposure as well as ours. s. 38(2): the licensee "must supervise and assume professional responsibility for any work done by a person who assists": **a counsel question whether a software vendor's content, or a model's draft inside it, is "work done by a person who assists" at all.** The other sections copied in the Case assistant (22(2), 22(3), 28(1), 38(1), 38(3)) concern the firm's handling of a client's documents, status and confidentiality and do not apply to pack authoring; they are not copied here.
3. **Automated fetching of government pages (W-21).** Whether fetching canada.ca and ircc.canada.ca pages on a schedule is permitted under those sites' terms of use and Crown copyright (general knowledge; Unknown): counsel. The same question for any provincial page a provincial programme cites.
4. **The platform's own model use and residency.** AG11-D15 governs "AI and OCR processing of client data"; pack content is not client data, and samples are synthetic by rule (G-7). Whether the platform's own calls may use a provider or region the firms' calls may not, and whether the no-training term (AG-11-73) must cover pack content: counsel; the provider entry itself is IMP-6.
5. **Retention of the platform's AI run log and proposal packages.** Staff-action audit entries are kept ≥ 7 years (SA-11-14, "**confirm with counsel**" in its own text); the AI run log's interim 1 year (AG-11-98) is a firm value; the pack version is append-only. ## 10. Glossary additions

Only terms not already in `../ai-organisation.md` §8 or `case-assistant.md` §10.

- **Content author / Content Manager:** one platform role under two names: SA-07 v2.10's "Content author" ("Writes the Canada pack.") and SA-01 v2.2's "Content Manager" ("Write and maintain the pack."). The person this persona works for.
- **Content approver / content publisher:** the second person who approves, publishes and rolls back production packs, "never their own draft" (SA-07 v2.10 §2); "Platform Owner or content publisher" in SA-01 v2.2 §10.
- **Two-person rule (production pack):** "its author and its submitter can never approve or publish it (enforced on the server; refusals are audited)" (SA-01 v2.2 §3.12); the platform's approval point for this persona.
- **Draft / In review / Approved / Published:** the pack draft's states (`DRAFT → IN_REVIEW → APPROVED → published`; a rejection returns it to Draft "with the reviewer's reason", SA-01 v2.2 §3.12, §6).
- **Test-only / production pack:** a pack version's classification (`TEST_ONLY | PRODUCTION`); test-only packs "are never served to firms" and may be approved by one person (SA-1-61).
- **Validation report:** the product's pass / warning / error report before submit and publish ("Errors block; warnings don't.", SA-01 v2.2 §3.13); "The report that authorised a publish is kept." (BR-1).
- **Diff:** the per-content-area comparison of a draft against a version or of two versions, "shown in the approval step" (SA-1-53).
- **Import preview and all-or-nothing commit:** "Import previews first and commits all or nothing; it creates draft content only." (SA-1-56); the author's act that brings a proposal into a draft.
- **Form edition:** one issue of a government form, "with an edition date, an effective date and an uploaded PDF" (SA-1-28); a row points at the form, never at an edition (SA-1B-26).
- **Parsed field inventory:** the list of a PDF's fillable boxes "read on upload" (SA-1-30); what the edition comparison reads.
- **Purpose:** a named way of picking a value out of a list the client answered once ("the entry marked current", "the latest entry", and three more), which form boxes reference "never a section" (SA-1B-11, SA-1B-12).
- **Configurator row / line:** one row per full combination of Pathway › Program › Category › Sub-category, holding lines of "One line shape" for sections, documents, forms and government steps (SA-1B-55, SA-1B-57).
- **Reference table:** a typed table of official values (occupations, language scores, fees, funds, wages) built in the table designer (SA-1B-41); rows are bulk-uploaded with validation (SA-1B-44).
- **Source, date checked, next-review date:** the three fields every item reflecting a government rule carries (SA-1B-39); the watcher's inputs. **Work queue:** where overdue items appear (SA-1B-40).
- **Sample client / sample family:** the made-up person or family the dry-run runs on (SA-1-52; SA-1B-62); synthetic by rule in this document (G-7).
- **Conformance test:** AG-03 v1.4 BR-18's requirement that "known reference profiles reproduce expected scores/outcomes" before a pack version publishes; in conflict with SA1B-D18 (G-11).
- **Pinning / adoption:** a client's or case's work stays on the pack version in force when it started; staff adopt a newer version deliberately, audited (SA-1-58; AG-07 v2.7 BR-21; FD-3). **Stale assessment:** an assessment made under a version older than the current one (AG-3-29).
- **Actor type / tenant id:** on every platform audit entry, `actorType` is one of super_admin, firm_staff, client or system, and `tenantId` is "null for global actions" (SA-11-2).
- **Kill switch flag:** a `killSwitchEligible` flag tripped at PLATFORM scope with a mandatory reason under `system/flag:kill`; "pauses in-flight feature work" (SA-12-12).
- **Content-neutrality gate:** the CI check that bans immigration tokens in code so content "must arrive as data, never in code" (SA-01 v2.2 §12; SA-01B v1.2 §13).
- **CRS:** the Comprehensive Ranking System, the points grid for Express Entry candidates, named in SA-01 v2.2 §1 ("the CRS grid"); general knowledge, confirm with the Immigration SME.
- **AcroForm:** the fillable-PDF format the built engine can fill; IRCC's forms are XFA, which it refuses (SA-01B v1.2 §12).
- **Proposal package:** this document's name for the files and reports the persona hands the author (G-2, Proposal). **Release note:** the persona's plain-words note of what a version changes (G-6, Proposal).
