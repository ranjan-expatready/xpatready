## 0. Summary: the persona in five plain lines

1. When a client signs the retainer, the Case assistant starts working the file the way a careful case officer would: it asks the client for documents on the firm's own schedule, reads what arrives, fills in the client's facts with the source of every value beside it, cross-checks the facts against each other, and keeps the checklist current (W-01, W-04, W-07).
2. It drafts what the firm sends and files what the firm receives: the "please fix this upload" note in the client's language, the reply to a client's question, the letter of explanation, the entry in the file for every email and WhatsApp message (W-08, W-06, W-07). When a government letter arrives it proposes the milestone, the deadline, the task and the client update (W-03).
3. It assembles the government forms from checked values only, with no AI anywhere in the filling (W-05); on an employer's LMIA file it keeps the advertising and candidate records inspection-ready, and never screens or ranks a candidate (W-13); and it writes the internal pickup summary and each person's ranked day (W-17).
4. It never decides anything that matters: every value it proposes is verified by a person, every client message is a firm-confirmed template or is approved by whoever the firm's settings allow (a licensed person by default), every form is approved by the form approver, and the file is handed over as a "readiness report" that the reviewer approves. It never files anything with the government.
5. It works under one named case officer's delegation, with a subset of that officer's own permissions, and every step it takes is in the firm's audit log with the delegation's reference number, so a regulator or a client can be shown who was answerable for each step.

For this persona that means: a document that says *send my file to this address* is read as text, and the address is a value for a person to verify, never a recipient (IMP-26 rule 2: "a recipient must be the file's client or a firm user"); the next action is always chosen by a rule from the fixed menu, never by the model (rule 1); content from an unverified sender or an unapproved document can only produce "ask me first" items (rule 4; AG-10-47); an approval item whose values came from client content says so in one line beside the approve button (rule 6); a standing test set of planted instructions runs against every version of the model instructions before it goes live (rule 5; IMP-5).

**Restricted personal data (IMP-21, Proposal).** The persona passes a model only the fields a step needs; Restricted fields (the most sensitive personal data, such as passport and financial numbers; the exact set is the founder's open item B-1, Founder Decisions Log v1.5) are never passed, only their status (present, expired, missing); names and numbers that identify a person are replaced by record references the product resolves after the answer comes back. The one exception is the Reader, which must read the passport; its output stays by reference (AG-9-48: the log "SHALL carry no file content or extracted values"). Passport and financial numbers are never written into messages, notifications or logs (AG-7-88; AG-11 v1.11 §11).

**What happens when a limit is hit.** (1) *A floored action set too low:* the engine "SHALL re-check at run time and treat a floored action as `APPROVE`, recording why" (AG-11-53); the item waits in Needs you. (2) *A blocked action:* refused on the server (IMP-27 pattern), the action result records the refusal, the run continues past it ("Actions are non-fatal to each other", AG-11 v1.11 §3.3). (3) *A failure:* retried with backoff, then "moved to a dead-letter store with full context" and "SHALL raise a Manager Notification" (AG-11-27); the run is parked. (4) *A spend cap:* "a runaway run is stopped and parked for a manager to look at, with a notification" (IMP-36, Proposal). (5) *A stop condition (section 1):* the run stops; waiting items stay visible, marked, and cannot send (AG-11-101 pattern). (6) *Who is told:* the file owner through their Needs you queue and the Minder's reminder on overdue items (AG-11-59); users who can reassign cases (`agent/case:assign`) and the Owner for overdue and unassigned items (AG-11-55); the Owner for any Owner-route approval (AG-11-90); the firm's Manager Notification for dead letters (AG-11-27). (7) *Always recorded:* the audit entry with the delegation reference (IMP-1), and the run record state (IMP-35).

**What the approver sees (AG-11-56).** "What will happen (the dry-run rendering of §3.7), why (recipe, trigger, run, record), the provenance of every value and the confidence of any AI output, its age and its due time." For the readiness report the "why" names the persona, the delegation and the run (IMP-2(b), Proposal). *Plus one line saying whether the proposed values came from client content* (IMP-26 rule 6, Proposal).

**What the approver can do (AG-11-57).** "Approve, edit then approve, or reject (reason optional)"; "The edited version is what runs"; the action runs once under its idempotency key (a tag that stops the same action running twice if a message is redelivered, AG-11-25) and passes every send-time rail. For the readiness report: approve-all, approve-some and reject-with-reason per line (IMP-34, Proposal). **Against rubber-stamping** (the Lead's `../../proposals.md` row of 10 Oct, lenses 3 and 5, Proposal for the founder): approve-all opens every value below a confidence threshold before it can be pressed; a small random share of values is shown blank for the approver to enter and the match rate is recorded; an alarm fires when a person's agreement rate with proposals climbs above a firm-set level in a short time. This document assumes those three safeguards sit on the readiness report item once the founder decides.

**Stale items (AG-11-61).** If the record changed while the item waited, it "SHALL be re-rendered on open and flagged stale, showing what changed"; the server "SHALL refuse" an approve request "if the record or the rendering changed since". If the reason has gone (the chased document arrived, the recipe was disabled), the item "SHALL be cancelled with the reason".

**Never because time passed (AG-11-59).** "A pending item SHALL never execute because time passed." Overdue after 2 working days by default (AG-16-52); deadline-linked items due at least 2 working days before the deadline, else immediate and urgent (AG-11-100); overdue items escalate to users with `agent/case:assign` and to the Owner (AG-11-55).

**Inline approval (AG-11-78).** When the person who would approve is the one acting, for example the officer uploads a document and reviews the Reader's values, the approval is inline and no Needs you item is created; "A solo user therefore never approves their own work twice" (AG-11 v1.11 §3.13).

**Four-eyes (AIW-D33).** In the product four-eyes applies to government forms: with Team safeguards on and "the firm has 2 or more active, non-suspended users who hold `agent/case:form-approve`", "the user who prepared a form draft SHALL NOT approve it" (AG-11-81). The delegating case officer "counts as the preparer" for anything the persona prepared (AIW-D33; IMP-1), replacing "the Filler counts as no person" for persona-run drafts, so neither the persona nor that officer approves the form; with exactly one form approver, self-approval is allowed and recorded as self-approved (AG-7-65, AG-7-66). The review sign-off has no four-eyes rule in the product; the Reviewer role is "independent QA for the pre-submission review" (AG-07 v2.7 §3.8) and the firm's role settings decide who holds `agent/case:review-approve` (AIW-D26).

**Backup approver and the Owner route (AG-11-55; AG11-D11(d); IMP-17).** An item awaiting a professional approval is "shown at once in the Needs you of every active holder of the relevant approval permission", "active licensed holders marked 'preferred'" (AG-11 v1.11 §3.13); "the first holder to decide closes it for all" (AG-11-89). The Owner may nominate "one backup approver", who receives items "whose approver is suspended or deactivated, and items overdue past their due time" (AG-11-83). If nobody holds the permission, the Owner approves, recorded "approved by Owner — no active holder of the approval permission"; if an item needs a licensed approver and none is active, the Owner approves, recorded "approved by Owner without a licensed user"; "nothing is blocked" (AG-11-90; AG11-D11(d)). IMP-17(c) counts Owner-route approvals monthly (Proposal); IMP-17(b), a default pause of client-facing preparation while the firm has no active licensed user, is an open founder decision (`../ai-organisation.md` §7 decision 7) and this document does not rely on it.

## 10. Glossary additions

Only terms not already in `../ai-organisation.md` §8.

- **Binder:** the case's checklist of required documents, built from the Country Pack at case creation, with a status per document (AG-07 v2.7 §3.4).
- **Reviewer (the engine):** the part of the case module that "continuously computes, for a case, what is missing or does not meet a requirement — the deficiencies — and an overall readiness score" (AG-07 v2.7 §3.6). Not a person; the human reviewer is the role in AG-07 v2.7 §3.8.
- **Deficiency Library:** the pack-driven set of checks the Reviewer evaluates; a subset is marked Critical (AG-07 v2.7 §3.6). **Severity:** CRITICAL, MAJOR, MINOR or INFO; a CRITICAL warning is fixed or passed with a reason, never a lock (AG17-D17 per AG-07 v2.7 §3.6).
- **Filler:** the rule-based Doer that fills government forms from verified values only; not an AI Doer (AG-07 v2.7 §3.5; IMP-25).
- **Reader, Sorter, Drafter, Checker:** the four AI Doers: the Reader reads documents into proposed values; the Sorter classifies and files inbound messages; the Drafter drafts messages; the Checker cross-checks facts across documents, profile and forms (AG11-D4). "Drafter" is also the name of the template engine; IMP-24 asks the founder to rename one.
- **Unmatched inbox:** where an inbound message lands when it cannot be matched to a file; a person links or dismisses it (AG-10 v1.9 §3.2).
- **Template message:** a message "sent from a firm-scope PUBLISHED template version (AG-12) with only its merge fields filled"; the firm approved the template once, so it sends automatically (AG-11-79). **"Review your standard messages":** the one screen the firm confirms before any seeded message sends (AG-11-91).
- **Immigration-significant merge field:** a template field (dates, status, numbers, program) that renders only from a verified value; otherwise the send drops to "ask me first" (AG-11-97).
- **Quiet / "Not started":** a client, lead or case whose client-facing automation has not been switched on, so no automated message reaches it (AG-11-87). **Client paused:** items for a paused client stay in Needs you and cannot send (AG-11-101).
- **Preferred mark:** the mark and sort order that puts active licensed holders first when an item is shown to every holder of an approval permission; "not a restriction on who may decide" (AG-11-89).
- **Self-approved:** recorded whenever the approver of a form draft is also its preparer (AG-7-66).
- **Owner route:** the Owner approving an item when nobody holds the permission or no licensed user is active, recorded in the words of AG-11-90.
- **Stale item:** a waiting item whose record changed; re-rendered on open and flagged, and refused if approved on the old rendering (AG-11-61).
- **Idempotency key:** a tag on each action that stops the same action running twice if the engine redelivers a run (AG-11-25). **Dead letter:** a failed action parked with its context after retries, with a manager notification (AG-11-27).
- **Run record:** this document's name for IMP-35's `WorkerRun`: one persona's work on one case from start to stop (Proposal).
- **Shadow mode:** proposals shown beside the person's own entry, nothing applied, until the agreement rate earns trust (IMP-30, Proposal).
- **AI run log:** the record of every model call: Doer, model, prompt version, firm, record, time and outcome (AG-11-72; developers: `AiRunLog`).
- **Provenance:** where a value came from (document, page or region, message, questionnaire answer, who entered it) and when (AG-08 v1.7 §3.8; AG-8-25). **Confidence:** the model's own estimate of how sure it is, carried on every proposal and never a substitute for a person's check (AG-11-70).
- **MRZ:** the machine-readable lines on a passport that the Reader reads first (AG-9-43).
- **AOR, ADR, PPR, COPR:** the Canada PR pack's post-submission milestones: acknowledgement of receipt; additional-document request; passport request; confirmation of permanent residence (AG-07 v2.7 §3.3, §3.7; expansions general knowledge, confirm with the Immigration SME).
- **Express Entry:** the federal system for skilled-worker permanent residence applications, the beachhead case type (FD-19, Founder Decisions Log v1.5; general knowledge, confirm with the Immigration SME).
- **Substitute set:** a master document's list of alternatives, satisfied by any one member or by all together (SA-1B-19).
- **Prepared-file meter:** the count of runs whose readiness report a person approved, the unit of price-card option (a) (IMP-18, Proposal).
- **Automation bias:** the habit of approving what a machine proposes without reading it; the safeguards against it are the Lead's `../../proposals.md` row of 10 Oct (general knowledge, cited there).
